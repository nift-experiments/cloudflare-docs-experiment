<p>When building a <a href="https://modelcontextprotocol.io">Model Context Protocol (MCP)</a> server, you need both a way to allow users to login (authentication) and allow them to grant the MCP client access to resources on their account (authorization).</p>
<p>The Model Context Protocol uses <a href="https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization">a subset of OAuth 2.1 for authorization</a>. OAuth allows your users to grant limited access to resources, without them having to share API keys or other credentials.</p>
<p>Cloudflare provides an <a href="https://github.com/cloudflare/workers-oauth-provider">OAuth Provider Library</a> that implements the provider side of the OAuth 2.1 protocol, allowing you to easily add authorization to your MCP server.</p>
<p>You can use the OAuth Provider Library in four ways:</p>
<ol>
<li>Use Cloudflare Access as an OAuth provider.</li>
<li>Integrate directly with a third-party OAuth provider, such as GitHub or Google.</li>
<li>Integrate with your own OAuth provider, including authorization-as-a-service providers you might already rely on, such as Stytch, Auth0, or WorkOS.</li>
<li>Your Worker handles authorization and authentication itself. Your MCP server, running on Cloudflare, handles the complete OAuth flow.</li>
</ol>
<p>The following sections describe each of these options and link to runnable code examples for each.</p>
<h2 id="authorization-options">Authorization options</h2>
<h3 id="1-cloudflare-access-oauth-provider">(1) Cloudflare Access OAuth provider</h3>
<p>Cloudflare Access allows you to add Single Sign-On (SSO) functionality to your MCP server. Users authenticate to your MCP server using a <a href="/cloudflare-one/integrations/identity-providers/">configured identity provider</a> or a <a href="/cloudflare-one/integrations/identity-providers/one-time-pin/">one-time PIN</a>, and they are only granted access if their identity matches your <a href="/cloudflare-one/access-controls/policies/">Access policies</a>.</p>
<p>To deploy an <a href="https://github.com/cloudflare/ai/tree/main/demos/remote-mcp-cf-access">example MCP server</a> with Cloudflare Access as the OAuth provider, refer to <a href="/cloudflare-one/access-controls/ai-controls/secure-mcp-servers/">Secure MCP servers with Access for SaaS</a>.</p>
<h3 id="2-third-party-oauth-provider">(2) Third-party OAuth Provider</h3>
<p>The <a href="https://github.com/cloudflare/workers-oauth-provider">OAuth Provider Library</a> can be configured to use a third-party OAuth provider, such as GitHub or Google. You can see a complete example of this in the <a href="/agents/model-context-protocol/guides/remote-mcp-server/#add-authentication">GitHub example</a>.</p>
<p>When you use a third-party OAuth provider, you must provide a handler to the <code>OAuthProvider</code> that implements the OAuth flow for the third-party provider.</p>
<pre tabindex="0"><code class="language-ts">import MyAuthHandler from &quot;./auth-handler&quot;;&#10;&#10;export default new OAuthProvider({&#10;	apiRoute: &quot;/mcp&quot;,&#10;	// Your MCP server:&#10;	apiHandler: MyMCPServer.serve(&quot;/mcp&quot;),&#10;	// Replace this handler with your own handler for authentication and authorization with the third-party provider:&#10;	defaultHandler: MyAuthHandler,&#10;	authorizeEndpoint: &quot;/authorize&quot;,&#10;	tokenEndpoint: &quot;/token&quot;,&#10;	clientRegistrationEndpoint: &quot;/register&quot;,&#10;});&#10;</code></pre>
<p>Note that as <a href="https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization#authorization-flow-steps">defined in the Model Context Protocol specification</a> when you use a third-party OAuth provider, the MCP Server (your Worker) generates and issues its own token to the MCP client:</p>
<pre tabindex="0"><code class="language-mermaid">sequenceDiagram&#10;    participant B as User-Agent (Browser)&#10;    participant C as MCP Client&#10;    participant M as MCP Server (your Worker)&#10;    participant T as Third-Party Auth Server&#10;&#10;    C-&gt;&gt;M: Initial OAuth Request&#10;    M-&gt;&gt;B: Redirect to Third-Party /authorize&#10;    B-&gt;&gt;T: Authorization Request&#10;    Note over T: User authorizes&#10;    T-&gt;&gt;B: Redirect to MCP Server callback&#10;    B-&gt;&gt;M: Authorization code&#10;    M-&gt;&gt;T: Exchange code for token&#10;    T-&gt;&gt;M: Third-party access token&#10;    Note over M: Generate bound MCP token&#10;    M-&gt;&gt;B: Redirect to MCP Client callback&#10;    B-&gt;&gt;C: MCP authorization code&#10;    C-&gt;&gt;M: Exchange code for token&#10;    M-&gt;&gt;C: MCP access token&#10;</code></pre>
<p>Read the docs for the <a href="https://github.com/cloudflare/workers-oauth-provider">Workers OAuth Provider Library</a> for more details.</p>
<h3 id="3-bring-your-own-oauth-provider">(3) Bring your own OAuth Provider</h3>
<p>If your application already implements an OAuth Provider itself, or you use an authorization-as-a-service provider, you can use this in the same way that you would use a third-party OAuth provider, described above in <a href="#2-third-party-oauth-provider">(2) Third-party OAuth Provider</a>.</p>
<p>You can use the auth provider to:</p>
<ul>
<li>Allow users to authenticate to your MCP server through email, social logins, SSO (single sign-on), and MFA (multi-factor authentication).</li>
<li>Define scopes and permissions that directly map to your MCP tools.</li>
<li>Present users with a consent page corresponding with the requested permissions.</li>
<li>Enforce the permissions so that agents can only invoke permitted tools.</li>
</ul>
<h4 id="stytch">Stytch</h4>
<p>Get started with a <a href="https://stytch.com/docs/guides/connected-apps/mcp-servers">remote MCP server that uses Stytch</a> to allow users to sign in with email, Google login or enterprise SSO and authorize their AI agent to view and manage their company's OKRs on their behalf. Stytch will handle restricting the scopes granted to the AI agent based on the user's role and permissions within their organization. When authorizing the MCP Client, each user will see a consent page that outlines the permissions that the agent is requesting that they are able to grant based on their role.</p>

<h3 id="4-your-mcp-server-handles-authorization-and-authentication-itself">(4) Your MCP Server handles authorization and authentication itself</h3>
<p>Your MCP Server, using the <a href="https://github.com/cloudflare/workers-oauth-provider">OAuth Provider Library</a>, can handle the complete OAuth authorization flow, without any third-party involvement.</p>
<p>The <a href="https://github.com/cloudflare/workers-oauth-provider">Workers OAuth Provider Library</a> is a Cloudflare Worker that implements a <a href="/workers/runtime-apis/handlers/fetch/"><code>fetch()</code> handler</a>, and handles incoming requests to your MCP server.</p>
<p>You provide your own handlers for your MCP Server's API, and authentication and authorization logic, and URI paths for the OAuth endpoints, as shown below:</p>
<pre tabindex="0"><code class="language-ts">export default new OAuthProvider({&#10;	apiRoute: &quot;/mcp&quot;,&#10;	// Your MCP server:&#10;	apiHandler: MyMCPServer.serve(&quot;/mcp&quot;),&#10;	// Your handler for authentication and authorization:&#10;	defaultHandler: MyAuthHandler,&#10;	authorizeEndpoint: &quot;/authorize&quot;,&#10;	tokenEndpoint: &quot;/token&quot;,&#10;	clientRegistrationEndpoint: &quot;/register&quot;,&#10;});&#10;</code></pre>
<p>Refer to the <a href="/agents/model-context-protocol/guides/remote-mcp-server/">getting started example</a> for a complete example of the <code>OAuthProvider</code> in use, with a mock authentication flow.</p>
<p>The authorization flow in this case works like this:</p>
<pre tabindex="0"><code class="language-mermaid">sequenceDiagram&#10;    participant B as User-Agent (Browser)&#10;    participant C as MCP Client&#10;    participant M as MCP Server (your Worker)&#10;&#10;    C-&gt;&gt;M: MCP Request&#10;    M-&gt;&gt;C: HTTP 401 Unauthorized&#10;    Note over C: Generate code_verifier and code_challenge&#10;    C-&gt;&gt;B: Open browser with authorization URL + code_challenge&#10;    B-&gt;&gt;M: GET /authorize&#10;    Note over M: User logs in and authorizes&#10;    M-&gt;&gt;B: Redirect to callback URL with auth code&#10;    B-&gt;&gt;C: Callback with authorization code&#10;    C-&gt;&gt;M: Token Request with code + code_verifier&#10;    M-&gt;&gt;C: Access Token (+ Refresh Token)&#10;    C-&gt;&gt;M: MCP Request with Access Token&#10;    Note over C,M: Begin standard MCP message exchange&#10;</code></pre>
<p>Remember — <a href="https://www.cloudflare.com/learning/access-management/authn-vs-authz/">authentication is different from authorization</a>. Your MCP Server can handle authorization itself, while still relying on an external authentication service to first authenticate users. The <a href="/agents/model-context-protocol/guides/remote-mcp-server/">example</a> in getting started provides a mock authentication flow. You will need to implement your own authentication handler — either handling authentication yourself, or using an external authentication services.</p>
<h2 id="using-authentication-context-in-tools">Using authentication context in tools</h2>
<p>When a user authenticates through the OAuth Provider, their identity information is available inside your tools. How you access it depends on whether you use <code>McpAgent</code> or <code>createMcpHandler</code>.</p>
<h3 id="with-mcpagent-during-migration">With <code>McpAgent</code> during migration</h3>
<p>This pattern applies only to existing deprecated <code>McpAgent</code> routes. The third type parameter defines the authentication context shape. Access it through <code>this.props</code> inside <code>init()</code> and tool handlers.</p>
<pre tabindex="0"><code class="language-ts">import { McpAgent } from &quot;agents/mcp&quot;;&#10;import { McpServer } from &quot;@modelcontextprotocol/sdk/server/mcp.js&quot;;&#10;&#10;type AuthContext = {&#10;	claims: { sub: string; name: string; email: string };&#10;	permissions: string[];&#10;};&#10;&#10;export class MyMCP extends McpAgent&lt;Env, unknown, AuthContext&gt; {&#10;	server = new McpServer({ name: &quot;Auth Demo&quot;, version: &quot;1.0.0&quot; });&#10;&#10;	async init() {&#10;		this.server.tool(&quot;whoami&quot;, &quot;Get the current user&quot;, {}, async () =&gt; ({&#10;			content: [{ type: &quot;text&quot;, text: `Hello, ${this.props.claims.name}!` }],&#10;		}));&#10;	}&#10;}&#10;</code></pre>
<h3 id="with-stateless-createmcphandler">With stateless <code>createMcpHandler</code></h3>
<p>A compatible Workers OAuth Provider supplies standard token metadata at <code>context.http.authInfo</code>. Use <code>getMcpAuthContext()</code> for existing application props.</p>
<pre tabindex="0"><code class="language-ts">import { createMcpHandler, getMcpAuthContext } from &quot;agents/mcp/server&quot;;&#10;import { McpServer } from &quot;@modelcontextprotocol/server&quot;;&#10;&#10;function createServer() {&#10;	const server = new McpServer({ name: &quot;Auth Demo&quot;, version: &quot;1.0.0&quot; });&#10;&#10;	server.registerTool(&#10;		&quot;whoami&quot;,&#10;		{ description: &quot;Get the current user&quot;, inputSchema: {} },&#10;		async (_args, context) =&gt; {&#10;			const auth = getMcpAuthContext();&#10;			const name = (auth?.props.name as string) ?? &quot;anonymous&quot;;&#10;			return {&#10;				content: [&#10;					{&#10;						type: &quot;text&quot;,&#10;						text: `${name}: ${context.http?.authInfo?.clientId}`,&#10;					},&#10;				],&#10;			};&#10;		},&#10;	);&#10;&#10;	return server;&#10;}&#10;&#10;export default {&#10;	fetch(request, env, ctx) {&#10;		return createMcpHandler(createServer)(request, env, ctx);&#10;	},&#10;} satisfies ExportedHandler;&#10;</code></pre>
<p>Do not log or return the raw access token.</p>
<h2 id="permission-based-tool-access">Permission-based tool access</h2>
<p>You can control which tools are available based on user permissions. There are two approaches: check permissions inside the tool handler, or conditionally register tools.</p>
<pre tabindex="0"><code class="language-ts">export class MyMCP extends McpAgent&lt;Env, unknown, AuthContext&gt; {&#10;	server = new McpServer({ name: &quot;Permissions Demo&quot;, version: &quot;1.0.0&quot; });&#10;&#10;	async init() {&#10;		this.server.tool(&quot;publicTool&quot;, &quot;Available to all users&quot;, {}, async () =&gt; ({&#10;			content: [{ type: &quot;text&quot;, text: &quot;Public result&quot; }],&#10;		}));&#10;&#10;		this.server.tool(&#10;			&quot;adminAction&quot;,&#10;			&quot;Requires admin permission&quot;,&#10;			{},&#10;			async () =&gt; {&#10;				if (!this.props.permissions?.includes(&quot;admin&quot;)) {&#10;					return {&#10;						content: [&#10;							{ type: &quot;text&quot;, text: &quot;Permission denied: requires admin&quot; },&#10;						],&#10;					};&#10;				}&#10;				return {&#10;					content: [{ type: &quot;text&quot;, text: &quot;Admin action completed&quot; }],&#10;				};&#10;			},&#10;		);&#10;&#10;		if (this.props.permissions?.includes(&quot;special_feature&quot;)) {&#10;			this.server.tool(&quot;specialTool&quot;, &quot;Special feature&quot;, {}, async () =&gt; ({&#10;				content: [{ type: &quot;text&quot;, text: &quot;Special feature result&quot; }],&#10;			}));&#10;		}&#10;	}&#10;}&#10;</code></pre>
<p>Checking inside the handler returns an error message to the LLM, which can explain the denial to the user. Conditionally registering tools means the LLM never sees tools the user cannot access — it cannot attempt to call them at all.</p>
