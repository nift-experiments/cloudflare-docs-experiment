<p><a href="/cloudflare-one/access-controls/applications/non-http/infrastructure-apps/">Access for Infrastructure</a> provides granular control over how users can connect to your SSH servers. Like the <a href="/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-device-client/">self-managed SSH keys</a> method, it uses the Cloudflare One Client on user devices and Cloudflare Tunnel on the server to create a secure, private connection through Cloudflare's network. Access for Infrastructure adds application-level policies with per-target and per-username controls, as well as SSH command logging.</p>
<p>Furthermore, Access for Infrastructure replaces traditional SSH keys with short-lived certificates issued to your users based on the token generated by their Access login. In traditional models, users generate an SSH key pair and administrators grant access to individual SSH servers by deploying their users' public keys to those servers. These SSH keys can remain unchanged on these servers for months or years. Cloudflare Access removes the burden of managing SSH keys, while also improving security by replacing long-lived SSH keys with ephemeral SSH certificates.</p>

<h3 id="save-the-public-key">Save the public key</h3>
<ol>
<li>Use the following command to change directories to the SSH configuration directory on the remote target machine:</li>
</ol>
<pre tabindex="0"><code class="language-sh">cd /etc/ssh&#10;</code></pre>
<ol start="2">
<li>Once there, you can use the following command to both generate the file and open a text editor to input/paste the public key.</li>
</ol>
<pre tabindex="0"><code class="language-sh">vim ca.pub&#10;</code></pre>
<ol start="3">
<li>In the <code>ca.pub</code> file, paste the public key without any modifications.</li>
</ol>
<pre tabindex="0"><code class="language-txt">ecdsa-sha2-nistp256 &lt;redacted&gt; open-ssh-ca@cloudflareaccess.org&#10;</code></pre>
<p>The <code>ca.pub</code> file can hold multiple keys, listed one per line. Empty lines and comments starting with <code>#</code> are also allowed.</p>
<ol start="4">
<li>Save the <code>ca.pub</code> file. In some systems, you may need to use the following command to force the file to save depending on your permissions:</li>
</ol>
<pre tabindex="0"><code class="language-bash">:w !sudo tee %&#10;:q!&#10;</code></pre>
<h3 id="modify-your-sshd-config-file">Modify your <code>sshd_config</code> file</h3>
<p>Configure your SSH server to trust the Cloudflare SSH CA by updating the <code>sshd_config</code> file on the remote target machine.</p>
<ol>
<li>While in the <code>/etc/ssh</code> directory on the remote machine, open the <code>sshd_config</code> file.</li>
</ol>
<pre tabindex="0"><code class="language-sh"> sudo vim /etc/ssh/sshd_config&#10;</code></pre>
<ol start="2">
<li>Press <code>i</code> to enter insert mode, then add the following lines at the top of the file, above all other directives:</li>
</ol>
<pre tabindex="0"><code class="language-txt">PubkeyAuthentication yes&#10;TrustedUserCAKeys /etc/ssh/ca.pub&#10;</code></pre>

<h2 id="8-optional-require-independent-mfa-for-ssh"><ol start="8">
<li>(Optional) Require independent MFA for SSH</li>
</ol></h2>
<p>You can require users to authenticate with a PIV key or FIDO2 key before connecting to SSH servers. When configuring custom MFA, select <strong>PIV key</strong>, <strong>FIDO2 key</strong>, or both.</p>
<p>To configure independent MFA for SSH, refer to <a href="/cloudflare-one/access-controls/policies/mfa-requirements/#infrastructure-applications">Enforce MFA for infrastructure applications</a>.</p>
<p>Before users can connect with MFA turned on, they must enroll their key and configure their SSH client.</p>
<ul>
<li>For PIV keys, <a href="/cloudflare-one/access-controls/access-settings/independent-mfa/#enroll-a-piv-key-for-infrastructure-apps">enroll the key</a> and <a href="/cloudflare-one/access-controls/access-settings/independent-mfa/#configure-your-ssh-client">configure the SSH client</a>.</li>
<li>For FIDO2 keys, <a href="/cloudflare-one/access-controls/access-settings/independent-mfa/#enroll-a-fido2-key-for-infrastructure-apps">enroll the key</a> and <a href="/cloudflare-one/access-controls/access-settings/independent-mfa/#configure-your-ssh-client-for-a-fido2-key">configure the SSH client</a>.</li>
</ul>
<p>When the user runs <code>ssh &lt;username&gt;@&lt;target IP&gt;</code>, the SSH proxy checks if MFA is required for the matching policy. If required, the user authenticates with their hardware key. Whether the key prompts for a touch, a PIN, or both depends on the PIV key policies you configured or on the FIDO2 key's own configuration. The proxy then completes the connection.</p>

<h2 id="ssh-command-logs">SSH command logs</h2>
<p>SSH command logs contain the actual SSH commands that a user ran on the target. Customers on all plans can store SSH logs on Cloudflare and download the logs from the dashboard. <a href="#download-encrypted-ssh-logs">Downloadable logs</a> are encrypted using a public key provided by the customer and are not visible to Cloudflare. Delivery of downloadable SSH logs is best effort; for guaranteed delivery, Enterprise customers can <a href="#export-ssh-logs-with-logpush">configure a Logpush job</a> to send SSH logs to storage destinations. Logpush payloads are not encrypted with a customer-provided public key.</p>
<h3 id="download-encrypted-ssh-logs">Download encrypted SSH logs</h3>
<p>Follow these instructions to encrypt and download SSH command logs from Zero Trust.</p>
<h4 id="enable-ssh-command-logging">Enable SSH command logging</h4>
<p>To log SSH commands, you will need to generate an HPKE key pair and upload the public key to Cloudflare.</p>
<ol>
<li>
<p><a href="https://github.com/cloudflare/ssh-log-cli/releases/latest/">Download</a> the Cloudflare <code>ssh-log-cli</code> utility.</p>
</li>
<li>
<p>Using the <code>ssh-log-cli</code> utility, generate a public and private key pair.</p>
</li>
</ol>
<pre tabindex="0"><code class="language-sh">./ssh-log-cli generate-key-pair -o sshkey&#10;ls&#10;</code></pre>
<pre tabindex="0"><code class="language-sh">README.md    ssh-log-cli    sshkey    sshkey.pub&#10;</code></pre>
<p>This command outputs two files, an <code>sshkey.pub</code> public key and a matching <code>sshkey</code> private key.</p>
<ol start="3">
<li>
<p>In the <a href="https://dash.cloudflare.com/">Cloudflare dashboard</a>, go to <strong>Zero Trust</strong> &gt; <strong>Traffic policies</strong> &gt; <strong>Traffic settings</strong>.</p>
</li>
<li>
<p>In <strong>SSH log encryption public key</strong>, paste the contents of <code>sshkey.pub</code> and select <strong>Save</strong>.</p>
</li>
</ol>
<p>All proxied SSH commands are immediately encrypted using this public key. The matching private key is required to view logs.</p>

<h4 id="view-ssh-logs">View SSH logs</h4>
<p>SSH command logs are not visible from the dashboard itself and must be exported and decrypted.</p>
<p>To manually retrieve logs:</p>
<ol>
<li>In the <a href="https://dash.cloudflare.com/">Cloudflare dashboard</a>, go to <strong>Zero Trust</strong> &gt; <strong>Insights</strong> &gt; <strong>Logs</strong>.</li>
<li>Select <strong>SSH command logs</strong>.</li>
<li>Filter the logs using the name of your <a href="#5-add-an-infrastructure-application">SSH application</a>.</li>
<li>Select the SSH session for which you want to export command logs.</li>
<li>In the side panel, scroll down to <strong>SSH logs</strong> and select <strong>Download</strong>.</li>
<li></li>
</ol>
<p>To decrypt the log, follow the instructions in the <a href="https://github.com/cloudflare/ssh-log-cli/">SSH Logging CLI repository</a>. In the following example, <code>sshkey</code> is the private key that matches the public key uploaded to Cloudflare.</p>
<pre tabindex="0"><code class="language-sh">./ssh-log-cli decrypt -i sshlog -k sshkey&#10;</code></pre>
<p>This command outputs a <code>sshlog-decrypted.zip</code> file with the decrypted logs.</p>

<h2 id="known-limitations">Known limitations</h2>

<h3 id="5-debug-sshd-config-file-misconfiguration"><ol start="5">
<li>Debug <code>sshd_config</code> file misconfiguration</li>
</ol></h3>
<p>One reason a user is failing to connect to your SSH endpoint might be the result of a misconfigured <code>sshd_config</code> file. Follow the steps below to audit your <code>sshd_config</code> file for misconfigurations.</p>
<h4 id="review-your-sshd-logs">Review your <code>sshd</code> logs</h4>
<p><code>sshd</code> logs can confirm whether or not the user is making it to the server. The location of your <code>sshd</code> logs is defined in your <code>sshd_config</code>. The logs location is likely at <code>journalctl -u ssh</code> on Ubuntu and <code>tail /var/log/auth.log</code> for Red Hat.</p>
<p>Using your <code>sshd</code> logs, validate that SSH connection attempts are arriving to the server.</p>

<h4 id="confirm-the-account-authorizes-the-certificate-principal">Confirm the account authorizes the certificate principal</h4>
<p>If your <code>sshd</code> logs show that the certificate was accepted as CA-signed but the connection still fails, the account may not authorize the certificate's principal. <code>sshd</code> reports this as:</p>
<pre tabindex="0"><code class="language-txt">Certificate invalid: name is not a listed principal&#10;</code></pre>
<p>Check the effective configuration for the account you are connecting as, because these directives are often set within a <code>Match</code> block:</p>
<pre tabindex="0"><code class="language-sh">sudo sshd -T -C user=&lt;USERNAME&gt; | grep -i principals&#10;</code></pre>
<p>If <code>authorizedprincipalsfile</code> or <code>authorizedprincipalscommand</code> is set to any value other than <code>none</code>, confirm that the SSH username appears in that file or in the command's output. If it is missing, add it, validate your configuration with <code>sudo sshd -t</code>, then <a href="#reload-your-ssh-server">reload</a> your SSH server.</p>
