<h4 id="multiple-versions-of-the-same-log">Multiple versions of the same log</h4>
<p>The <code>warp-debugging-info</code> folder may contain multiple versions of the same log, such as <code>daemon.log</code>, <code>daemon.1.log</code>, and <code>daemon.2.log</code>. Since logs can get very long, they are rotated either daily or when they exceed a certain size.</p>
<ul>
<li><code>&lt;logfile&gt;.log</code> is the most current log. This is almost always the log you should be looking at, as it shows events that occurred on the day you ran the <code>warp-diag</code> command.</li>
<li><code>&lt;logfile&gt;.1.log</code> shows events from the previous day.</li>
<li><code>&lt;logfile&gt;.2.log</code> shows events from two days before.</li>
</ul>

<h3 id="extra-debug-logging">Extra debug logging</h3>
<p>Starting with version 2026.5.0, you can enable extra debug logging with the command <code>warp-cli debug extra start</code>.
Extra debug logging times out after 10 minutes unless you manually stop it with <code>warp-cli debug extra stop</code>.</p>
<p>This enables a few more logging features:</p>
<ul>
<li>Packet captures (PCAPs) on all interfaces (on Windows, the original <code>.etl</code> file is preserved; other PCAP commands convert it to <code>.pcap</code> before removing it)</li>
<li>QLog files for MASQUE tunnel connections</li>
<li>DNS logs for <a href="/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/modes/">service modes with DNS filtering</a></li>
<li>One-shot connectivity checks (same information as <code>connectivity.txt</code>, collected when extra debug logging starts rather than when <code>warp-diag</code> runs)</li>
<li>One-shot traceroutes to:
<ul>
<li>DNS resolver IPs</li>
<li>DNS resolver hostname</li>
<li>Device API endpoint IPs</li>
<li>Device API endpoint hostname</li>
<li>Tunnel edge connection IPs</li>
</ul>
</li>
<li>On Windows, if you are an administrator:
<ul>
<li><a href="https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-trace"><code>netsh</code> trace</a> with the <code>Microsoft-Windows-TCPIP</code> provider</li>
<li><a href="https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-wfp">WFP capture</a></li>
</ul>
</li>
</ul>
<p>If extra debug logging is enabled, the command <code>warp-cli debug extra reconnect</code> forces the tunnel connection to restart.
This can be useful for collecting log information if the tunnel connection fails.</p>

<h3 id="log-retention-window">Log retention window</h3>
<p>Each client log file (such as <code>connection_stats.log</code>, <code>dns_stats.log</code>, <code>daemon.log</code>, <code>boringtun.log</code>, <code>daemon_dns.log</code>, <code>dex.log</code> and <code>captive-portal.log</code>) is limited by size and age:</p>
<ul>
<li><strong>Maximum file size:</strong> 10 MB</li>
<li><strong>Maximum file age:</strong> 24 hours</li>
<li><strong>Maximum number of retained versions per log:</strong> 4 (for example, <code>daemon.log</code>, <code>daemon.1.log</code>, <code>daemon.2.log</code>, and <code>daemon.3.log</code>)</li>
</ul>
<p>Log files may include data from up to 96 hours (four days) prior to when <code>warp-diag</code> was run, but only if log activity is minimal. In environments with high logging volume (for example, repeated errors), logs may rotate more frequently, and the captured window could be much shorter (only a few hours).</p>
<p>Always check the timestamps at the end of each log file to verify the time range covered by the diagnostic archive.</p>
