<p>Random prefix attacks are when someone sends a lot of traffic to subdomains that are highly unlikely to exist (<code>12345.example.com</code>, <code>abcdefg.example.com</code>), but are still associated with your main domain (<code>example.com</code>).</p>
<p>Usually, a DNS query to each random subdomain (or prefix) is not repeated, so it cannot be cached by resolvers or any other proxies and always reaches the authoritative nameservers. Rate limiting or blocking queries based on source IP can introduce a high amount of false positives, since random prefix attacks commonly are conducted via public resolvers. This makes these attacks particularly effective and hard to mitigate.
<br /></p>
<h2 id="attack-characteristics">Attack characteristics</h2>
<h3 id="queries-for-nonexistent-domains">Queries for nonexistent domains</h3>
<p>If the request only involved nonexistent domains, the <code>NXDOMAIN</code> errors would only be served by the top-level domain (TLD) nameservers for <code>com.</code>. This means that the queries never reach the authoritative nameservers.</p>

<br />
<h3 id="queries-for-nonexistent-subdomains">Queries for nonexistent subdomains</h3>
<p>These attacks are successful because they target subdomains, which require a response from a domain's authoritative nameservers.</p>
<pre tabindex="0"><code class="language-mermaid">    flowchart TD&#10;      accTitle: Random prefix attacks diagram&#10;      A[End user query to &lt;code&gt;random.example.com&lt;/code&gt;] --&quot;1)&quot;--&gt; B[&lt;code&gt;1.1.1.1 resolver&lt;/code&gt;]&#10;      B -- &quot;2)&quot; --&gt; C[&lt;code&gt;com.&lt;/code&gt; TLD NS]&#10;      C -- &quot;3)&quot; Query Authoritative NS --&gt; B&#10;      B -- &quot;4)&quot; --&gt; D[Authoritative NS]&#10;      D --&quot;5)&quot; &lt;code&gt;NXDOMAIN error&lt;/code&gt;--&gt; B&#10;      B --&quot;6)&quot; &lt;code&gt;NXDOMAIN error&lt;/code&gt;--&gt; A&#10;</code></pre>
<br />
<p>With an attack against a subdomain of an existing domain, the resolver is forced to fully resolve it against the authoritative nameservers since these random subdomains are likely not cached by the resolver or any other proxy. If an attacker sends enough of these queries, and the authoritative nameservers cannot handle the query load, it will become unresponsive or even fall over, taking all zones it is hosting down, not just the attacked zone.</p>
<p>This attack is difficult to mitigate for a few reasons. From the perspective of the authoritative nameservers, the attacker appears to be Cloudflare (<code>1.1.1.1</code>) since that is the source of the queries. Blocking Cloudflare is not an option since that will block legitimate traffic.</p>
<h2 id="solution">Solution</h2>
<p>When you <a href="/dns/dns-firewall/random-prefix-attacks/setup/">enable random prefix attack mitigations</a>, Cloudflare monitors incoming queries for potential random prefix attacks.</p>
<p>When we detect an attack, we will temporarily stop querying your upstream nameservers for subdomains, sub-subdomains, and more. Cloudflare will then respond with cached responses (if their TTL has not yet expired).</p>
