<p>When you have a partial zone (<div class="nb-interactive-component" data-cf-component="GlossaryTooltip"></p>
@markup("md", "content/.markup/bodies/7939.md")
</div>), Cloudflare handles DNS records a bit differently from primary zones (full setup) in order to internally resolve the origin server where proxied HTTP requests are sent to.
<h2 id="records-within-the-same-zone">Records within the same zone</h2>
<p>When you <a href="/dns/manage-dns-records/how-to/create-dns-records/#create-dns-records">create a new DNS record</a> in a partial zone, Cloudflare automatically checks whether any of your CNAME records point to existing A, AAAA, or CNAME records within the same zone.</p>
<p>For example, Cloudflare would show a warning if you had the following records in your partial zone:</p>
<pre><code class="language-txt">sub1.partialzone.com   CNAME   sub2.partialzone.com&#10;sub2.partialzone.com   A       192.0.2.1&#10;</code></pre>
<p>Since Cloudflare contains both the CNAME and its target, our DNS resolution will send incoming HTTP requests to <code>sub1.partialzone.com</code> to the origin <code>192.0.2.1</code>.</p>
<p>This can cause issues if you already have DNS records for <code>sub2.partialzone.com</code> at your authoritative DNS provider. These records may point to <code>192.0.2.4</code>, another IP address, or another domain but - because Cloudflare contains the initial record and the target - it never queries your authoritative DNS provider for the record for <code>sub2.partialzone.com</code>.</p>
<pre><code class="language-mermaid">    flowchart TD&#10;      accTitle: DNS resolution flow with CNAME target in same partial zone&#10;      A[Request to &lt;code&gt;sub1.partialzone.com&lt;/code&gt;] --&gt; B[&lt;code&gt;CNAME&lt;/code&gt; record for &lt;code&gt;sub1.partialzone.com&lt;/code&gt; to &lt;code&gt;sub2.partialzone.com&lt;/code&gt;]&#10;      subgraph Cloudflare&#10;        B --&gt; C[&lt;code&gt;A&lt;/code&gt; record for &lt;code&gt;sub2.partialzone.com&lt;/code&gt; to &lt;code&gt;192.0.2.1&lt;/code&gt;]&#10;      end&#10;      C --&gt; D[&lt;code&gt;192.0.2.1&lt;/code&gt;]&#10;      subgraph Authoritative DNS&#10;      E[&lt;code&gt;A&lt;/code&gt; record for &lt;code&gt;sub2.partialzone.com&lt;/code&gt; to &lt;code&gt;192.0.2.4&lt;/code&gt;]&#10;      end&#10;</code></pre>
<br />
<p>When you avoid this situation - meaning you do not have the <strong>target</strong> of the CNAME record within your partial zone - this DNS resolution would happen differently.</p>
<pre><code class="language-mermaid">    flowchart TD&#10;      accTitle: DNS resolution flow with CNAME target not in partial zone&#10;      A[Request to &lt;code&gt;sub1.partialzone.com&lt;/code&gt;] --&gt; B[&lt;code&gt;CNAME&lt;/code&gt; record for &lt;code&gt;sub1.partialzone.com&lt;/code&gt; to &lt;code&gt;sub2.partialzone.com&lt;/code&gt;]&#10;      B --&gt; C[&lt;code&gt;A&lt;/code&gt; record for &lt;code&gt;sub2.partialzone.com&lt;/code&gt; to &lt;code&gt;192.0.2.4&lt;/code&gt;]&#10;      C --&gt; D[&lt;code&gt;192.0.2.4&lt;/code&gt;]&#10;      subgraph Cloudflare&#10;        B&#10;      end&#10;      subgraph Authoritative DNS&#10;        C&#10;      end&#10;</code></pre>

<h2 id="records-pointing-to-a-partial-zone-within-the-same-account">Records pointing to a partial zone within the same account</h2>
<p>You could also <a href="/dns/manage-dns-records/how-to/create-dns-records/#create-dns-records">create a CNAME record</a> in a zone (partial or full) that points to a record in another partial zone within your account.</p>
<p>In this case, Cloudflare will always resolve the CNAME target based on the value at your authoritative DNS provider of the CNAME target zone.</p>
<pre><code class="language-mermaid">    flowchart TD&#10;      accTitle: DNS resolution flow with CNAME target in a zone within the same account&#10;      A[Request to &lt;code&gt;www\.alice.com&lt;/code&gt;] --&gt; B[&lt;code&gt;CNAME&lt;/code&gt; record for &lt;code&gt;www\.alice.com&lt;/code&gt; to &lt;code&gt;www\.partialzone.com&lt;/code&gt;]&#10;      B --&gt; C[&lt;code&gt;A&lt;/code&gt; record for &lt;code&gt;www\.partialzone.com&lt;/code&gt; to &lt;code&gt;192.0.2.4&lt;/code&gt;]&#10;      C --&gt; D[&lt;code&gt;192.0.2.4&lt;/code&gt;]&#10;      subgraph Cloudflare account&#10;        subgraph Cloudflare zone 1&#10;          B&#10;        end&#10;        subgraph Cloudflare zone 2&#10;        E[&lt;code&gt;A&lt;/code&gt; record for &lt;code&gt;www\.partialzone.com&lt;/code&gt; to &lt;code&gt;203.0.113.1&lt;/code&gt;]&#10;        end&#10;      end&#10;      subgraph Authoritative DNS&#10;      C&#10;      end&#10;</code></pre>
<h3 id="auth-dns-points-to-cdn-cloudflare-net">Auth DNS points to <code>cdn.cloudflare.net</code></h3>
<p>Considering the following scenario:</p>
<ul>
<li>The target zone (Cloudflare zone 2 in this example) is a partial zone and the DNS record on the partial zone is proxied.</li>
<li>The DNS record on the authoritative DNS server points to <code>cdn.cloudflare.net</code></li>
</ul>
<p>If such setup is in place, the subdomain (<code>www.partialzone.com</code> in this example) will resolve to a Cloudflare proxy IP, which will ultimately result in an error. Consider using <a href="/cloudflare-for-platforms/cloudflare-for-saas/domain-support/">custom hostnames</a> and <a href="/cloudflare-for-platforms/cloudflare-for-saas/saas-customers/how-it-works/">O2O</a> setup instead.</p>
