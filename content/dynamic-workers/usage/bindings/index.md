<p>Bindings let you control what a Dynamic Worker can access. When you create a Dynamic Worker, you decide exactly what resources and operations it can use.</p>
<p>This allows you to:</p>
<ul>
<li><strong>Give each Dynamic Worker its own resources</strong> — Partition a <a href="/kv/">KV</a> namespace, <a href="/r2/">R2</a> bucket, or database so each worker only sees its own data.</li>
<li><strong>Expose custom capabilities</strong> — Define your own methods that Dynamic Workers can call — like posting to a chat room, sending an email, or querying an internal service. You design the interface and the Dynamic Worker just calls it.</li>
<li><strong>Restrict and control access</strong> — Inspect, transform, or reject calls before they reach the underlying resource.</li>
</ul>
<h2 id="custom-bindings-with-dynamic-workers">Custom Bindings with Dynamic Workers</h2>
<p>With custom bindings, you:</p>
<ul>
<li><strong>Define the binding implementation in your loader Worker</strong>: You create a class with methods. Because this runs in your loader Worker, that's where you can add authentication, logging, scope access per customer.</li>
<li><strong>Pass it to the Dynamic Worker as a binding</strong>: It just calls methods like <code>this.env.CHAT_ROOM.post(&quot;Hello!&quot;)</code> without knowing anything about the implementation behind it.</li>
</ul>
<h3 id="how-it-works">How it works</h3>
<h4 id="step-1-define-the-binding">Step 1: Define the binding</h4>
<p>To create a custom binding, your loader Worker needs to implement a <a href="/workers/runtime-apis/bindings/service-bindings/rpc#the-workerentrypoint-class"><code>WorkerEntrypoint</code> class</a> and export it. The methods you define on this class are the methods the Dynamic Worker will be able to call.</p>
<pre tabindex="0"><code class="language-ts">import { WorkerEntrypoint } from &quot;cloudflare:workers&quot;;&#10;&#10;export class ChatRoom extends WorkerEntrypoint {&#10;  async post(text: string): Promise&lt;void&gt; {&#10;    // Your implementation here&#10;  }&#10;}&#10;</code></pre>
<h4 id="step-2-pass-it-to-the-dynamic-worker">Step 2: Pass it to the Dynamic Worker</h4>
Your loader Worker will then create an instance of the exported class, called a stub, and pass it into the Dynamic Worker's `env`. 
<pre tabindex="0"><code class="language-ts">let chatRoom = ctx.exports.ChatRoom({ props: { roomName: &quot;#bot-chat&quot; } });&#10;&#10;let worker = env.LOADER.load({&#10;  env: { CHAT_ROOM: chatRoom },&#10;  // ...&#10;});&#10;</code></pre>
<p>From the Dynamic Worker's perspective, <code>CHAT_ROOM</code> just looks like a regular binding with methods it can call:</p>
<pre tabindex="0"><code class="language-ts">// Inside the Dynamic Worker&#10;await this.env.CHAT_ROOM.post(&quot;Hello!&quot;);&#10;</code></pre>
<h4 id="step-3-customize-per-user-with-props">Step 3: Customize per user with props</h4>
One class can serve many different Dynamic Workers. Instead of defining a separate class for each user, you pass in `props` when creating the stub, which contains information specific to that user. 
<pre tabindex="0"><code class="language-ts">// Same class, different props per user&#10;let aliceRoom = ctx.exports.ChatRoom({ props: { roomName: &quot;#alice&quot;, apiKey: ALICE_KEY } });&#10;let bobRoom   = ctx.exports.ChatRoom({ props: { roomName: &quot;#bob&quot;, apiKey: BOB_KEY } });&#10;</code></pre>
<p>When the Dynamic Worker calls a method on the binding, it's actually making a call back to your loader Worker, that's where the method runs. Inside that method, you can read the <code>props</code> via <a href="/workers/runtime-apis/context#props"><code>this.ctx.props</code></a>. Only the loader Worker has access to the props, the Dynamic Worker never sees them.</p>
<pre tabindex="0"><code class="language-ts">export class ChatRoom extends WorkerEntrypoint&lt;Cloudflare.Env, ChatRoomProps&gt; {&#10;  async post(text: string): Promise&lt;void&gt; {&#10;    // Props are set when the stub is created — the Dynamic Worker never sees them&#10;    let roomName = this.ctx.props.roomName;&#10;    await postToChat(roomName, text);&#10;  }&#10;}&#10;</code></pre>
<h3 id="example-chat-room-agent">Example: Chat room agent</h3>
Here's a complete example putting it all together. Say you're building a platform where AI agents can post to chat rooms. Each agent should only be able to post to its assigned room and it should never see the API key used to authenticate.
<p>You define a <code>ChatRoom</code> class in your parent Worker. This class has a <code>post</code> method, the only method the Dynamic Worker can call on this binding. Inside this class, you control which room the message goes to, which API key is used, and what name is attached to the message.</p>
<pre tabindex="0"><code class="language-ts">import { WorkerEntrypoint } from &quot;cloudflare:workers&quot;;&#10;&#10;export class ChatRoom extends WorkerEntrypoint&lt;Cloudflare.Env, ChatRoomProps&gt; {&#10;  async post(text: string): Promise&lt;void&gt; {&#10;    let { apiKey, botName, roomName } = this.ctx.props;&#10;&#10;    // Prefix the message with the bot&#x27;s name.&#10;    text = `[${botName}]: ${text}`;&#10;&#10;    // Send it to the chat service.&#10;    await postToChat(apiKey, roomName, text);&#10;  }&#10;}&#10;&#10;type ChatRoomProps = {&#10;  apiKey: string;&#10;  roomName: string;&#10;  botName: string;&#10;};&#10;</code></pre>
<p>You export one <code>ChatRoom</code> class, but each stub you create can have different <code>props</code> — a different room name, a different API key, a different bot name. The <code>props</code> are set when you create the stub, and the Dynamic Worker never sees them.</p>
<p>Now pass it to a Dynamic Worker:</p>
<pre tabindex="0"><code class="language-ts">// Create a stub scoped to a specific room.&#10;let chatRoom = ctx.exports.ChatRoom({&#10;  props: {&#10;    apiKey,&#10;    roomName: &quot;#bot-chat&quot;,&#10;    botName: &quot;Robo&quot;,&#10;  },&#10;});&#10;&#10;let worker = env.LOADER.load({&#10;  env: {&#10;    CHAT_ROOM: chatRoom,&#10;  },&#10;  compatibilityDate: &quot;$today&quot;,&#10;  mainModule: &quot;index.js&quot;,&#10;  modules: {&#10;    &quot;index.js&quot;: `&#10;      export class Agent extends WorkerEntrypoint {&#10;        async run() {&#10;          // This is all the Dynamic Worker sees.&#10;          await this.env.CHAT_ROOM.post(&quot;Hello!&quot;);&#10;        }&#10;      }&#10;    `,&#10;  },&#10;  globalOutbound: null,&#10;});&#10;&#10;return worker.getEntrypoint(&quot;Agent&quot;).run();&#10;</code></pre>
<p>The agent just calls <code>this.env.CHAT_ROOM.post(&quot;Hello!&quot;)</code>. It has no way to post to a different room, see or use the API key, or change the bot name attached to its messages.</p>
<h3 id="tip-tell-your-agent-about-the-types">Tip: Tell your agent about the types</h3>
<p>For an AI agent to write code against your bindings, it needs to know the interface. Give your agent TypeScript type declarations with doc comments describing each method. Modern LLMs understand TypeScript well, making it the most concise way to describe a JavaScript API. This works even if the agent is writing plain JavaScript.</p>
<p>Make sure your <code>WorkerEntrypoint</code> class extends the TypeScript type so the declarations stay in sync with the implementation.</p>
<h2 id="passing-normal-workers-bindings">Passing normal Workers bindings</h2>
<p>To pass resources like a <a href="/kv/">KV</a> namespace or <a href="/r2/">R2</a> bucket to a Dynamic Worker, you need to bind the resource to your loader Worker and create a custom binding that wraps it. You can scope access per customer by prefixing keys and defining only the methods you want to expose.</p>
<h3 id="example-scoping-a-kv-namespace-per-customer">Example: Scoping a KV namespace per customer</h3>
<p>First, bind the KV namespace to your loader Worker. Then in your loader Worker, export a class that uses the KV binding and defines the methods Dynamic Workers can call:</p>
<pre tabindex="0"><code class="language-ts">import { WorkerEntrypoint } from &quot;cloudflare:workers&quot;;&#10;&#10;export class MyStorage extends WorkerEntrypoint&lt;Cloudflare.Env, MyStorageProps&gt; {&#10;  // Export this class from your loader Worker&#10;  // The Dynamic Worker will be able to call get() and put()&#10;  async get(key: string): Promise&lt;string | null&gt; {&#10;    // Prefix the key so this customer can only access their own data&#10;    return this.env.MY_KV.get(`${this.ctx.props.prefix}:${key}`);&#10;  }&#10;&#10;  async put(key: string, value: string): Promise&lt;void&gt; {&#10;    await this.env.MY_KV.put(`${this.ctx.props.prefix}:${key}`, value);&#10;  }&#10;}&#10;&#10;type MyStorageProps = {&#10;  prefix: string;&#10;};&#10;</code></pre>
<p>Then pass it to the Dynamic Worker with a customer-specific prefix:</p>
<pre tabindex="0"><code class="language-ts">// Create a stub scoped to this customer&#x27;s prefix&#10;let storage = ctx.exports.MyStorage({&#10;  props: { prefix: `customer-${customerId}` },&#10;});&#10;&#10;let worker = env.LOADER.load({&#10;  env: { STORAGE: storage },&#10;  // ...&#10;});&#10;</code></pre>
<p>The Dynamic Worker just uses it like any other binding:</p>
<pre tabindex="0"><code class="language-ts">// Inside the Dynamic Worker, it just sees STORAGE with get and put&#10;let value = await this.env.STORAGE.get(&quot;settings&quot;);&#10;await this.env.STORAGE.put(&quot;settings&quot;, &quot;dark-mode&quot;);&#10;</code></pre>
<p>This same pattern works for any resource your loader Worker has access to — <a href="/r2/">R2</a> buckets or <a href="/d1/">D1</a> databases. Bind the resource to your loader Worker, export a class that uses it, and pass the stub to the Dynamic Worker.</p>
<p>For persistent storage that lives with each Dynamic Worker, see <a href="/dynamic-workers/usage/durable-object-facets/">Durable Object Facets</a>.</p>
<h2 id="capability-based-sandboxing">Capability-based Sandboxing</h2>
<p>Custom bindings follow a capability-based security model — a Dynamic Worker can only access what you explicitly give it.  If it hasn't received a stub for something, it can't access it.</p>
<p>This is powered by Workers RPC, also known as <a href="https://github.com/cloudflare/capnweb">Cap'n Web</a>, an RPC system designed to pass object references across security boundaries. When a Dynamic Worker receives a stub, it can call that object's methods and each call is an RPC back to the original object in your loader Worker. Stubs have no global identifier and cannot be forged, the only way to obtain one is to receive it.</p>
<p>Capability-based security is essential to the design of most successful sandboxes, though it's usually hidden as an implementation detail — Android has Binder, Chrome has Mojo, and Cloudflare Workers has Cap'n Web. Dynamic Workers directly expose this power to you, the developer, so that you can build your own strong sandbox.</p>
