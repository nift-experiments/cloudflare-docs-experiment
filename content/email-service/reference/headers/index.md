<p class="article-summary">Which email headers you can set, which are auto-generated, and how they are validated</p>
<p>When sending emails with Cloudflare Email Service, you can set custom headers using the <code>headers</code> field in the <a href="/email-service/api/send-emails/workers-api/">Workers API</a> or <a href="/email-service/api/send-emails/rest-api/">REST API</a>. The Email Service uses a <strong>allowlist-based approach</strong> — only explicitly approved headers are accepted. Any header not on the allowlist (and not an <code>X-</code> prefixed custom header) is rejected at API time with a clear error.</p>
<p>When sending over <a href="/email-service/api/send-emails/smtp/">SMTP</a>, set headers directly in the MIME message rather than through a <code>headers</code> field. The same allowlist applies.</p>
<h2 id="platform-controlled-headers">Platform-controlled headers</h2>
<p>These headers are auto-generated by the Cloudflare Email Service infrastructure. You cannot set or override them. If you include any of these in the <code>headers</code> object, the API returns <code>E_HEADER_NOT_ALLOWED</code>.</p>

<p>Headers that correspond to first-class API fields — <code>From</code>, <code>To</code>, <code>Cc</code>, <code>Bcc</code>, <code>Subject</code>, <code>Reply-To</code> — are also rejected in the <code>headers</code> object with <code>E_HEADER_USE_API_FIELD</code>. Set these using the dedicated API fields (<code>from</code>, <code>to</code>, <code>cc</code>, <code>bcc</code>, <code>subject</code>, <code>replyTo</code> for Workers / <code>reply_to</code> for REST) instead.</p>
<h2 id="allowlisted-custom-headers">Allowlisted custom headers</h2>
<p>These headers can be set via the <code>headers</code> field. Any header not listed here and not starting with <code>X-</code> is rejected with <code>E_HEADER_NOT_ALLOWED</code>.</p>
<p>Email Service rejects the entire send request if it contains a disallowed header. It does not remove the header and continue sending the message.</p>

<h3 id="custom-x-headers">Custom X-headers</h3>
<p>Any header starting with <code>X-</code> is allowed. This covers common headers like <code>X-Mailer</code>, <code>X-Priority</code>, <code>X-Campaign-ID</code>, and any custom tracking headers your application needs.</p>
<ul>
<li><strong>Name format:</strong> <code>X-[A-Za-z0-9\-_]+</code>, maximum 100 characters</li>
<li><strong>Value:</strong> UTF-8, maximum 2,048 bytes</li>
<li><strong>No count limit</strong> on X-headers (subject to the 16 KB total payload limit)</li>
</ul>

<p>The total payload is calculated as <code>sum(len(name) + 2 + len(value) + 2)</code> for all custom headers (name + <code>: </code> + value + CRLF). Allowlisted and X-headers are counted together toward this limit.</p>
<h2 id="validation-rules">Validation rules</h2>
<ol>
<li><strong>Header names</strong> — ASCII only, no spaces, no colons, 1–100 characters. Allowlisted headers must match <code>[A-Za-z0-9\-]+</code>. X-headers must match <code>X-[A-Za-z0-9\-_]+</code> (underscores allowed only in X-headers).</li>
<li><strong>Header values</strong> — UTF-8 allowed, maximum 2,048 bytes, no bare CR/LF. Empty values are rejected.</li>
<li><strong>Case-insensitive matching</strong> — Header names are matched case-insensitively per <a href="https://datatracker.ietf.org/doc/html/rfc5322#section-2.2">RFC 5322 §2.2</a>. The canonical casing from the allowlist is used in the generated message.</li>
<li><strong>Proper line folding</strong> — Long headers are folded at 78 characters per RFC 5322 using CRLF+WSP, not MIME encoding.</li>
<li><strong>Single occurrence</strong> — The <code>headers</code> type is <code>{ [key]: string }</code>, so each header name can appear at most once. For headers that support multiple values (such as <code>Keywords</code> or <code>Comments</code>), use comma-separated values in a single string.</li>
</ol>
