<p>Use <code>wrangler flagship</code> to manage Flagship apps and feature flags from the command line. Every <code>wrangler flagship flags</code> command takes the app ID as the first argument. Most subcommands then take a flag key, for example <code>wrangler flagship flags get &lt;APP_ID&gt; &lt;KEY&gt;</code>. List-style commands, such as <code>wrangler flagship flags list &lt;APP_ID&gt;</code>, take only the app ID.</p>
<h2 id="before-you-begin">Before you begin</h2>
<h3 id="authenticate-wrangler">Authenticate Wrangler</h3>
<p><code>wrangler flagship</code> calls the Cloudflare API. Authenticate Wrangler before running commands:</p>
<pre tabindex="0"><code class="language-sh">wrangler login&#10;</code></pre>
<p>For automation, set <a href="/workers/wrangler/system-environment-variables/"><code>CLOUDFLARE_API_TOKEN</code></a> to an <a href="/fundamentals/api/get-started/create-token/">API token</a> with the appropriate Flagship permissions.</p>
<table>
<thead>
<tr>
<th>Permission</th>
<th>Use it for</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>flagship:read</code></td>
<td>Listing apps, getting apps, listing flags, inspecting flags, evaluating flags, and reading changelogs.</td>
</tr>
<tr>
<td><code>flagship:write</code></td>
<td>Creating apps, updating apps, deleting apps, creating flags, updating flags, changing defaults, rollouts, splits, enable/disable, and deleting flags.</td>

<p>Most commands that modify an existing flag first read the current flag and then write back the updated definition. For those workflows, grant both <code>flagship:read</code> and <code>flagship:write</code>.</p>

<h2 id="quick-start">Quick start</h2>
<p>Create a boolean flag, evaluate it for a user, and disable it as a kill switch:</p>
<pre tabindex="0"><code class="language-sh">&#35; With no variations, Wrangler creates on=true, off=false,&#10;&#35; and serves off by default.&#10;wrangler flagship flags create &lt;APP_ID&gt; new-checkout&#10;&#10;&#35; Evaluate the flag for a user.&#10;wrangler flagship flags evaluate &lt;APP_ID&gt; new-checkout --targeting-key user-42&#10;&#10;&#35; Disable the flag instantly. Disabled flags always serve their default variation.&#10;wrangler flagship flags disable &lt;APP_ID&gt; new-checkout&#10;</code></pre>
<h2 id="manage-apps">Manage apps</h2>
<p>Apps group related flags. A common pattern is one app per service, Worker, or product surface.</p>
<table>
<thead>
<tr>
<th>Task</th>
<th>Command</th>
</tr>
</thead>
<tbody>
<tr>
<td>Create app</td>
<td><code>wrangler flagship apps create &lt;NAME&gt;</code></td>
</tr>
<tr>
<td>List apps</td>
<td><code>wrangler flagship apps list</code></td>
</tr>
<tr>
<td>Get app</td>
<td><code>wrangler flagship apps get &lt;APP_ID&gt;</code></td>
</tr>
<tr>
<td>Rename app</td>
<td><code>wrangler flagship apps update &lt;APP_ID&gt; --name &lt;NAME&gt;</code></td>
</tr>
<tr>
<td>Delete app</td>
<td><code>wrangler flagship apps delete &lt;APP_ID&gt;</code></td>
</tr>
</tbody>
</table>
<p><code>wrangler flagship apps ls</code> is an alias for <code>apps list</code>. <code>wrangler flagship apps rm</code> is an alias for <code>apps delete</code>.</p>
<p><code>wrangler flagship apps list</code> follows pagination automatically and displays all apps in the account.</p>
<p>Creating an app returns the app ID and shows the binding snippet to add to your Wrangler configuration:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship apps create checkout-service&#10;</code></pre>
<p>To add the new app to your <code>wrangler.json</code> or <code>wrangler.jsonc</code> file as a Worker binding, pass <code>--binding</code>:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship apps create checkout-service --binding FLAGS&#10;</code></pre>
<p>Wrangler also supports <code>--update-config</code> to update your JSON or JSONC configuration after prompting for a binding name.</p>
<p>For non-JSON configuration files, Wrangler prints the binding snippet but does not edit the file automatically.</p>
<p>When <code>--json</code> is used, <code>apps create</code> prints the created app as JSON and does not prompt for or update configuration.</p>
<p>For scripts, capture the app ID from JSON output:</p>
<pre tabindex="0"><code class="language-sh">APP_ID=$(wrangler flagship apps create checkout-service --json | jq -r &#x27;.id&#x27;)&#10;</code></pre>
<p>Deleting an app deletes all of its flags and changelog history. The API rejects app deletion if a Worker still references the app through a Flagship binding.</p>
<p>Use <code>--force</code> or <code>-y</code> to skip the delete confirmation prompt. If you also use <code>--json</code>, you must pass <code>--force</code> so the confirmation prompt cannot appear in JSON output.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship apps delete &lt;APP_ID&gt; --force&#10;</code></pre>
<p>Delete multiple apps by passing multiple app IDs:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship apps delete &lt;APP_ID_1&gt; &lt;APP_ID_2&gt; &lt;APP_ID_3&gt; --force&#10;</code></pre>
<h2 id="create-flags">Create flags</h2>
<p>Flag keys are unique within an app. Use stable keys that describe the behavior being controlled, such as <code>new-checkout</code>, <code>pricing-page-layout</code>, or <code>upload-limit</code>.</p>
<h3 id="boolean-flags">Boolean flags</h3>
<p>If you omit variations, Wrangler creates a boolean flag with <code>on=true</code>, <code>off=false</code>, and <code>off</code> as the default variation.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; new-checkout&#10;</code></pre>
<h3 id="explicit-variations">Explicit variations</h3>
<p>Use <code>--variation</code> (<code>-V</code>) to add each variation as <code>name=value</code>. Use <code>--default</code> to choose the fallback variation.</p>
<pre tabindex="0"><code class="language-sh">&#35; String flag.&#10;wrangler flagship flags create &lt;APP_ID&gt; checkout-flow \&#10;	&#45;V v1=old-checkout \&#10;	&#45;V v2=new-checkout \&#10;	&#45;-default v1 \&#10;	&#45;-type string&#10;&#10;&#35; Number flag.&#10;wrangler flagship flags create &lt;APP_ID&gt; upload-limit \&#10;	&#45;V free=10 \&#10;	&#45;V pro=100 \&#10;	&#45;V enterprise=1000 \&#10;	&#45;-default free \&#10;	&#45;-type number&#10;&#10;&#35; JSON flag.&#10;wrangler flagship flags create &lt;APP_ID&gt; theme-config \&#10;	&#45;V &#x27;light={&quot;bg&quot;:&quot;#ffffff&quot;,&quot;fg&quot;:&quot;#111111&quot;}&#x27; \&#10;	&#45;V &#x27;dark={&quot;bg&quot;:&quot;#111111&quot;,&quot;fg&quot;:&quot;#ffffff&quot;}&#x27; \&#10;	&#45;-default light \&#10;	&#45;-type json&#10;</code></pre>
<p>Supported value types are <code>boolean</code>, <code>string</code>, <code>number</code>, and <code>json</code>. If <code>--type</code> is omitted, Wrangler infers each value's scalar type independently.</p>
<p>All variations on a flag must use the same value type. Wrangler rejects a flag whose variations resolve to mixed types, for example one boolean and one number, before sending the request. Pass <code>--type</code> explicitly to coerce every variation to the same type.</p>
<p>Use <code>--description</code> (<code>-d</code>) to document the purpose of a flag:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; checkout-flow \&#10;	&#45;V v1=old-checkout \&#10;	&#45;V v2=new-checkout \&#10;	&#45;-default v1 \&#10;	&#45;-type string \&#10;	&#45;-description &quot;Controls which checkout experience is served&quot;&#10;</code></pre>
<p>Flag keys and variation names can contain letters, numbers, hyphens, and underscores. Keep keys stable, because application code evaluates flags by key.</p>
<h3 id="disabled-flags">Disabled flags</h3>
<p>Use <code>--disabled</code> to create a flag that serves its default variation until you enable it.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; coming-soon \&#10;	&#45;V on=true \&#10;	&#45;V off=false \&#10;	&#45;-default off \&#10;	&#45;-disabled&#10;</code></pre>
<h2 id="target-users-with-rules">Target users with rules</h2>
<p>Targeting rules decide which variation to serve for a given evaluation context. Pass rules with <code>--rule</code> or <code>--rule-json</code>.</p>
<h3 id="rule-syntax">Rule syntax</h3>
<p>The compact <code>--rule</code> syntax uses semicolon-separated segments:</p>
<pre tabindex="0"><code class="language-txt">serve=&lt;VARIATION&gt;; when=&lt;CONDITIONS&gt;; rollout=&lt;PERCENT&gt;%@&lt;ATTRIBUTE&gt;; priority=&lt;NUMBER&gt;&#10;</code></pre>
<table>
<thead>
<tr>
<th>Segment</th>
<th>Required</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>serve</code></td>
<td>Yes</td>
<td>Variation served when the rule matches. Must reference an existing variation.</td>
</tr>
<tr>
<td><code>when</code></td>
<td>No</td>
<td>Conditions matched against evaluation context. If omitted, the rule matches every context.</td>
</tr>
<tr>
<td><code>rollout</code></td>
<td>No</td>
<td>Percentage of matching traffic to receive the variation. The attribute controls sticky bucketing.</td>
</tr>
<tr>
<td><code>priority</code></td>
<td>No</td>
<td>Evaluation order. Lower numbers run first. If omitted, Wrangler assigns priorities by order.</td>
</tr>
</tbody>
</table>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; premium-banner \&#10;	&#45;V on=true \&#10;	&#45;V off=false \&#10;	&#45;-default off \&#10;	&#45;-rule &quot;serve=on; when=plan equals enterprise AND country in [US,CA]; rollout=25%@user_id&quot;&#10;</code></pre>
<h3 id="conditions">Conditions</h3>
<p>Conditions compare attributes from the evaluation context with rule values. The compact syntax supports all <a href="/flagship/targeting/operators/">Flagship operators</a>:</p>
<pre tabindex="0"><code class="language-sh">&#45;-rule &quot;serve=on; when=plan equals pro&quot;&#10;&#45;-rule &quot;serve=on; when=country in [US,CA,UK]&quot;&#10;&#45;-rule &quot;serve=off; when=email ends_with @example.com&quot;&#10;&#45;-rule &quot;serve=strict; when=score less_than 20&quot;&#10;</code></pre>
<p>Use <code>AND</code> and <code>OR</code> to combine conditions. <code>AND</code> has higher precedence than <code>OR</code>.</p>
<pre tabindex="0"><code class="language-sh">&#35; Both conditions must match.&#10;&#45;-rule &quot;serve=on; when=plan equals pro AND country equals US&quot;&#10;&#10;&#35; Either condition can match.&#10;&#45;-rule &quot;serve=on; when=plan equals enterprise OR plan equals team&quot;&#10;&#10;&#35; Equivalent to: (plan=pro AND country=US) OR plan=enterprise.&#10;&#45;-rule &quot;serve=on; when=plan equals pro AND country equals US OR plan equals enterprise&quot;&#10;</code></pre>
<p><code>AND</code> and <code>OR</code> are reserved as logical operators when they appear outside quoted values or lists. Wrap values in single or double quotes when they contain reserved words or separators such as <code>AND</code>, <code>OR</code>, <code>;</code>, or <code>,</code>:</p>
<pre tabindex="0"><code class="language-sh">&#45;-rule &#x27;serve=on; when=title equals &quot;WAR AND PEACE&quot; OR title equals &quot;tom; jerry&quot;&#x27;&#10;&#45;-rule &#x27;serve=on; when=country in [&quot;US&quot;,&quot;CA&quot;]&#x27;&#10;</code></pre>
<p>For <code>in</code> and <code>not_in</code>, pass a bracketed list. Wrangler rejects malformed lists, empty list items, unterminated quotes, and unbalanced brackets before sending the request.</p>
<p>Use <code>--rule-json</code> for deeply nested logical groups or if you prefer to pass the API rule shape directly. Wrangler validates <code>--rule-json</code> against the Flagship rule schema and rejects unknown or conflicting fields.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; beta-features \&#10;	&#45;V on=true \&#10;	&#45;V off=false \&#10;	&#45;-default off \&#10;	&#45;-rule-json &#x27;{&quot;serve_variation&quot;:&quot;on&quot;,&quot;conditions&quot;:[{&quot;logical_operator&quot;:&quot;OR&quot;,&quot;clauses&quot;:[{&quot;attribute&quot;:&quot;beta&quot;,&quot;operator&quot;:&quot;equals&quot;,&quot;value&quot;:true},{&quot;attribute&quot;:&quot;plan&quot;,&quot;operator&quot;:&quot;equals&quot;,&quot;value&quot;:&quot;enterprise&quot;}]}]}&#x27;&#10;</code></pre>
<h3 id="multiple-rules">Multiple rules</h3>
<p>Repeat <code>--rule</code> or <code>--rule-json</code> to declare multiple rules. Rules are evaluated in priority order. The first matching rule wins.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags create &lt;APP_ID&gt; rate-limit-tier \&#10;	&#45;V strict=50 \&#10;	&#45;V normal=200 \&#10;	&#45;V relaxed=1000 \&#10;	&#45;-default normal \&#10;	&#45;-type number \&#10;	&#45;-rule &quot;serve=strict; when=score less_than 20&quot; \&#10;	&#45;-rule &quot;serve=relaxed; when=score greater_than_or_equals 90&quot;&#10;</code></pre>
<p>Wrangler validates duplicate rule priorities, duplicate variation names, malformed lists, non-finite numeric values such as <code>Infinity</code>, and unknown variation names before sending the request.</p>
<h2 id="inspect-flags">Inspect flags</h2>
<p>List flags in an app:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags list &lt;APP_ID&gt;&#10;</code></pre>
<p>The list command is paginated. Use <code>--limit</code> and <code>--cursor</code> for manual pagination, or <code>--all</code> to fetch every page.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags list &lt;APP_ID&gt; --limit 50&#10;wrangler flagship flags list &lt;APP_ID&gt; --cursor &lt;CURSOR&gt;&#10;wrangler flagship flags list &lt;APP_ID&gt; --all&#10;</code></pre>
<p>Inspect a full flag definition:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags get &lt;APP_ID&gt; new-checkout&#10;</code></pre>
<p><code>wrangler flagship flags ls</code> is an alias for <code>flags list</code>. <code>wrangler flagship flags inspect</code> is an alias for <code>flags get</code>.</p>
<h2 id="update-flags">Update flags</h2>
<p><code>wrangler flagship flags update</code> reads the current flag, applies your changes, and writes the full flag definition back to the API.</p>
<h3 id="update-metadata-and-variations">Update metadata and variations</h3>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; new-checkout \&#10;	&#45;-description &quot;Redesigned checkout experience&quot;&#10;&#10;wrangler flagship flags update &lt;APP_ID&gt; upload-limit \&#10;	&#45;-set-variation team=500&#10;&#10;wrangler flagship flags update &lt;APP_ID&gt; upload-limit \&#10;	&#45;-remove-variation team&#10;</code></pre>
<p>To add a variant to an existing flag, set a new variation name and value:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; checkout-flow \&#10;	&#45;-set-variation experiment=new-checkout-v2&#10;</code></pre>
<p>Pass an empty description to clear it:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; new-checkout --description &quot;&quot;&#10;</code></pre>
<p>When you add or replace variations on an existing flag, use <code>--type</code> if Wrangler should coerce the new values to a specific type:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; upload-limit \&#10;	&#45;-type number \&#10;	&#45;-set-variation team=500&#10;</code></pre>
<p>Wrangler validates that the resulting variation set still has a single value type and that the default variation and targeting rules still reference known variations.</p>
<p>You can also enable or disable a flag through <code>flags update</code>, although <code>flags enable</code> and <code>flags disable</code> are shorter for kill-switch workflows:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; new-checkout --disable&#10;wrangler flagship flags update &lt;APP_ID&gt; new-checkout --enable&#10;</code></pre>
<h3 id="change-the-default-variation">Change the default variation</h3>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags set &lt;APP_ID&gt; checkout-flow --variation v2&#10;</code></pre>
<p>Use <code>--clear-rules</code> if the new default should be served to everyone.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags set &lt;APP_ID&gt; checkout-flow --variation v2 --clear-rules&#10;</code></pre>
<h3 id="replace-append-or-clear-all-rules">Replace, append, or clear all rules</h3>
<p>Use <code>--rule</code> or <code>--rule-json</code> to replace the full rule set:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-rule &quot;serve=on; when=plan equals pro AND country not_in [CN,RU]&quot;&#10;</code></pre>
<p>Use <code>--add-rule</code> or <code>--add-rule-json</code> to append rules without changing existing rules:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-add-rule &quot;serve=off; when=account_age less_than 7&quot;&#10;&#10;wrangler flagship flags update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-add-rule-json &#x27;{&quot;serve_variation&quot;:&quot;off&quot;,&quot;conditions&quot;:[{&quot;attribute&quot;:&quot;country&quot;,&quot;operator&quot;:&quot;in&quot;,&quot;value&quot;:[&quot;CN&quot;,&quot;RU&quot;]}]}&#x27;&#10;</code></pre>
<p>Clear all rules:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags update &lt;APP_ID&gt; premium-banner --clear-rules&#10;</code></pre>

<h3 id="list-rules">List rules</h3>
<p>Use <code>rules list</code> to see the priorities you can target with rule-specific commands:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules list &lt;APP_ID&gt; premium-banner&#10;</code></pre>
<h3 id="reorder-rules">Reorder rules</h3>
<p>Flagship evaluates rules by ascending <code>priority</code>; the first matching rule wins. Use <code>rules reorder</code> to reorder existing rules without rewriting every condition.</p>
<p>Pass the existing priorities in the new order. Wrangler renumbers them to <code>1..n</code> in that order:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules reorder &lt;APP_ID&gt; rate-limit-tier --order 2,1&#10;</code></pre>
<p>If the existing priorities were <code>1=strict</code> and <code>2=relaxed</code>, this makes <code>relaxed</code> priority <code>1</code> and <code>strict</code> priority <code>2</code>.</p>
<h3 id="change-one-rule">Change one rule</h3>
<p>Use <code>rules update</code> to edit one rule by priority while preserving the rest of the rule set.</p>
<p>Change only a rollout percentage:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-priority 1 \&#10;	&#45;-rollout 50%@user_id&#10;</code></pre>
<p>Change the variation served by a rule:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-priority 1 \&#10;	&#45;-serve off&#10;</code></pre>
<p>Change the conditions on a rule:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-priority 1 \&#10;	&#45;-when &quot;plan equals enterprise OR plan equals team&quot;&#10;</code></pre>
<p>Remove conditions from a rule so it matches every evaluation context:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-priority 1 \&#10;	&#45;-clear-conditions&#10;</code></pre>

<p>Remove a rollout from a rule:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rules update &lt;APP_ID&gt; premium-banner \&#10;	&#45;-priority 1 \&#10;	&#45;-clear-rollout&#10;</code></pre>
<h3 id="delete-one-rule">Delete one rule</h3>
<p>Use <code>rules delete</code> to remove one rule by priority:</p>

<h3 id="enable-and-disable">Enable and disable</h3>
<p>Disabling a flag is an immediate kill switch. A disabled flag ignores targeting rules and serves its default variation.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags disable &lt;APP_ID&gt; new-checkout&#10;wrangler flagship flags enable &lt;APP_ID&gt; new-checkout&#10;</code></pre>

<pre tabindex="0"><code class="language-sh">wrangler flagship flags disable &lt;APP_ID&gt; new-checkout dark-mode premium-banner&#10;wrangler flagship flags enable &lt;APP_ID&gt; new-checkout dark-mode premium-banner&#10;</code></pre>
<h3 id="roll-out-one-variation">Roll out one variation</h3>
<p>Use <code>rollout</code> to serve one variation to a percentage of traffic.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags rollout &lt;APP_ID&gt; new-checkout \&#10;	&#45;-to on \&#10;	&#45;-percentage 25 \&#10;	&#45;-by user_id&#10;</code></pre>
<p>Use <code>--from-variation</code> (alias <code>--from</code>) to choose the fallback variation for the remaining traffic. A rollout percentage of <code>0</code> removes the rollout rule and keeps the flag's current default variation unchanged.</p>
<p><code>rollout</code> sends the percentage you provide directly to Flagship. For example, <code>--percentage 25 --to on</code> serves the <code>on</code> variation to 25% of bucketed traffic. The remaining traffic falls through to the flag's default variation.</p>
<h3 id="split-traffic-across-variations">Split traffic across variations</h3>
<p>Use <code>split</code> for A/B tests or multi-way traffic allocation. Wrangler converts weights into cumulative rollout thresholds.</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags split &lt;APP_ID&gt; checkout-flow \&#10;	&#45;-weight v1=80 \&#10;	&#45;-weight v2=20 \&#10;	&#45;-by user_id&#10;</code></pre>
<p><code>-w</code> is an alias for <code>--weight</code>. Each variation can only be weighted once, and weights must be finite, non-negative numbers.</p>
<p>Weights are relative. Wrangler totals the weights, converts each one into a percentage of the total, and sends cumulative thresholds to Flagship. For example, <code>--weight v1=80 --weight v2=20</code> sends two generated rules: one for <code>v1</code> with a rollout percentage of <code>80</code>, and one for <code>v2</code> with a rollout percentage of <code>100</code>. This creates bucket ranges of <code>0-80</code> for <code>v1</code> and <code>80-100</code> for <code>v2</code>.</p>
<p>With three weights, <code>--weight a=50 --weight b=30 --weight c=20</code> becomes cumulative thresholds of <code>50</code>, <code>80</code>, and <code>100</code>. Zero-weight variations are skipped.</p>
<p>Use <code>--default</code> with <code>split</code> to choose the fallback variation when bucketing cannot run:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship flags split &lt;APP_ID&gt; checkout-flow \&#10;	&#45;-weight v1=80 \&#10;	&#45;-weight v2=20 \&#10;	&#45;-default v1 \&#10;	&#45;-by user_id&#10;</code></pre>

<h2 id="automate-with-json-output">Automate with JSON output</h2>
<p>Every <code>wrangler flagship</code> command accepts <code>--json</code>. JSON output suppresses the Wrangler banner and is intended for scripts.</p>
<p>Delete commands require <code>--force</code> with <code>--json</code> to keep stdout valid JSON. <code>rollout</code> and <code>split</code> also require <code>--force</code> with <code>--json</code> if they would replace existing targeting rules that have conditions.</p>
<p>Bulk commands, such as <code>flags delete</code>, <code>flags enable</code>, and <code>flags disable</code>, continue processing remaining flags if one flag fails. In JSON mode, partial failures return a JSON error object containing successful <code>results</code> and per-flag <code>failures</code>.</p>
<p>Commands that can update <code>wrangler.json</code> or <code>wrangler.jsonc</code>, such as <code>apps create --binding</code>, do not prompt for or update configuration when <code>--json</code> is used.</p>
<p>Create an app, capture its ID, then create a flag:</p>
<pre tabindex="0"><code class="language-sh">APP_ID=$(wrangler flagship apps create checkout-service --json | jq -r &#x27;.id&#x27;)&#10;&#10;wrangler flagship flags create &quot;$APP_ID&quot; new-checkout --json&#10;</code></pre>
<p>Delete several apps in a loop:</p>
<pre tabindex="0"><code class="language-sh">for app_id in &lt;APP_ID_1&gt; &lt;APP_ID_2&gt; &lt;APP_ID_3&gt;; do&#10;	wrangler flagship apps delete &quot;$app_id&quot; --force&#10;done&#10;</code></pre>
<p>Or pass the app IDs directly:</p>
<pre tabindex="0"><code class="language-sh">wrangler flagship apps delete &lt;APP_ID_1&gt; &lt;APP_ID_2&gt; &lt;APP_ID_3&gt; --force&#10;</code></pre>
