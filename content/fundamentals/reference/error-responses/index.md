<p>When Cloudflare cannot complete a request, it generates an error response. The format depends on what the client requests via the <code>Accept</code> header and on the zone's <a href="/rules/custom-errors/">Custom Errors</a> configuration.</p>
<p>By default, error responses are HTML. Clients that request a structured format (such as <code>application/json</code>, <code>application/problem+json</code>, or <code>text/markdown</code>) receive a machine-readable response instead. This machine-readable response covers all <a href="/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/">1xxx error codes</a> (which return HTTP 4xx or 5xx status codes depending on the error) and Cloudflare-generated <a href="/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/">5xx errors</a> (500, 502, 504, 520-526). Responses for 5xx errors generated by the origin server are passed through by Cloudflare to the client and are not affected.</p>

<h2 id="content-negotiation">Content negotiation</h2>
<p>Cloudflare selects the response format based on the client's <code>Accept</code> header, following standard <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Content_negotiation">HTTP content negotiation</a>. When multiple formats are acceptable, quality factors (<code>q</code> values) determine precedence. At the same quality value, the first-listed type wins.</p>
<table>
<thead>
<tr>
<th><code>Accept</code> header sent</th>
<th>Response format</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>application/json</code></td>
<td>JSON (<code>application/json; charset=utf-8</code>)</td>
</tr>
<tr>
<td><code>application/problem+json</code></td>
<td>JSON (<code>application/problem+json; charset=utf-8</code>)</td>
</tr>
<tr>
<td><code>application/json, text/markdown;q=0.9</code></td>
<td>JSON (higher quality factor)</td>
</tr>
<tr>
<td><code>text/markdown</code></td>
<td>Markdown (<code>text/markdown; charset=utf-8</code>)</td>
</tr>
<tr>
<td><code>text/markdown, application/json</code></td>
<td>Markdown (equal quality, first-listed wins)</td>
</tr>
<tr>
<td><code>text/*</code></td>
<td>Markdown</td>
</tr>
<tr>
<td><code>text/html</code></td>
<td>HTML</td>
</tr>
<tr>
<td><code>*/*</code></td>
<td>HTML</td>
</tr>
<tr>
<td>Not set</td>
<td>HTML</td>
</tr>
</tbody>
</table>
<p>Structured error responses are available on all plans, including the Free plan. <a href="/rules/custom-errors/#custom-error-rules">Custom Error Rules</a> for overriding these responses require a Cloudflare paid plan.</p>

<h2 id="interaction-with-custom-errors">Interaction with Custom Errors</h2>
<p>Structured error responses are the default for zones with no custom error configuration. Zones that use <a href="/rules/custom-errors/">Custom Errors</a> retain full control over what clients receive.</p>
<p>What a client receives depends on which custom error features your zone has configured. Refer to the following sections for details.</p>
<h3 id="no-custom-error-page-no-custom-error-rules">No custom error page, no custom error rules</h3>
<p>This is the default for most zones. Cloudflare serves its default error response in the format the client requests.</p>
<table>
<thead>
<tr>
<th>Client sends</th>
<th>Response</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>Accept: application/json</code></td>
<td>Default Cloudflare structured JSON response</td>
</tr>
<tr>
<td><code>Accept: text/markdown</code></td>
<td>Default Cloudflare structured Markdown response</td>
</tr>
<tr>
<td><code>Accept: text/html</code></td>
<td>Default Cloudflare HTML error page</td>
</tr>
<tr>
<td>No <code>Accept</code> header</td>
<td>Default Cloudflare HTML error page</td>
</tr>
</tbody>
</table>
<h3 id="error-page-configured-no-custom-error-rules">Error Page configured, no custom error rules</h3>
<p>The zone has an Error Page uploaded via the Cloudflare dashboard. No Custom Error Rules are configured. The Error Page is served to all clients regardless of <code>Accept</code> header — Error Pages do not perform content negotiation.</p>
<table>
<thead>
<tr>
<th>Client sends</th>
<th>Response</th>
</tr>
</thead>
<tbody>
<tr>

</tr>
<tr>
<td><code>Accept: text/markdown</code></td>
<td>Your custom HTML error page</td>
</tr>
<tr>
<td><code>Accept: text/html</code></td>
<td>Your custom HTML error page</td>
</tr>
<tr>
<td>No <code>Accept</code> header</td>
<td>Your custom HTML error page</td>
</tr>
</tbody>
</table>
<p>If you want agents to receive structured responses while keeping your custom HTML for browsers, add a Custom Error Rule that matches on the <code>Accept</code> header. Refer to the next section for details.</p>
<h3 id="custom-error-rules-configured">Custom Error Rules configured</h3>
<p>The zone has one or more <a href="/rules/custom-errors/#custom-error-rules">Custom Error Rules</a> (available on paid plans). These take priority over Error Pages. You control what gets served, to whom, and under what conditions.</p>
<table>
<thead>
<tr>
<th>Client sends</th>
<th>Response</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>Accept: application/json</code></td>
<td>If a Custom Error Rule matches, the rule's content is served. If no rule matches, falls back to the Error Page (if configured) or the structured JSON response.</td>
</tr>
<tr>
<td><code>Accept: text/markdown</code></td>
<td>If a Custom Error Rule matches, the rule's content is served. If no rule matches, falls back to the Error Page (if configured) or the structured Markdown response.</td>
</tr>
<tr>
<td><code>Accept: text/html</code></td>
<td>If a Custom Error Rule matches, the rule's content is served. If no rule matches, falls back to the Error Page or the default HTML.</td>
</tr>
<tr>
<td>No <code>Accept</code> header</td>
<td>Same fallback chain</td>
</tr>
</tbody>
</table>
<p>Custom Error Rules can match on any request header including <code>Accept</code>, and can target specific error codes. You can serve JSON to API clients, Markdown to agents, and HTML to browsers, all from the same zone.</p>

<h3 id="priority-order">Priority order</h3>
<p>When Cloudflare generates an error response, the following priority order determines what the client receives:</p>
<ol>
<li><strong><a href="/rules/custom-errors/#custom-error-rules">Custom Error Rules</a></strong> — If a rule matches the error and request conditions, the rule's content is served.</li>
<li><strong><a href="/rules/custom-errors/#error-pages">Error Pages</a></strong> — If an Error Page is configured for the error type and no Custom Error Rule matched, the Error Page is served as HTML regardless of the <code>Accept</code> header.</li>
<li><strong>Structured error responses</strong> — If no Custom Error Rule matched and no Error Page is configured, Cloudflare serves its default response in the format the client requested (JSON, Markdown, or HTML).</li>
</ol>
<p>For the full priority order including account-level versus zone-level rules, WAF custom block responses, and security challenge pages, refer to the <a href="/rules/custom-errors/">Custom Errors</a> documentation.</p>

<h2 id="response-fields">Response fields</h2>
<p>Both JSON and Markdown responses contain the same set of fields. JSON responses return them as a flat object; Markdown responses place them in YAML frontmatter followed by prose sections. The field definitions below apply to both formats.</p>
<p>JSON responses follow <a href="https://www.rfc-editor.org/rfc/rfc9457">RFC 9457 (Problem Details for HTTP APIs)</a>. Any HTTP client that understands Problem Details can parse the five standard members (<code>type</code>, <code>title</code>, <code>status</code>, <code>detail</code>, <code>instance</code>) without Cloudflare-specific code.</p>

<h3 id="markdown-specific-structure">Markdown-specific structure</h3>
<p>Markdown responses place these fields in YAML frontmatter (between <code>---</code> delimiters), followed by three prose sections:</p>
<ul>
<li><strong><code># Error {code}: {description}</code></strong> — heading with the error code and short description.</li>
<li><strong><code>## What Happened</code></strong> — corresponds to the <code>detail</code> field.</li>
<li><strong><code>## What You Should Do</code></strong> — corresponds to the <code>what_you_should_do</code> field.</li>
</ul>
<p>The frontmatter omits the RFC 9457 standard members (<code>type</code>, <code>title</code>, <code>instance</code>) and the <code>footer</code> field since these are either redundant with the prose or not applicable to the Markdown format.</p>
