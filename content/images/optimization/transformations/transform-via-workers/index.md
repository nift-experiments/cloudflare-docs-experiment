<p>Workers lets you optimize images with a custom URL scheme.</p>
<p>You can set image optimization parameters on a <code>fetch()</code> subrequest in a Worker using the <code>cf.image</code> property. This is the same underlying mechanism as the <a href="/images/optimization/transformations/overview/#url-interface">URL interface</a>, but gives you programmatic control over every image request.</p>
<p>To work with image bytes directly instead of URLs, use the <a href="/images/optimization/binding/">Images binding</a>.</p>
<p>Here are a few examples of the flexibility that Workers give you:</p>
<ul>
<li><strong>Use a custom URL scheme</strong>. Instead of specifying pixel dimensions in image URLs, use preset names such as <code>thumbnail</code> and <code>large</code>.</li>
<li><strong>Hide the actual location of the original image</strong>. You can store images in an external S3 bucket or a hidden folder on your server without exposing that information in URLs.</li>
<li><strong>Implement content negotiation</strong>. This is useful to adapt image sizes, formats and quality dynamically based on the device and condition of the network.</li>
</ul>
<h2 id="how-it-works">How it works</h2>
<p>The resizing feature is accessed via the <a href="/workers/runtime-apis/request/#the-cf-property-requestinitcfproperties">options</a> of a <code>fetch()</code> <a href="/workers/runtime-apis/fetch/">subrequest inside a Worker</a>. The <code>fetch()</code> function accepts parameters in the second argument inside the <code>{cf: {image: {…}}}</code> object.</p>
<p>In your worker, where you would fetch the image using <code>fetch(request)</code>, add options like in the following example:</p>
<pre tabindex="0"><code class="language-js">fetch(imageURL, {&#10;	cf: {&#10;		image: {&#10;			fit: &quot;scale-down&quot;,&#10;			width: 800,&#10;			height: 600,&#10;		},&#10;	},&#10;});&#10;</code></pre>
<p>These typings are also available in <a href="https://github.com/cloudflare/workers-types">our Workers TypeScript definitions library</a>.</p>
<p><code>cf.image</code> is available on any zone that hosts a Worker, including <code>*.workers.dev</code> subdomains. Each transformation is billed to the account that owns the Worker.</p>
<h2 id="configure-a-worker">Configure a Worker</h2>
<p>Create a new script in the Workers section of the Cloudflare dashboard. Scope your Worker script to a path dedicated to serving assets, such as <code>/images/*</code> or <code>/assets/*</code>. Only supported image formats can be resized. Attempting to resize any other type of resource (CSS, HTML) will result in an error.</p>
<aside class="nb-aside caution">
<h3 class="nb-aside-title" id="warning">Warning</h3>
@markup("md", "content/.markup/bodies/9457.md")
</aside>
<p>It is best to keep the path handled by the Worker separate from the path to original (unresized) images, to avoid request loops caused by the image resizing worker calling itself. For example, store your images in <code>example.com/originals/</code> directory, and handle resizing via <code>example.com/thumbnails/*</code> path that fetches images from the <code>/originals/</code> directory. If source images are stored in a location that is handled by a Worker, you must prevent the Worker from creating an infinite loop.</p>
<h3 id="prevent-request-loops">Prevent request loops</h3>
<p>To perform resizing and optimizations, the Worker must be able to fetch the original, unresized image from your origin server. If the path handled by your Worker overlaps with the path where images are stored on your server, it could cause an infinite loop by the Worker trying to request images from itself.</p>
<p>You must detect which requests must go directly to the origin server. When the <code>image-resizing</code> string is present in the <code>Via</code> header, it means that it is a request coming from another Worker and should be directed to the origin server:</p>
<pre tabindex="0"><code class="language-js">export default {&#10;	async fetch(request) {&#10;		// If this request is coming from image resizing worker,&#10;		// avoid causing an infinite loop by resizing it again:&#10;		if (/image-resizing/.test(request.headers.get(&quot;via&quot;))) {&#10;			return fetch(request);&#10;		}&#10;&#10;		// Now you can safely use image resizing here&#10;	},&#10;};&#10;</code></pre>

<p>The script preview of the Worker editor ignores <code>fetch()</code> options, and will always fetch unresized images. To see the effect of image transformations you must deploy the Worker script and use it outside of the editor.</p>
<h2 id="local-development">Local development</h2>
<p>When running <code>wrangler dev</code>, <code>cf.image</code> transformations are applied locally using a low fidelity mock.</p>
<p>A subset of options are supported, including resize, rotate, format, and background colour. Unsupported options are ignored.</p>
<h2 id="error-handling">Error handling</h2>
<p>When an image cannot be resized — for example, because the image does not exist or the resizing parameters were invalid — the response will have an HTTP status indicating an error (for example, <code>400</code>, <code>404</code>, or <code>502</code>).</p>
<p>By default, the error will be forwarded to the browser, but you can decide how to handle errors. For example, you can redirect the browser to the original, unresized image instead:</p>
<pre tabindex="0"><code class="language-js">const response = await fetch(imageURL, options);&#10;&#10;if (response.ok || response.redirected) {&#10;	// fetch() may respond with status 304&#10;	return response;&#10;} else {&#10;	return Response.redirect(imageURL, 307);&#10;}&#10;</code></pre>
<p>Keep in mind that if the original images on your server are very large, it may be better not to display failing images at all, than to fall back to overly large images that could use too much bandwidth, memory, or break page layout.</p>
<p>You can also replace failed images with a placeholder image:</p>
<pre tabindex="0"><code class="language-js">const response = await fetch(imageURL, options);&#10;if (response.ok || response.redirected) {&#10;	return response;&#10;} else {&#10;	// Change to a URL on your server&#10;	return fetch(&quot;https://img.example.com/blank-placeholder.png&quot;);&#10;}&#10;</code></pre>
<h2 id="an-example-worker">An example worker</h2>
<p>Assuming you <a href="/workers/get-started/guide/">set up a Worker</a> on <code>https://example.com/image-resizing</code> to handle URLs like <code>https://example.com/image-resizing?width=80&amp;image=https://example.com/uploads/avatar1.jpg</code>:</p>
<pre tabindex="0"><code class="language-js">/**&#10; &#42; Fetch and log a request&#10; &#42; @param {Request} request&#10; &#42;/&#10;export default {&#10;	async fetch(request) {&#10;		// Parse request URL to get access to query string&#10;		let url = new URL(request.url);&#10;&#10;		// Cloudflare-specific options are in the cf object.&#10;		let options = { cf: { image: {} } };&#10;&#10;		// Copy parameters from query string to request options.&#10;		// You can implement various different parameters here.&#10;		if (url.searchParams.has(&quot;fit&quot;))&#10;			options.cf.image.fit = url.searchParams.get(&quot;fit&quot;);&#10;		if (url.searchParams.has(&quot;width&quot;))&#10;			options.cf.image.width = parseInt(url.searchParams.get(&quot;width&quot;), 10);&#10;		if (url.searchParams.has(&quot;height&quot;))&#10;			options.cf.image.height = parseInt(url.searchParams.get(&quot;height&quot;), 10);&#10;		if (url.searchParams.has(&quot;quality&quot;))&#10;			options.cf.image.quality = parseInt(url.searchParams.get(&quot;quality&quot;), 10);&#10;&#10;		// Your Worker is responsible for automatic format negotiation. Check the Accept header.&#10;		const accept = request.headers.get(&quot;Accept&quot;);&#10;		if (/image\/avif/.test(accept)) {&#10;			options.cf.image.format = &quot;avif&quot;;&#10;		} else if (/image\/webp/.test(accept)) {&#10;			options.cf.image.format = &quot;webp&quot;;&#10;		}&#10;&#10;		// Get URL of the original (full size) image to resize.&#10;		// You could adjust the URL here, e.g., prefix it with a fixed address of your server,&#10;		// so that user-visible URLs are shorter and cleaner.&#10;		const imageURL = url.searchParams.get(&quot;image&quot;);&#10;		if (!imageURL)&#10;			return new Response(&#x27;Missing &quot;image&quot; value&#x27;, { status: 400 });&#10;&#10;		try {&#10;			// TODO: Customize validation logic&#10;			const { hostname, pathname } = new URL(imageURL);&#10;&#10;			// Optionally, only allow URLs with JPEG, PNG, GIF, or WebP file extensions&#10;			// @see https://developers.cloudflare.com/images/url-format#supported-formats-and-limitations&#10;			if (!/\.(jpe?g|png|gif|webp)$/i.test(pathname)) {&#10;				return new Response(&quot;Disallowed file extension&quot;, { status: 400 });&#10;			}&#10;&#10;			// Demo: Only accept &quot;example.com&quot; images&#10;			if (hostname !== &quot;example.com&quot;) {&#10;				return new Response(&#x27;Must use &quot;example.com&quot; source images&#x27;, {&#10;					status: 403,&#10;				});&#10;			}&#10;		} catch (err) {&#10;			return new Response(&#x27;Invalid &quot;image&quot; value&#x27;, { status: 400 });&#10;		}&#10;&#10;		// Build a request that passes through request headers&#10;		const imageRequest = new Request(imageURL, {&#10;			headers: request.headers,&#10;		});&#10;&#10;		// Returning fetch() with resizing options will pass through response with the resized image.&#10;		return fetch(imageRequest, options);&#10;	},&#10;};&#10;</code></pre>
<p>When testing image resizing, please deploy the script first. Resizing will not be active in the online editor in the dashboard.</p>
<h2 id="warning-about-cachekey">Warning about <code>cacheKey</code></h2>
<p>Resized images are always cached. They are cached as additional variants under a cache entry for the URL of the full-size source image in the <code>fetch</code> subrequest. Do not worry about using many different Workers or many external URLs — they do not influence caching of resized images, and you do not need to do anything for resized images to be cached correctly.</p>
<p>If you use the <code>cacheKey</code> fetch option to unify the caches of multiple source URLs, do not include any resizing options in the <code>cacheKey</code>. Doing so will fragment the cache and hurt caching performance. The <code>cacheKey</code> should reference only the full-size source image URL, not any of its resized versions.</p>
