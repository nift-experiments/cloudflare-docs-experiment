<h2 id="create-reusable-policy-components">Create reusable policy components</h2>
<p>If you have many policies that contain duplicate rules, we recommend <a href="/cloudflare-one/access-controls/policies/groups/">building a rule group</a> and referencing it across multiple policies. For example, you could define a rule group for &quot;corporate users&quot;, which has both device posture check requirements and specific emails, or just “developers”, which references a group in your identity provider.</p>
<h2 id="define-your-domain-structure">Define your domain structure</h2>
<p>Access applications have an inherently flexible and powerful domain structure capability. Your domain structure should achieve your application security goals without being overly permissive or overly restrictive. Before designing applications for production, review the <a href="/cloudflare-one/access-controls/policies/app-paths/">Application paths documentation</a> to understand how path definitions work and how to use wildcards.</p>
<h3 id="multiple-domains-in-an-application">Multiple domains in an application</h3>
<p>Many customers who have workflows designed around internal web applications, especially those that were built internally, often see challenges related to interdependencies on multiple internal services. Separately, there can be challenges related to SPAs (Single-Page Applications) that make deploying clientless access difficult. For example, an application may have iFrames or other embedded systems that rely on different internal and/or external addresses.</p>
<p>If your internal service operates in this way, we recommend specifying multiple top-level domains in a single Access application. Otherwise, if the goal of using multiple domains is to streamline or simplify policy creation, we recommend making one primary domain per application, and automating the rest of your deployment <a href="/learning-paths/clientless-access/terraform/">using Terraform</a> or another Infrastructure as Code (IaC) service.</p>
