<p>By following this guide, you will create a Worker through which your applications can perform multipart uploads.
This example worker could serve as a basis for your own use case where you can add authentication to the worker, or even add extra validation logic when uploading each part.
This guide also contains an example Python application that uploads files to this worker.</p>

<h2 id="perform-a-multipart-upload-with-your-worker-optional">Perform a multipart upload with your Worker (optional)</h2>
<p>This example application uploads a local file to the Worker in multiple parts. It uses Python's built-in <code>ThreadPoolExecutor</code> to parallelize the uploading of parts to the Worker, which increases upload speeds. HTTP requests to the Worker are made with the <a href="https://pypi.org/project/requests/">requests</a> library.</p>
<p>Utilizing the multipart API in this way also allows you to use your Worker to upload files larger than the <a href="/workers/platform/limits#request-limits">Workers request body size limit</a>. The uploading of individual parts is still subject to this limit.</p>
<p>Save the following code in a file named <code>mpuscript.py</code> on your local machine. Change the <code>worker_endpoint variable</code> to where your worker is deployed. Pass the file you want to upload as an argument when running this script: <code>python3 mpuscript.py myfile</code>. This will upload the file <code>myfile</code> from your machine to your bucket through the Worker.</p>

<h2 id="state-management">State management</h2>
<p>The stateful nature of multipart uploads does not easily map to the usage model of Workers, which are inherently stateless. In a normal multipart upload, the multipart upload is usually performed in one continuous execution of the client application. This is different from multipart uploads in a Worker, which will often be completed over multiple invocations of that Worker. This makes state management more challenging.</p>
<p>To overcome this, the state associated with a multipart upload, namely the <code>uploadId</code> and which parts have been uploaded, needs to be kept track of somewhere outside of the Worker.</p>
<p>In the example Worker and Python application described in this guide, the state of the multipart upload is tracked in the client application which sends requests to the Worker, with the necessary state contained in each request. Keeping track of the multipart state in the client application enables maximal flexibility and allows for parallel and unordered uploads of each part.</p>
<p>When keeping track of this state in the client is impossible, alternative designs can be considered. For example, you could track the <code>uploadId</code> and which parts have been uploaded in a Durable Object or other database.</p>
