<p>In this section, we describe how to use this collective key pair to generate publicly-verifiable, unbiasable, and unpredictable randomness in a distributed manner.</p>
<p>First, we explain pairing-based cryptography (PBC), which has become quite popular, and is used in many modern consensus protocols or zero-knowledge proofs, such as zk-SNARKs. We will then show how drand uses PBC for the randomness beacon generation phase for threshold Boneh-Lynn-Shacham (BLS) signatures. Finally, we will discuss how drand links the generated threshold BLS signatures into a randomness chain.</p>
<h2 id="pairing-based-cryptography">Pairing-based Cryptography</h2>
<p>Pairing-based cryptography is based on bilinear groups <code>(𝔾1,𝔾2,𝔾𝑡)</code>, where <code>𝔾1</code>, <code>𝔾2</code>, and <code>𝔾𝑡</code> are cyclic groups of prime order <code>𝑝</code> with generators <code>𝑔1</code>, <code>𝑔2</code>, and <code>𝑔𝑡</code>, respectively, and a pairing operation <code>𝑒:𝔾1×𝔾2→𝔾𝑡</code> with these properties:</p>
<ul>
<li>
<p><strong>Bilinearity:</strong> <code>∀𝑎,𝑏∈ℤ∗𝑝,∀𝑃∈𝔾1,∀𝑄∈𝔾2,</code> we have <code>𝑒(𝑎𝑃,𝑏𝑄)=𝑒(𝑃,𝑄)𝑎𝑏</code></p>
</li>
<li>
<p><strong>Non-degeneracy:</strong> <code>𝑒≠1</code></p>
</li>
<li>
<p><strong>Computability:</strong> There exists an efficient algorithm to compute <code>𝑒</code>.
drand currently uses the Barreto-Lynn-Scott curve BLS12-381.</p>
</li>
</ul>
<h2 id="bls-signatures">BLS Signatures</h2>
<p>To generate publicly-verifiable, unbiasable, distributed randomness, drand utilizes threshold Boneh-Lynn-Shacham (BLS) signatures. First we will describe regular BLS signatures and then the threshold variant.</p>
<p>BLS signatures are short signatures that rely on bilinear pairings and consist only of a single element in <code>𝔾1</code>. They are deterministic in the sense they depend only on the message and the signer’s key, unlike other signature schemes, such as ECDSA, that require a fresh random value for each signed message to be secure. Put differently, any two BLS signatures on a given message produced with the same key are identical. In drand, we utilize this property to achieve unbiasability for randomness generation.</p>
<p>The BLS signature scheme consists of the these sub-procedures.</p>
<h3 id="key-generation">Key Generation</h3>
<p>To generate a key pair, a signer first chooses a private key, <code>𝑥∈ℤ∗𝑝</code>, at random, and then computes the corresponding public key as <code>𝑋=𝑔𝑥2∈𝔾2</code>.</p>
<h3 id="signature-generation">Signature Generation</h3>
<p>Let <code>𝐻:{0,1}∗→𝔾1</code> denote a cryptographic hash function that maps arbitrary bit strings to elements of <code>𝔾1</code>. To compute a BLS signature <code>𝜎</code> on a message <code>𝑚</code>, the signer computes <code>𝜎=𝑥𝐻(𝑚)∈𝔾1</code>.</p>
<h3 id="signature-verification">Signature Verification</h3>
<p>To verify that a BLS signature <code>𝜎</code> on a message <code>𝑚</code> is valid, the verifier checks if <code>𝑒(𝐻(𝑚),𝑋)=𝑒(𝜎,𝑔2)</code> holds using the signer’s public key <code>𝑋</code>.</p>
<p>Note that this equation holds for valid signatures since <code>𝑒(𝐻(𝑚),𝑋)=𝑒(𝐻(𝑚),𝑔𝑥2)=𝑒(𝐻(𝑚),𝑔2)𝑥=𝑒(𝑥𝐻(𝑚),𝑔2)=𝑒(𝜎,𝑔2)</code>.</p>
<h2 id="threshold-bls-signature">Threshold BLS Signature</h2>
<p>The goal of a threshold signature scheme is to collectively compute a signature by combining individual partial signatures independently generated by the participants. A threshold BLS signature scheme has the following sub-procedures.</p>
<h3 id="key-generation-1">Key Generation</h3>
<p>The <code>𝑛</code> participants run a <code>𝑡-of-𝑛</code> DKG to setup a collective public key, <code>𝑆∈𝔾2</code>, and private key shares <code>𝑠𝑖∈ℤ∗𝑝</code> of the unknown collective private key, <code>𝑠</code>, as described above.</p>
<h3 id="partial-signature-generation">Partial Signature Generation</h3>
<p>To sign a message, <code>𝑚</code>, each <code>𝑖</code> uses their private key share, <code>𝑠𝑖</code>, to create a partial BLS signature, <code>𝜎𝑖=𝑠𝑖𝐻(𝑚)</code>.</p>
<h3 id="partial-signature-verification">Partial Signature Verification</h3>
<p>To verify the correctness of a partial signature, <code>𝜎𝑖</code>, on <code>𝑚</code>, a verifier uses the public key share, <code>𝑆𝑖</code>, generated during the DKG, and verifies that <code>𝑒(𝐻(𝑚),𝑆𝑖)=𝑒(𝜎𝑖,𝑔2)</code> holds.</p>
<h3 id="signature-reconstruction">Signature Reconstruction</h3>
<p>To reconstruct the collective BLS signature, <code>𝜎</code> on <code>𝑚</code>, a verifier first gathers <code>𝑡</code> different and valid partial BLS signatures, <code>𝜎𝑖</code>, on <code>𝑚</code> followed by a Lagrange interpolation.</p>
<h3 id="signature-verification-1">Signature Verification</h3>
<p>To verify a collective BLS signature, <code>𝜎</code>, a verifier checks that <code>𝑒(𝐻(𝑚),𝑆)=𝑒(𝜎,𝑔2)</code> holds, where <code>𝑆</code> is the collective public key.</p>
<p>Thanks to the properties of Lagrange interpolation, the value of <code>𝜎</code> is independent of the subset of <code>𝑡</code> valid partial signatures, <code>𝜎𝑖</code>, chosen during signature reconstruction. Additionally, Lagrange interpolation also guarantees that no set of less than <code>𝑡</code> signers can predict or bias <code>𝜎</code>.</p>
<p>In summary, a threshold BLS signature, <code>𝜎</code>, exhibits all properties required for publicly-verifiable, unbiasable, unpredictable, and distributed randomness.</p>
<h3 id="1-2-swap"><code>𝔾1/𝔾2</code> swap</h3>
<p>In the above, <code>𝔾1</code> and <code>𝔾2</code> could be swapped. The implication is on the relative size of public key and signatures. The first drand chains are constructed as described above, with signatures on <code>𝔾2</code> and public keys on <code>𝔾1</code>. Signature size is 96 bytes, and public key size is 48 bytes.</p>
<p>Certain applications prefer smaller signatures at the cost of a larger public key. This is why certain drand beacons have signatures on <code>𝔾1</code> and public key on <code>𝔾2</code>. Such a change is referred to as <code>𝔾1/𝔾2 swap</code>.</p>
<h2 id="chained-randomness">Chained Randomness</h2>
<p>The drand randomness beacon operates in discrete rounds, <code>𝑟</code>. In every round, drand beacons configured to use chained randomness produce a new random value using threshold BLS signatures linked together into a chain of randomness. To extend this chain of randomness, each drand participant, <code>𝑖</code>, creates in round <code>𝑟</code> the partial BLS signature, <code>𝜎𝑟𝑖</code> on the message <code>𝑚=𝐻(𝑟∥𝜎𝑟−1)</code> where, <code>𝜎𝑟−1</code> denotes the (full) BLS threshold signature from round <code>𝑟−1</code> and <code>𝐻</code>, a cryptographic hash function.</p>
<p>Once at least <code>𝑡</code> participants have broadcasted their partial signatures, <code>𝜎𝑟𝑖</code>, on <code>𝑚</code>, anyone can recover the full BLS threshold signature, <code>𝜎𝑟</code> that corresponds to the random value of round <code>𝑟</code>. After this, drand nodes move to round <code>𝑟+1</code> and reiterate the process.</p>
<p>For round <code>𝑟=0</code>, drand participants sign a seed fixed during drand setup. This process ensures that every new random value depends on all previously generated signatures. Since the signature is deterministic, there is also no possibility for an adversary forking the chain and presenting two distinct signatures <code>𝜎𝑟</code> and <code>𝜎′𝑟</code> in a given round <code>𝑟</code> to generate inconsistencies in the systems relying on public randomness.</p>
<h2 id="unchained-randomness">Unchained Randomness</h2>
<p>drand beacons can also be configured to use unchained randomness. To extend this chain of randomness, each drand participant, <code>𝑖</code>, creates in round <code>𝑟</code> the partial BLS signature, <code>𝜎𝑟𝑖</code> on the message <code>𝑚=𝐻(𝑟)</code> where <code>𝐻</code> a cryptographic hash function.</p>
<p>This process allows for a direct precomputation of message <code>𝑚</code> for round <code>𝑟=i</code>.</p>
