<h2 id="introduction">Introduction</h2>
<p><a href="https://www.cloudflare.com/learning/ai/ai-vibe-coding/">Vibe coding</a> is a software development practice that uses large language models (LLMs) to generate applications from natural language descriptions. An enterprise AI vibe coding platform is an internal tool where employees describe what they want to build in natural language, and the platform generates working code, shows a live preview, and publishes it, all within an environment the organization controls.</p>
<p>This allows all employees to build internal tools, dashboards, and business applications regardless of previous software development experiences. Without governance, each AI-built application risks uncontrolled data exposure, unapproved LLM provider usage, and code with an unknown security posture.</p>
<p>This reference architecture extends the <a href="/reference-architecture/diagrams/ai/ai-vibe-coding-platform/">AI Vibe Coding Platform</a> with enterprise controls for identity, data protection, cost attribution, discoverability, and audit logging. The base architecture builds on Cloudflare's Developer Platform: <a href="/ai-gateway/">AI Gateway</a> for LLM governance and guardrails, a <a href="/sandbox/">Sandbox</a> for code execution, and <a href="/cloudflare-for-platforms/workers-for-platforms/">Workers for Platforms</a> for deployment and hosting. This document focuses on the enterprise layer built on top of those primitives.</p>
<h2 id="security-model">Security model</h2>
<p>Enterprise vibe coding platforms must assume that AI-generated code is untrusted. The security model enforces protection at the platform level, not the code level.</p>
<ul>
<li><strong>Untrusted code execution:</strong> AI-generated code may contain bugs, vulnerabilities, or unintended behavior. Sandboxes and containers isolate it from production systems.</li>
<li><strong>Data exfiltration via prompts:</strong> Employees may inadvertently include sensitive data in prompts. AI Gateway and DLP inspect and block before prompts reach LLM providers.</li>
<li><strong>Prompt injection:</strong> Malicious prompts may attempt to manipulate the AI into generating harmful code. All interactions are logged and auditable.</li>
<li><strong>Credential exposure:</strong> AI-generated code never handles real secrets. Outbound handlers or outbound workers inject credentials at the platform layer.</li>
<li><strong>Privilege escalation:</strong> Misconfigured connection strings or network access could provision unauthorized access to higher-level resources. The binding model enforces allowlist-based connectivity.</li>
<li><strong>Unauthorized access:</strong> Without identity controls, deployed applications could be accessed by anyone in the organization. Cloudflare Access enforces role-based policies on both the platform and deployed applications.</li>
</ul>
<h2 id="core-architecture">Core architecture</h2>
<p>An enterprise vibe coding platform consists of three systems where existing enterprise controls can be layered or extended as required:</p>
<ul>
<li><strong>Development plane:</strong> Where employees create and iterate on applications through AI, with controlled access to LLMs and enterprise data.</li>
<li><strong>Deployment pipeline:</strong> The approval and validation workflow that promotes an application from development to production, including security checks, dependency scans, and human-in-the-loop review where required.</li>
<li><strong>Production plane:</strong> Where approved applications run in isolated, multi-tenant environments with full observability, egress controls, and access policies.</li>
</ul>
<p>Observability, discoverability, and cost controls should be embedded across all three components. <a href="/resource-tagging/">Resource tagging</a> applied across the lifecycle provides visibility, allowing platform administrators to track and manage all applications, users, and resources in one place.</p>

<h2 id="development-plane">Development plane</h2>
<p><img src="/assets/upstream/images/reference-architecture/enterprise-ai-vibe-coding/dev-plane.png" alt="Development plane architecture" /></p>
<p><a href="/cloudflare-one/access-controls/">Cloudflare Access</a> protects the entrypoint to the platform, whether that is a web-based user interface or authenticated access to a coding harness through the CLI. Access integrates with existing identity providers (Okta, Azure AD, Google Workspace) via SAML and OIDC, allowing organizations to use their existing SSO.</p>
<p>The platform stores metadata such as user profiles, sessions, cost tags, department and team permissions in a data store such as <a href="/d1/">D1</a> for structured queries, <a href="/kv/">KV</a> for fast key-value lookups, or <a href="/r2/">R2</a> for object storage. The frontend or agent flow queries this metadata to determine permissions and track usage.</p>
<p>The development flow supports two paths. In a browser-based environment, employees interact through a web UI that orchestrates agents server-side. AI-generated code executes in one of two isolation models depending on the workload. <a href="/sandbox/">Sandboxed containers</a> provide a complete development environment with preview URLs, suited for applications that need a full runtime with dependencies. <a href="/dynamic-workers/">Dynamic Workers</a> provide lightweight, instant code evaluation without container overhead, suited for rapid iteration on smaller scripts and functions. The development service can use either option independently or combine them, using Dynamic Workers for fast code validation and containers for full application previews.</p>
<p>With a local agent harness, developers use CLI-based tools like Cursor, Windsurf, or OpenCode integrated into their existing IDE and terminal workflow. Code iterates locally on the developer's machine. When ready, the developer pushes to Cloudflare where it executes in a sandboxed container or Dynamic Worker for preview and staging. <a href="/cloudflare-one/access-controls/ai-controls/mcp-portals/">MCP server portals</a> and <a href="/ai-gateway/">AI Gateway</a> can be integrated into local development flows to provide visibility into tool usage, prompt logging, and cost tracking even before code reaches the platform.</p>
<p>All LLM interactions are tracked and managed through <a href="/ai-gateway/">AI Gateway</a>, which provides provider routing, cost controls, prompt logging, and <a href="/cloudflare-one/data-loss-prevention/">DLP inspection</a>. <a href="/ai-gateway/observability/costs/">Cost tracking</a> attributes usage to projects, teams, departments, and individual users.</p>
<p>All egress from the development environment is controlled at the platform level. For containers, an <a href="/containers/guides/outbound-traffic/">outbound handler</a> intercepts HTTP traffic. For Dynamic Workers, <a href="/dynamic-workers/usage/egress-control/">egress control</a> provides equivalent capabilities. Secrets required for downstream connectivity are stored in <a href="/secrets-store/">Secrets Store</a> and injected by the outbound handler at the platform level. The sandboxed environment never has direct access to credentials. With this outbound handler, platform administrators can allow or deny specific origin destinations, reroute traffic, apply custom policies on outbound traffic, or connect to other Cloudflare resources through <a href="/workers/runtime-apis/bindings/">bindings</a>. For access to on-premises or internal systems, <a href="/workers-vpc/">Workers VPC</a> establishes private connectivity without exposing those systems to the Internet.</p>
<p>Additional security controls can be layered into the development container through package version locking and organizational controls baked into the container image. If the harness uses MCP servers, <a href="/cloudflare-one/access-controls/ai-controls/mcp-portals/">MCP portals</a> provide audit logging of tool invocations, permission management for tool access, and visibility into which tools agents use and what data they access.</p>
<h2 id="deployment-pipeline">Deployment pipeline</h2>
<p><img src="/assets/upstream/images/reference-architecture/enterprise-ai-vibe-coding/deploy-pipeline.png" alt="Deployment pipeline architecture" /></p>
<p>Assets generated in the development plane can be stored in existing enterprise code repositories or in <a href="/artifacts/">Artifacts</a>, Cloudflare's git-compatible storage built for agents. Teams can embed vibe-coded output into existing code review flows to ensure best practices and development controls are applied before the application is deployed to a production environment.</p>
<p>The platform integrates with existing enterprise software development workflows. Git repositories, secret stores, and CI/CD pipelines can all be used alongside Cloudflare-native services.</p>
<h2 id="production-plane">Production plane</h2>
<p><img src="/assets/upstream/images/reference-architecture/enterprise-ai-vibe-coding/prod-plane.png" alt="Production plane architecture" /></p>
<p>Deployed applications are hosted on <a href="/cloudflare-for-platforms/workers-for-platforms/">Workers for Platforms</a>. <a href="/cloudflare-one/access-controls/">Cloudflare Access</a> verifies and secures employee or third-party access for the entire custom domain, controlling access to deployed applications through the <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/dynamic-dispatch/">dispatch worker</a>. Granular access controls can be applied at the dispatch worker level to ensure user access matches role-based access control and assigned permissions.</p>
<p>Workers for Platforms host the vibe-coded application, with the <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/">outbound worker</a> controlling all egress. Secrets are stored in <a href="/secrets-store/">Secrets Store</a> and injected by the outbound worker, ensuring user workers never handle credentials directly. The outbound worker also controls downstream access: <a href="/workers/runtime-apis/bindings/">bindings</a>, external APIs, <a href="/hyperdrive/">Hyperdrive</a> for existing databases, or <a href="/workers-vpc/">Workers VPC</a> with <a href="/cloudflare-one/networks/connectors/cloudflare-tunnel/">Cloudflare Tunnel</a> to establish connectivity to on-premises or existing internal systems.</p>
<p>Each user worker has access to a set of <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/bindings/">bindings</a> to provide storage and services to each vibe-coded application. For complete per-tenant isolation, the platform creates and attaches a unique D1 database, KV namespace, or R2 bucket per application. Each User Worker can only access the bindings that are explicitly attached to it.</p>
<p>The dispatch worker can set <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/custom-limits/">custom limits</a> per invocation, capping the maximum processing time and the number of subrequests to prevent abuse or unintentional loops from consuming excessive resources. The platform can assign different limits by user tier, team, or application classification. If a limit is exceeded, the user worker throws an exception that the dispatch worker can handle and log.</p>
<p>Observability operates at two levels. At the platform level, <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/observability/">Workers Trace Events Logpush</a> enabled on the dispatch worker covers all user workers in the namespace. The <a href="/analytics/graphql-api/">GraphQL Analytics API</a> queries by <code>dispatchNamespaceName</code> for aggregate metrics across the platform. At the app level, <a href="/cloudflare-for-platforms/workers-for-platforms/configuration/observability/">Tail Workers</a> can be attached to individual user workers for granular logging. <a href="/analytics/analytics-engine/">Workers Analytics Engine</a> lets the platform write and query events by script tag, surfacing per-app usage metrics to individual users.</p>
<p>As the number of vibe-coded applications grows, the platform metadata store serves as an application registry, surfacing the owner, team, description, connected data sources, and usage metrics for each deployment. As with the development plane, this metadata can be stored in any preferred data store such as <a href="/d1/">D1</a>, <a href="/kv/">KV</a>, or <a href="/r2/">R2</a>. This allows employees to find existing tools before duplicating efforts. <a href="/resource-tagging/">Resource tagging</a> applied to the underlying Cloudflare resources links each user worker back to its owner and cost attribution.</p>
