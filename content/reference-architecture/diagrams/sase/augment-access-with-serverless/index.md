<h2 id="introduction">Introduction</h2>
<p>Companies using Zero Trust Network Access (ZTNA) services build policies to determine if a user can access a protected resource such as a privately hosted Wiki server or source code repository. Policies typically use group membership, authentication methods, device security posture to determine which users can access which resources.</p>
<p>Secure access requires a range of attributes being available to the policy engine for evaluation. With Cloudflare's ZTNA service, <a href="/cloudflare-one/access-controls/policies/">Access</a>, it is possible to include in the policy an external request to another API that provides part of the data required for the access decision.</p>
<p>For example, you might have a policy which states all members of the group &quot;Engineers&quot;, who have authenticated with credentials that required a hard token, can have access to the self-hosted source code repository. But you also want to only allow engineers who have completed security training. That data might be available in another system, so Cloudflare allows you to, as part of the policy check, make a call using <a href="https://workers.cloudflare.com/">Workers</a> to the training system to determine if this user has passed security training.</p>
<p>Additionally, once authentication and the policy checks are successful Cloudflare passes traffic to the protected origin. It is important to note that the origin should, too, verify that the incoming requests are authenticated by Cloudflare in order to avoid any illegitimate access. Cloudflare inserts a JWT token in the traffic destined to the origin to prove cryptographically that the request was successfully authenticated, and the origin can use this data as part of its authorization logic.</p>
<p>To help integrate these types of use cases, Cloudflare has an <a href="/workers/">entire development platform</a> on which you can design and run your own business logic. This means you spend less time trying to piece a solution together and more time getting the integration done.</p>
<p>This document outlines how to combine both solutions to enhance Cloudflare Access capabilities in terms of <a href="https://www.cloudflare.com/learning/access-management/what-is-access-control/">authorization and authentication</a>.</p>

<h2 id="use-cases">Use-cases</h2>
<ul>
<li><strong>Custom authorization logic</strong>: Access External evaluation using Workers as a backend (for example, using your own implementation of <a href="https://www.openpolicyagent.org/integrations/cloudflare-worker/">Open Policy Agent aka OPA</a>])</li>

<h2 id="getting-started">Getting started</h2>
<p>The following outlines how organizations can run their own custom business logic, allowing them to tailor authentication and authorization processes to meet almost any requirement. Each use case below refers to a step in the above diagram.</p>
<h3 id="1-custom-authorization-process-using-your-own-rules"><ol>
<li>Custom authorization process using your own rules</li>
</ol></h3>
<p>During policy evaluation, the <a href="/cloudflare-one/access-controls/policies/external-evaluation/">external evaluation</a> rule allows for executing your own code during access policy evaluation. In this example an API exposed by Cloudflare Workers receives data about the user making the request, the important part being their username.</p>
<p>The code typically makes calls to either a <a href="/d1/">database</a> or another API to evaluate if the passed username has access to the application. The external evaluation rule requires that the call returns either a True or False, and this is combined with the policy to determine access.</p>

<h3 id="2-analyze-and-validate-the-authentication-material-jwt"><ol start="2">
<li>Analyze and validate the authentication material (JWT)</li>
</ol></h3>
<p>When a user successfully authenticates and is authorized to access a protected application, Cloudflare inserts a <a href="/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/">JSON Web Token (JWT)</a> into the HTTP traffic sent to the origin. This token serves as a valuable asset for expanding custom business logic through secure processing. The format for that JWT is deterministic and rather lightweight to avoid overloading the requests towards origin unnecessarily.</p>
<p>Here is an example of a JWT sent to an origin (use <a href="http://jwt.io">JWT.io</a> to read the contents of a JWT)</p>
<pre tabindex="0"><code class="language-json">{&#10;	&quot;aud&quot;: [&quot;264063895705477af73bfbaed1bf401981f4812eefcdb9fea33f5e10e666e282&quot;],&#10;	&quot;email&quot;: &quot;john.doe@cloudflare.com&quot;,&#10;	&quot;exp&quot;: 1728551137,&#10;	&quot;iat&quot;: 1728464737,&#10;	&quot;nbf&quot;: 1728464737,&#10;	&quot;iss&quot;: &quot;https://myorg.cloudflareaccess.com&quot;,&#10;	&quot;type&quot;: &quot;app&quot;,&#10;	&quot;identity_nonce&quot;: &quot;IA0hPRvwILtbUXSQ&quot;,&#10;	&quot;sub&quot;: &quot;ce40d564-c72f-475f-a9b8-f395f19ad986&quot;,&#10;	&quot;device_id&quot;: &quot;8469d7c4-83a9-11ee-b559-76e6e80876db&quot;,&#10;	&quot;country&quot;: &quot;FR&quot;&#10;}&#10;</code></pre>
<p>Cloudflare exposes a specific <a href="/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/#_top">endpoint</a> to allow anyone to validate and expand a Cloudflare signed JWT.</p>
<p>Cloudflare's Workers are a great candidate for interacting with incoming JSON Web Tokens (JWTs), enabling additional processing directly within the serverless platform without introducing any added latency.</p>
