<p>The <a href="https://developers.cloudflare.com/">Cloudflare Docs</a> are open source and hosted on the <a href="https://github.com/cloudflare/cloudflare-docs">cloudflare-docs repository</a> on GitHub. This means that anyone, including those who are not part of the Cloudflare organization, can contribute to them. We welcome all suggestions that help keep our docs high quality and up to date.</p>
<p>To contribute to our docs, you will need to <a href="https://docs.github.com/en/get-started/start-your-journey/creating-an-account-on-github">create an account on GitHub</a> (if you do not have one already) and log in. Then you have three options:</p>
<ul>
<li><a href="#create-a-github-issue">GitHub issue</a>: Quickly submit a general suggestion.</li>
<li><a href="#quick-edit">Quick edit (edit button)</a>: Quickly create a pull request. This is best if you want to edit a single page in your web browser and do not need to preview your changes.</li>
<li><a href="#full-development">Full development</a>: Create a pull request. This is best if you want to edit multiple pages and preview your changes. This can be done in your web browser (with <a href="https://docs.github.com/codespaces">Codespaces</a>) or on your local machine (with <a href="https://code.visualstudio.com/">Visual Studio Code</a>).</li>
</ul>
<p>In addition to using the <a href="/style-guide/">Cloudflare Style Guide</a> for guidance on grammar and style, we recommend browsing our <a href="/style-guide/build-the-page/components/">components</a> to add additional formatting such as buttons, tabs, and collapsible sections.</p>
<h2 id="create-a-github-issue">Create a GitHub issue</h2>
<p>To create a GitHub issue:</p>
<ol>
<li><a href="https://github.com/login">Log in to GitHub</a> and go to the <a href="https://github.com/cloudflare/cloudflare-docs">cloudflare-docs repository</a>.</li>
<li>Select <strong>Issues</strong> and then <strong>New issue</strong>.</li>
<li>Select the issue type, fill out the form, and select <strong>Create</strong>.</li>
</ol>
<p><a href="https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue">Learn more about creating GitHub issues.</a></p>
<h2 id="quick-edit">Quick edit</h2>
<p>To quickly create a pull request using the edit button:</p>
<ol>
<li><a href="https://github.com/login">Log in to GitHub</a>.</li>
<li>Go to the page you want to edit in the <a href="https://developers.cloudflare.com/">Cloudflare Docs</a></li>
<li>Select <details class="nb-details"><summary><strong>Edit</strong> or <strong>Edit page</strong></summary><div class="nb-details-body"></li>
</ol>

</div></details>
   The page's Markdown opens.
<aside class="nb-aside note">

4. Make your edits and select **Commit changes**.
5. In the form, update the **Commit message** with the product you changed in brackets and a brief description of your changes. For example “[Images] Fixed broken link."
6. Update the **Extended description** with more details about what you changed and why. The more details, the better.
7. Select **Propose changes** > **Create pull request** > **Create pull request** again.
<h2 id="full-development">Full development</h2>
<p>To edit and create a pull request with the <a href="https://docs.github.com/en/codespaces/developing-in-a-codespace/using-source-control-in-your-codespace">full development workflow</a>:</p>
<ol>
<li><a href="https://github.com/login">Log in to GitHub</a> and <a href="https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/fork-a-repo">fork the cloudflare-docs repository</a>.</li>
<li>If you are editing in your web browser (with <a href="https://docs.github.com/en/codespaces">Codespaces</a>), move on to step 3.</li>
</ol>
<br />
   If you are editing on your local machine (with [Visual Studio
   Code](https://code.visualstudio.com/)): * (Required) Install
   [Node.js](https://nodejs.org/en) (version 24 or later). * (Recommended, but
   not required) Install [Volta](https://volta.sh/) for easier package
   management. * (Required) [Clone the fork to your local
   machine.](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository)
3. Create a branch from your fork (or from your clone).
4. Make your edits.
5. Preview your edits by installing the dependencies and starting the local development server:
<pre tabindex="0"><code class="language-bash">pnpm install&#10;pnpm run dev&#10;</code></pre>
<p>A link appears in the terminal, for example <code>https://localhost:1111/</code>, where you can preview your changes. The preview updates automatically as you edit.</p>
<ol start="6">
<li>Commit your changes.</li>
<li>Push your commits to your branch and then back to your fork.</li>
<li>Return to GitHub and create a pull request from your committed changes. In the description form, add the product you changed in brackets and a brief description of your changes. For example, &quot;[Images] Fixed broken link.&quot;</li>
</ol>
<h2 id="after-you-create-an-issue-or-pr">After you create an issue or PR</h2>
<p>After you create an issue or PR, a member of the Cloudflare organization will review your suggestion. Here is what to expect:</p>
<ul>
<li>A member of the Cloudflare organization may tag others for technical or content reviews or feedback.</li>
<li>If your suggestion requires more information, a member of the Cloudflare organization may comment with a follow-up or clarification question. If they add the <code>more-information-needed</code> tag, the issue or pull request will automatically close if you do not respond within 14 days.</li>
<li>If your changes are approved:
<ul>
<li>For GitHub issues, a Cloudflare member might create and link a new pull request that addresses your request. When they merge the PR, they will also close your issue.</li>
<li>For GitHub PRs, the Cloudflare member will merge your PR.</li>
</ul>
</li>
<li>If your suggestion is not approved, the Cloudflare member will respond with the reasoning and close your issue or PR.</li>
</ul>
<p>Thank you for contributing to our open-source ecosystem and being a part of the Cloudflare community.</p>
<h2 id="content-reviews">Content reviews</h2>
<p>We work (and appreciate working) in <a href="https://github.com/cloudflare/cloudflare-docs">GitHub</a>, but it's not a perfect tool by any means.</p>
<p>We've added several ergonomic improvements to help us triage incoming work, streamline reviews, and automate communication.</p>
<h3 id="triage-work">Triage work</h3>
<p>To help our writers triage work (and help with backend reporting), we automate a few labels and issue / pull request assignment.</p>
<h4 id="pull-requests">Pull requests</h4>
<p>For pull requests, we use a specific <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/pr-label-assign.yml">GitHub action</a> to add labels and assign codeowners.</p>
<ul>
<li><a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/actions/label-products/">Label products</a>: We add labels for the top-level product folder, which helps writers scan incoming pull requests and see which are relevant to them.</li>
<li><a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/actions/label-size/">Label size</a>: We add labels for the size of the pull request, which helps writers see the relative size of the difference. It's not a perfect measure, but we use the lines changed to estimate the size of the pull request:</li>
<li><a href="https://github.com/cloudflare/cloudflare-docs/tree/production/.github/actions/assign-pr">Assign codeowners</a>: We use our <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/CODEOWNERS">CODEOWNERS</a> file to automatically assign people to pull requests based on the files changed. This assignment helps writers scan and filter to see which pull requests are relevant to them.</li>
</ul>
<h4 id="issues">Issues</h4>
<p>For issues, we use a similar <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/issue-label-assign.yml">GitHub action</a> to add labels and assign codeowners.</p>
<p>Our <a href="https://github.com/cloudflare/cloudflare-docs/tree/production/.github/actions/issue-label-assign">script</a> treats issues because usually they contain links to our site instead of files within the repository. We grab the associated links in the issue description fields and then use those to assign writers (again based on <code>CODEOWNERS</code>) and add product labels.</p>
<h3 id="streamline-reviews">Streamline reviews</h3>
<p>To streamline reviews, we use several automations to help solve common reviewer issues.</p>
<h4 id="will-this-break-anything">Will this break anything?</h4>
<p>We have one required check that runs on every commit, <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/ci.yml">CI</a>.</p>
<p>This check makes sure that:</p>
<ul>
<li>The site builds correctly.</li>
<li>All <a href="/style-guide/how-we-docs/links/#internal-links">internal links</a> are valid.</li>
<li>There are no <a href="/style-guide/how-we-docs/redirects/#infinite-redirects">infinite redirects</a>.</li>
<li>Specific pages and functionality in our docs <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/worker/index.worker.test.ts">behave as expected</a>.</li>
</ul>
<h4 id="who-needs-to-approve-this">Who needs to approve this?</h4>
<p>We commonly get questions about approvals, especially for pull requests that touch multiple product areas (or our components).</p>
<p>On open pull requests, the Cloudflare Docs Bot posts a <a href="https://github.com/cloudflare/cloudflare-docs/tree/production/.flue">Review coverage</a> comment that shows which areas still need a CODEOWNERS approval, suggests contacts for those areas, and summarizes the areas already covered. Expand the CODEOWNERS mappings section to see the exact patterns and owners for the ownership areas displayed in the comment. The bot skips draft, closed, and spam/off-topic pull requests.</p>
<h4 id="what-changed">What changed?</h4>
<p>We use a <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/publish-preview.yml">GitHub action</a> to publish preview builds for every commit on a pull request (and <a href="https://github.com/cloudflare/cloudflare-docs/tree/production/bin/post-preview-url-comment">comment those links</a> on the pull request). This action ensures that reviewers can see exactly what the site and content will look like when they're rendered (and not just look at the changed markdown in GitHub).</p>
<p>We are in the process of migrating to <a href="/workers/ci-cd/builds/git-integration/github-integration/">Workers Builds</a>, which provides that functionality natively.</p>
<p>Based on feedback, we have also added a before/after table of links to help reviewers easily find links in the preview builds.</p>
<p><img src="/assets/upstream/images/style-guide/how-we-docs/preview-comment.png" alt="Before/after table" /></p>
<h4 id="is-there-anything-else-i-need-to-check">Is there anything else I need to check?</h4>
<p>One difficult thing to check is potential redirects when a pull request renames or deletes content file paths.</p>
<p>We have a <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/comment-changed-filenames.yml">specific action</a> that posts a comment to help reviewers identify and then check these paths.</p>
<p><img src="/assets/upstream/images/style-guide/how-we-docs/redirects-github.png" alt="GitHub Actions redirect comment" /></p>
<h3 id="automate-communication">Automate communication</h3>
<p>We automate communication primarily through the <a href="https://github.com/lee-dohm/no-response"><code>no-response</code></a> GitHub Action.</p>
<p>Being open source means that we accept issues and pull requests from anyone! And a lot of these are either self explanatory or have enough context for us to follow up on them.</p>
<p>The ones without enough context, however, are often painful (especially in a <a href="https://github.com/cloudflare/cloudflare-docs/pulse">busy repo</a> like ours). A writer has to ask for more detail, then remember to check back in, and then sometimes re-ask for more detail, and then check in again.</p>
<p>To help avoid some of this mental toil, we'll ask a question and then apply the <code>more-information-needed</code> label. This label starts a <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/no-response.yml">14-day clock</a> for the author to respond. If they do respond, the label gets removed and the conversation can continue. If they don't respond, the issue automatically gets closed with a <a href="https://github.com/cloudflare/cloudflare-docs/issues/22943#issuecomment-3002211164">comment explaining why</a>.</p>
<p><img src="/assets/upstream/images/style-guide/how-we-docs/no-response-comment.png" alt="No response comment" /></p>
<p>This workflow - we hope - balances the needs our of team with a healthy respect for our contributors.</p>
<h4 id="stale-issues">Stale issues</h4>
<p>We intentionally avoid the <a href="https://github.com/github/docs/blob/main/.github/workflows/stale.yml"><code>stale</code> workflow</a> that closes pull requests or issues that have been inactive for a specific period of time.</p>
<p>In our opinion, this workflow causes more friction and frustration than it solves. Just because something has been around for a year doesn't mean it's not still relevant.</p>
<h2 id="contribute-to-cloudflare-documentation-with-ai">Contribute to Cloudflare documentation with AI</h2>
<p>The <code>cloudflare-docs</code> repository includes an <a href="https://github.com/cloudflare/cloudflare-docs/blob/production/AGENTS.md"><code>AGENTS.md</code></a> file that helps AI coding agents understand the structure, tooling, and conventions of the repository so they can make correct, buildable changes when contributing to documentation.</p>
<p><a href="https://agents.md/">AGENTS.md</a> is a simple, open format for guiding coding agents.</p>
<p>The repository includes configuration for the following AI tools out of the box:</p>
<ul>
<li><a href="https://opencode.ai/">OpenCode</a></li>
<li><a href="https://windsurf.com/">Windsurf</a></li>
<li><a href="https://claude.ai/code">Claude Code</a></li>
<li><a href="https://github.com/google-gemini/gemini-cli">Gemini CLI</a></li>
<li><a href="https://github.com/features/copilot">GitHub Copilot</a> (via VS Code)</li>
</ul>
<p>Agent skills, commands, and agent definitions all live in <code>.agents/</code> and are symlinked into the expected locations for each tool automatically.</p>
