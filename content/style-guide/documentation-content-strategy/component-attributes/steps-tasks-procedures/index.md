<h2 id="definition">Definition</h2>
<p>Action-oriented processes that outline steps to take and the order the steps should be taken.</p>
<h2 id="used-in">Used in</h2>
<p><a href="/style-guide/documentation-content-strategy/content-types/how-to/">How to</a>, <a href="/style-guide/documentation-content-strategy/content-types/tutorial/">Tutorial</a></p>
<h2 id="structure">Structure</h2>
<p><strong>Single-step procedures</strong>: When a procedure consists of just one step, add the step into the introductory sentence.</p>
<p><strong>Sub-steps in numbered procedures</strong>: In a numbered procedure, sub-steps should be lowercase letters, and sub-sub-steps get lowercase Roman numerals.</p>
<ul>
<li>When a step has sub-steps, treat the step like an introductory sentence. Put a colon or a period at the end of the step where appropriate.</li>
</ul>
<p><strong>Multi-action procedures</strong>: Use one step per action. However, you can combine small actions into one step.</p>
<p><strong>Multiple procedures for the same task</strong>: If there is more than one way to complete a task, pick one procedure to document that is accessible for all users. If all of the procedures need to be documented, use separate headings or pages or tabs to separate the procedures to make it clear to the reader that this is an alternative way to complete the same task.</p>
<p>The following guidelines can help you choose which procedure to document:</p>
<ul>
<li>Choose a procedure that lets readers do all the steps using only a keyboard.</li>
<li>Choose the shortest procedure.</li>
<li>Choose a procedure that uses a programming language that the majority of your audience is familiar with.</li>
</ul>
<p><strong>Repetitive procedures</strong>: Use concise procedures to avoid repetitiveness and overwhelming the user with a lot of bold UI elements.</p>
<p><a href="/style-guide/style-and-grammar/formatting/structure/lists/">Bullets vs. Numbered Lists</a></p>
<p><strong>Post requisites</strong>: Not used at this time. If you feel like you need a post requisites section, consider adding the task as the final step of a procedure or moving the content into Next steps.</p>
<h2 id="guidelines-for-writing-procedures">Guidelines for writing procedures</h2>
<p>If the user must log in to the dashboard as a first step, consolidate logging in and navigation into the first step. Also, write &quot;log in to&quot; (three words) instead of &quot;log into&quot;.</p>
<p>If the user must press <strong>Enter</strong> after a step, then include that instruction as part of the step.</p>
<p>If the user has to turn a setting on or off, use &quot;turn &lt;FEATURE_NAME&gt; on/off&quot; — or &quot;turn on/off &lt;FEATURE_NAME&gt;&quot; for features with long names — instead of &quot;enable/disable&quot;.</p>
<p>State the purpose of the action before stating the action.</p>
<p>Write in the order that the reader needs to follow. State the location of the action before stating the action. If there are multiple headings associated with a set of procedures, restate the location of the action in the first step of each procedure, even if the location is the same as in the previous procedure.</p>
<p>Do not use &quot;please.&quot;</p>
<h2 id="additional-information">Additional information</h2>
<p>Use complete sentences.</p>
<p>Use parallel structure.</p>
<p>Use second person imperative. Refer to the Style Guide for guidance on when to use certain verbs (click, select, choose, etc).</p>
<p>For an optional step, type (Optional) as the first word of the step.</p>
<ul>
<li>For example: (Optional) Type an arbitrary string, to be delivered to the target address with each notification delivered over this channel.</li>
</ul>
<p>Do not include keyboard shortcuts.</p>
<p>Do not use directional language to orient the reader, such as above, below, or right-hand side. This type of language does not work well for accessibility or for localization. If a UI element is hard to find, provide a screenshot.</p>
<p>Use sentences like &quot;The <code>&lt;screen/page/card&gt;</code> displays.&quot; wisely.</p>
