<p>Though all Terraform deployments are unique, follow these best practices to set yourself up for success.</p>
<h2 id="manage-terraform-resources-in-terraform">Manage Terraform resources in Terraform</h2>
<p>Terraform works best when it manages all changes to and the lifecycle of a resource.</p>
<p>After any operation on the configuration, Terraform attempts to reconcile the differences by syncing the remote into the local state. If there are differences in the local and remote - caused by managing resources outside of Terraform - you may need to delete and recreate the resource in the state file (usually via importing) as not all resources support in-place updates.</p>
<h2 id="directory-structure">Directory structure</h2>
<p>Cloudflare recommends using a directory structure that relies on a combination of accounts, zones, and products for isolating changes. This setup lets you have fine-grained owners and scoped Terraform operations to a specific product in a zone. It also more closely aligns owners with Cloudflare's <a href="/fundamentals/manage-members/roles/">default roles</a>, as well as additional tools like AWS or GCP storage by permissioning separate state files.</p>
<p>For products that encompass many responsibilities such as Rulesets, you can extend this even further by partitioning at the phase level (WAF, redirects, origin rules).</p>

<h2 id="avoid-modules-or-use-them-sparingly">Avoid modules (or use them sparingly)</h2>
<p>Terraform modules are ways of encapsulating multiple resources with logic in an abstracted interface. Consider the example where a module sets up default load balancer with a pool, some DNS entries, and perhaps a page rule. The end user may use it like this:</p>
<pre tabindex="0"><code class="language-hcl">module &quot;example&quot; &quot;an_example_site&quot; {&#10;  domain = &quot;example.com&quot;&#10;  origin_ip = &quot;192.168.0.1&quot;&#10;}&#10;</code></pre>

<p>While convenient, this setup can cause unanticipated issues. If this module is shared and then changes internally, the module may have resources out of sync or recreated.</p>
<p>Using modules also increases the difficulty of debugging or reproducing issues as you must then factor in potential logic bugs outside of Terraform core and the Cloudflare provider.</p>

<h2 id="migrate-resources-into-terraform">Migrate resources into Terraform</h2>
<p>Cloudflare recommends using <a href="/terraform/advanced-topics/import-cloudflare-resources/"><code>cf-terraforming</code></a> to migrate existing resources into Cloudflare.</p>
<h2 id="manage-some-resources-outside-of-terraform">Manage some resources outside of Terraform</h2>
<p>It is perfectly fine to manage some resources inside Terraform and others using a different tool, but make sure you are not <a href="#manage-terraform-resources-in-terraform">doing both for the same resource</a>.</p>
<h2 id="use-separate-environments">Use separate environments</h2>
<p>To safely manage separate environments (staging, QA, UAT, production), use separate Cloudflare accounts with separate domains (such as <code>example.com</code> and <code>example-staging.com</code>).</p>
<p>This is because some products defined at the account level are shared (such as Load Balancer monitors and pools) and you cannot make an isolated change to them if they are in the same account. Using separate accounts is also beneficial if you intend to test things like DNSSEC, which may affect your entire domain if configured incorrectly.</p>
<p>To minimize drift, use Terraform and a CI/CD pipeline that runs across both domains to keep them in sync as needed.</p>
<h2 id="store-credentials-safely">Store credentials safely</h2>
<p>We do not recommend storing Cloudflare credentials as plaintext.</p>
<p>Locally, you can use a third-party tool like <a href="https://github.com/jacobbednarz/cf-vault/">cf-vault</a> to store your Cloudflare credentials.</p>
<p>For CI pipelines, use an internal or secret storage tool (such as <a href="https://www.hashicorp.com/products/vault/secrets-management">Vault</a>).</p>
