<p>There are instances where Turnstile may encounter problems, invoking the <code>error-callback</code>.</p>
<p>These problems can range from network connectivity issues and browser compatibility problems to configuration errors and challenge failures.</p>
<p>When errors occur, implementing proper error handling ensures your visitors receive helpful feedback and your application can recover from temporary issues.</p>
<p>Refer to the <a href="/turnstile/troubleshooting/client-side-errors/error-codes/">Error codes</a> for troubleshooting guidance to address specific error conditions.</p>
<h2 id="error-handling">Error handling</h2>
<p>The <code>error-callback</code> option for explicitly rendering widgets and the <code>data-error-callback</code> attribute for implicit rendering provides a JavaScript callback to handle potential errors that occur.</p>
<p>This callback mechanism gives you complete control over how errors are presented to visitors and allows you to implement custom recovery strategies tailored to your application's needs.</p>

<p>Specifying an error callback is optional, but recommended for production applications. If no error callback is set, Turnstile will throw a JavaScript exception upon error, which can disrupt your page's functionality and create a poor user experience. By providing an error callback, you can catch these exceptions and handle them.</p>
<p>If an error callback returns with a non-falsy result, Turnstile will assume that the error callback handled the error accordingly and will not perform any additional error logging. If the error callback returns with a falsy result (including <code>undefined</code>), Turnstile will log a warning to the JavaScript console containing the error code, which can be useful for debugging during development.</p>
<p>An error callback will retrieve an error code as its first parameter. This error code follows a structured format where the first three digits indicate the error family (such as configuration issues, network problems, or challenge failures), and the remaining digits specify the exact error within that family.</p>
<pre tabindex="0"><code class="language-js">function handleTurnstileError(errorCode) {&#10;  const errorFamily = Math.floor(errorCode / 1000);&#10;  &#10;  switch(errorFamily) {&#10;    case 100:&#10;      showMessage(&#x27;Please refresh the page and try again.&#x27;);&#10;      break;&#10;    case 110:&#10;      showMessage(&#x27;Configuration error. Please contact support.&#x27;);&#10;      break;&#10;    case 300:&#10;    case 600:&#10;      showMessage(&#x27;Security check failed. Please try refreshing or using a different browser.&#x27;);&#10;      break;&#10;    default:&#10;      showMessage(&#x27;An unexpected error occurred. Please try again.&#x27;);&#10;  }&#10;}&#10;</code></pre>
<h2 id="retry">Retry</h2>
<p>By default, Turnstile will automatically retry upon encountering a problem, which helps handle transient network issues or temporary service disruptions without requiring user intervention.</p>
<p>This automatic retry mechanism is useful for <a href="/turnstile/get-started/mobile-implementation/">mobile visitors</a> who may experience intermittent connectivity or visitors on networks with occasional stability issues.</p>
<p>When subsequent failures due to retries are observed, the error callback can be invoked multiple times for the same underlying issue. Your error handling code should account for this possibility to avoid showing duplicate error messages or performing the same recovery action repeatedly.</p>
<pre tabindex="0"><code class="language-js">let retryCount = 0;&#10;&#10;turnstile.render(&#x27;#my-widget&#x27;, {&#10;  sitekey: &#x27;your-sitekey&#x27;,&#10;  &#x27;error-callback&#x27;: function(errorCode) {&#10;    retryCount++;&#10;    &#10;    if (retryCount &lt;= 2) {&#10;      console.log(`Turnstile retry attempt ${retryCount}`);&#10;      return false; // Let Turnstile handle the retry&#10;    } else {&#10;      showPersistentErrorMessage(errorCode);&#10;      return true; // We&#x27;ll handle it from here&#10;    }&#10;  }&#10;});&#10;</code></pre>
<p>You can adjust the retry behavior by setting the retry value to <code>never</code> instead of the default <code>auto</code>. This will result in Turnstile not automatically retrying, giving you control over when and how recovery attempts are made. If there is any issue or error verifying the visitor, the widget will not retry and will remain in the respective failure state until you take manual action.</p>
<pre tabindex="0"><code class="language-js">turnstile.render(&#x27;#my-widget&#x27;, {&#10;  sitekey: &#x27;your-sitekey&#x27;,&#10;  retry: &#x27;never&#x27;,&#10;  &#x27;error-callback&#x27;: function(errorCode) {&#10;    // You control all retry logic&#10;    setTimeout(() =&gt; {&#10;      turnstile.reset(&#x27;#my-widget&#x27;);&#10;    }, 3000);&#10;  }&#10;});&#10;</code></pre>
<p>You may call <code>turnstile.reset()</code> in the corresponding <code>error-callback</code> to manually trigger a retry. This approach is useful for when you want to implement custom retry logic, such as exponential backoff, user confirmation before retrying, or different retry strategies based on the specific error encountered.</p>
<p>The interval between retries for Turnstile can be configured by the <code>retry-interval</code> option, allowing you to optimize retry timing for your visitors’ typical network conditions. A longer interval may be more appropriate for visitors on slower or less reliable connections, while shorter intervals work well in environments with typically stable connectivity.</p>
<pre tabindex="0"><code class="language-js">turnstile.render(&#x27;#my-widget&#x27;, {&#10;  sitekey: &#x27;your-sitekey&#x27;,&#10;  retry: &#x27;auto&#x27;,&#10;  &#x27;retry-interval&#x27;: 8000, // Wait 8 seconds between retries&#10;  &#x27;error-callback&#x27;: handleError&#10;});&#10;</code></pre>
<h2 id="interactivity">Interactivity</h2>
<p>If the visitor fails to engage with an interactive challenge within a reasonable timeframe, the timeout callback function is triggered. This timeout mechanism prevents challenges from remaining in a pending state indefinitely and ensures that visitors receive feedback when action is required.</p>
<p>For instance, in a scenario where the Turnstile widget is implemented within a form that may require several minutes to complete, the interactive challenge within the widget becomes outdated if it remains unaddressed for an extended period. Visitors might focus on filling out form fields and overlook the Turnstile challenge, leading to a situation where they attempt to submit the form with an expired or invalid token.</p>
<p>In such instances, the <code>timeout-callback</code> of the widget is activated, enabling the widget to reset itself as needed and provide appropriate guidance. This callback allows you to implement user-friendly timeout handling, such as highlighting the Turnstile widget, displaying a notification, or automatically refreshing the challenge.</p>
<pre tabindex="0"><code class="language-js">turnstile.render(&#x27;#my-widget&#x27;, {&#10;  sitekey: &#x27;your-sitekey&#x27;,&#10;  callback: function(token) {&#10;    console.log(&#x27;Challenge completed successfully&#x27;);&#10;  },&#10;  &#x27;timeout-callback&#x27;: function() {&#10;    console.log(&#x27;Challenge timed out - user action required&#x27;);&#10;    document.getElementById(&#x27;challenge-notice&#x27;).textContent = &#10;      &#x27;Please complete the security check above to continue.&#x27;;&#10;    &#10;    // Optionally highlight the widget&#10;    document.getElementById(&#x27;my-widget&#x27;).style.border = &#x27;2px solid orange&#x27;;&#10;  },&#10;  &#x27;expired-callback&#x27;: function() {&#10;    console.log(&#x27;Token expired - challenge needs refresh&#x27;);&#10;    document.getElementById(&#x27;challenge-notice&#x27;).textContent = &#10;      &#x27;Security check expired. Please try again.&#x27;;&#10;  }&#10;});&#10;</code></pre>
