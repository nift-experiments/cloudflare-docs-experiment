<header><h1>SASE - Stop hosting your VPN service</h1></header>
<section class="video-content" aria-label="Video">
<p>Cloudflare's SASE platform can replace your traditional, expensive VPN appliances, which deliver poor performance for users and create more security risks than solve them. Cloudflare's Zero Trust Network Access (ZTNA) service is a more secure, highly scalable cloud solution. In this video, we look at how easily you can deploy Cloudflare to secure access to internal resources.</p>

<details class="nb-details"><summary>Transcript</summary><div class="nb-details-body video-transcript"><p>Corporate networks are often used to allow employees to access sensitive information in</p><p>private, self-hosted applications, such as an internal wiki,</p><p>a HR system, or a source code repository.</p><p>While some applications have migrated into the cloud as SaaS apps,</p><p>there are still applications that are run and maintained by IT.</p><p>These days, most of these self-hosted applications run in a web server and are</p><p>deployed either in a private data center or in a public cloud such as AWS,</p><p>Azure, or Google. Access to these applications is usually limited to internal</p><p>employees, but it's common to allow some form of restricted access to partners or</p><p>contractors. The old way of doing things was to have users either come into a physical</p><p>office or connect remotely via a VPN, giving them access to that corporate network</p><p>so they could access the application.</p><p>But these VPN solutions use on premises hardware appliances through which every user</p><p>request passes, creating a bottleneck and a security risk.</p><p>In fact, recently, many on premises VPN vendors such as Cisco,</p><p>Checkpoint, and Fortinet have reported a wide range of vulnerabilities which requires IT</p><p>and security teams to scramble to update their systems.</p><p>But there's another way to do this.</p><p>Did you know that Cloudflare can be used to easily create secure access to these</p><p>self-hosted applications using our SASE platform?</p><p>That's part of our connectivity cloud?</p><p>Well, similar to how a legacy VPN works, but using a much,</p><p>much more modern cloud approach.</p><p>Let's take a look at how we improve on the old way of doing things,</p><p>and create greater security for application access.</p><p>The first objective is to create connectivity between the user's browser and the</p><p>application. Right. So there are two parts to this. The connection from Cloudflare to the</p><p>app and the connection between the user and Cloudflare.</p><p>Cloudflare is going to sit in the middle and apply security policies and use its vast</p><p>network to protect the application and improve response times.</p><p>For the first part, to create connectivity from Cloudflare to the app,</p><p>we use tunnels that a variety of different methods you can use.</p><p>You can connect on premises networks to Cloudflare via IPsec or GRE tunnels,</p><p>typically using your existing network hardware,</p><p>or if your applications are running at a data center where Cloudflare already has its</p><p>servers, we can connect directly from your servers to our servers inside that data</p><p>center. But for this example, we're going to talk about using a software</p><p>agent. It's just a small daemon that is installed either directly on the application</p><p>server or runs on a dedicated server on the same local network.</p><p>The software then creates a secure tunnel back to Cloudflare.</p><p>This tunnel maintains a constant connection to two Cloudflare data centers,</p><p>so it's always available, and now your traffic can flow between your</p><p>Cloudflare network and the application.</p><p>Now for the second part, we need to connect your users to Cloudflare,</p><p>which we're going to do in this example using public DNS.</p><p>We'll associate a public hostname with the application.</p><p>Request to this hostname will resolve to Cloudflare,</p><p>which in turn proxies and routes traffic down the tunnel to the application,</p><p>but hold on a second. A public DNS record and a tunnel directly to the server?</p><p>If we didn't take this any further, we could now access this internal application</p><p>from anywhere just by heading to the new public hostname.</p><p>What we need to do is add authentication and authorization into the mix.</p><p>Because Cloudflare is now in front of access to the application,</p><p>we can integrate with your existing company identity providers.</p><p>So anyone attempting to access is first redirected to your identity provider to</p><p>authenticate. Now this is where it gets interesting because you can add multiple</p><p>identity providers in front of the same application.</p><p>So for example, you might use your main company directory where all your employee</p><p>accounts reside, but you might also integrate a separate identity service just for</p><p>contractors, partners and other third party users.</p><p>We also support consumer identity providers such as Facebook,</p><p>Google or GitHub. In fact, any SAML or OAuth identity service can be</p><p>used. Now, these identity integrations don't just provide authentication.</p><p>It's possible to import user and group information.</p><p>Which brings us on to the next step.</p><p>Now that we've ensured a user has authenticated,</p><p>we can start to leverage their identity information and other data to create an</p><p>access policy that defines who should and should not get access to the application.</p><p>Let's build a policy here in real time.</p><p>A range of different attributes can be used that define who is allowed or denied access.</p><p>We started by adding an identity provider, so users first need to authenticate.</p><p>Let's take it a little further and leverage group information from the same identity</p><p>service. We can say only users in the full time employees group have access to the</p><p>internal wiki. The identity service can also tell us how they authenticated.</p><p>So let's add that to our policy.</p><p>The requirement that they must have authenticated using MFA or multi-factor</p><p>authentication. In fact, let's say that they have to specifically use</p><p>a hard token such as a FIDO certified key.</p><p>Finally, we only want users working from Canada,</p><p>the US or Germany to access the application.</p><p>So let's add to the policy that only traffic coming from IP addresses geolocated in those</p><p>countries is allowed. Now, full time employees working from somewhere in</p><p>Canada who have authenticated using a strong set of credentials will be able to access the</p><p>company wiki. Let's take a look at this in action.</p><p>The user just needs to navigate to the public hostname,</p><p>authenticate, and bingo!</p><p>They have access from anywhere in the world with only a browser to our privately hosted</p><p>application. Simple. What a difference from the old way of doing things.</p><p>Also, it's important to note that all traffic from browser to application is secured using</p><p>standard TLS and SSL encryption, keeping the application data safe.</p><p>Let's turn our attention a little bit to performance.</p><p>We already mentioned that Cloudflare is a lot more efficient than a traditional VPN.</p><p>Let's think about somebody in Germany trying to access the wiki.</p><p>Cloudflare uses something called Anycast networking,</p><p>which means that a request to the hostname will resolve to the nearest Cloudflare data</p><p>center, of which we have many in over 300 cities.</p><p>We also have 12,000 network peering relationships,</p><p>allowing us to ensure fast connectivity from user to application.</p><p>So our user in Germany might on ramp to Cloudflare at a data center in Berlin,</p><p>whereas our Canadian user might on ramp in Vancouver,</p><p>and their requests are authenticated and the policy evaluated all close to the end user</p><p>and if authorized, their request is then routed via the most efficient network path to</p><p>the Cloudflare data center that is then nearest the application.</p><p>To further improve performance, there are many more things we can do.</p><p>Any of Cloudflare's existing performance services and network benefits apply to your</p><p>application traffic. So, for example, we can leverage Cloudflare's</p><p>caching technologies so that any static data from the wiki such as images,</p><p>files, videos is all cached locally at the data center that the user is accessing.</p><p>Something your old VPN could never do.</p><p>Setting up access like this can be typically done in less than an hour,</p><p>and it doesn't take long to migrate an entire company's internal application</p><p>infrastructure. Unlike your VPN, access to each application only exposes that</p><p>specific service. You don't need to worry about firewalling off SSH and RDP,</p><p>because Cloudflare is only allowing access to the specific application over HTTPS.</p><p>This is called network micro-segmentation and really reduces concerns of access gained by</p><p>lateral movement.
