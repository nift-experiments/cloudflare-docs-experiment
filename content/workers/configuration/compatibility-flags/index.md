<p>Compatibility flags enable specific features. They can be useful if you want to help the Workers team test upcoming changes that are not yet enabled by default, or if you need to hold back a change that your code depends on but still want to apply other compatibility changes.</p>
<p>Compatibility flags will often have a date in which they are enabled by default, and so, by specifying a <a href="/workers/configuration/compatibility-dates"><code>compatibility_date</code></a> for your Worker, you can quickly enable all of these various compatibility flags up to, and including, that date.</p>
<h2 id="setting-compatibility-flags">Setting compatibility flags</h2>
<p>You may provide a list of <code>compatibility_flags</code>, which enable or disable specific changes.</p>
<h4 id="via-wrangler">Via Wrangler</h4>
<p>Compatibility flags can be set in a Worker's <a href="/workers/wrangler/configuration/">Wrangler configuration file</a>.</p>
<p>This example enables the specific flag <code>formdata_parser_supports_files</code>, which is described <a href="/workers/configuration/compatibility-flags/#formdata-parsing-supports-file">below</a>. As of the specified date, <code>2021-09-14</code>, this particular flag was not yet enabled by default, but, by specifying it in <code>compatibility_flags</code>, we can enable it anyway. <code>compatibility_flags</code> can also be used to disable changes that became the default in the past.</p>

<h4 id="via-the-cloudflare-dashboard">Via the Cloudflare Dashboard</h4>
<p>Compatibility flags can be updated in the Workers settings on the <a href="https://dash.cloudflare.com/">Cloudflare dashboard</a>.</p>
<h4 id="via-the-cloudflare-api">Via the Cloudflare API</h4>
<p>Compatibility flags can be set when uploading a Worker using the <a href="/api/resources/workers/subresources/scripts/methods/update/">Workers Script API</a> or <a href="/api/resources/workers/subresources/scripts/subresources/versions/methods/create/">Workers Versions API</a> in the request body's <code>metadata</code> field.</p>

With this flag enabled, <code>ch.hasSubscribers</code> returns a boolean without a function call, consistent with the <a href="https://nodejs.org/docs/latest/api/diagnostics_channel.html#channelhassubscribers">Node.js documentation</a>.</p>
<p>This flag requires <a href="/workers/runtime-apis/nodejs/"><code>nodejs_compat</code></a> to be enabled.</p>
<h3 id="workflows-preserve-nonretryableerror-message">Workflows preserve `NonRetryableError` message</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-05-14</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>workflows_preserve_non_retryable_error_message</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>workflows_replace_non_retryable_error_message</code></td></tr></tbody></table><p>When enabled, if a <a href="/workflows/">Workflow</a> step throws a <a href="/workflows/build/workers-api/#nonretryableerror"><code>NonRetryableError</code></a>, the error <code>message</code> and <code>name</code> properties are preserved on the thrown exception instead of being replaced with a generic termination string.</p>
<p>Previously, throwing a <code>NonRetryableError</code> with a custom message would result in the original error message being lost and replaced with <code>&quot;The execution of the Workflow instance was terminated, as a step threw an NonRetryableError and it was not handled&quot;</code>:</p>
<pre tabindex="0"><code class="language-js">import { WorkflowEntrypoint, NonRetryableError } from &quot;cloudflare:workers&quot;;&#10;<p>export class MyWorkflow extends WorkflowEntrypoint {&#10;async run(event, step) {&#10;await step.do(&quot;my-step&quot;, async () =&gt; {&#10;throw new NonRetryableError(&quot;custom error message&quot;);&#10;// Without this flag: error.message === &quot;The execution of the Workflow instance was terminated, as a step threw an NonRetryableError and it was not handled&quot;&#10;// With this flag: error.message === &quot;custom error message&quot;&#10;});&#10;}&#10;}&#10;</code></pre></p>
<p>With the <code>workflows_preserve_non_retryable_error_message</code> flag enabled, the original error message and name are preserved, making it easier to debug and handle specific error cases in your Workflow code.</p>
<h3 id="enhanced-error-serialization">Enhanced error serialization</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-04-21</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>enhanced_error_serialization</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>legacy_error_serialization</code></td></tr></tbody></table><p>When <code>enhanced_error_serialization</code> is enabled, errors serialized using <code>structuredClone()</code> or V8 serialization support more error types and include own properties on the error object.</p>

<h3 id="use-an-isolated-pid-namespace-for-containers">Use an isolated PID namespace for containers</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-04-01</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>containers_pid_namespace</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>no_containers_pid_namespace</code></td></tr></tbody></table><p>When <code>containers_pid_namespace</code> is set, containers will use an isolated PID namespace. The <code>ENTRYPOINT</code> of your container will have PID 1.</p>
<p>When unset, the container shares the PID namespace with the virtual machine (VM) containing the container. The <code>ENTRYPOINT</code> of your container will <em>not</em> have PID 1 and other processes running on the VM (that are not part of your container) will be visible.</p>
<h3 id="spec-compliant-textencoderstream-textdecoderstream-backpressure">Spec-compliant TextEncoderStream/TextDecoderStream backpressure</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-03-24</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>encoder_stream_spec_compliant_backpressure</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>no_encoder_stream_spec_compliant_backpressure</code></td></tr></tbody></table><p>When <code>encoder_stream_spec_compliant_backpressure</code> is enabled, <code>TextEncoderStream</code> and <code>TextDecoderStream</code> use a readable-side high water mark of 0, as specified by the <a href="https://encoding.spec.whatwg.org/">WHATWG Encoding Standard</a>.</p>
<p>With a high water mark of 0, the readable side starts with backpressure applied, so writes correctly block until a reader pulls. Previously, the high water mark defaulted to 1, which caused <code>pull()</code> to fire at startup, clearing backpressure before any write occurred.</p>

<h3 id="websocket-auto-reply-to-close">WebSocket auto-reply to close</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-04-07</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>web_socket_auto_reply_to_close</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>web_socket_manual_reply_to_close</code></td></tr></tbody></table><p>When a server sends a WebSocket Close frame, the Workers runtime now automatically sends a reciprocal Close frame and transitions <code>readyState</code> to <code>CLOSED</code> before firing the <code>close</code> event. This matches the <a href="https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/close_event">WebSocket spec</a> and browser behavior.</p>
<p>Previously, receiving a server-initiated Close frame left the WebSocket in <code>CLOSING</code> and required the application to call <code>close()</code> itself. With this flag active, you no longer need to call <code>close()</code> in your <code>close</code> event handler. The runtime handles the close handshake automatically.</p>
<pre tabindex="0"><code class="language-js">const [client, server] = Object.values(new WebSocketPair());&#10;server.accept();&#10;<p>server.addEventListener(&quot;close&quot;, (event) =&gt; {&#10;// readyState is already CLOSED — no need to call server.close().&#10;console.log(server.readyState); // WebSocket.CLOSED&#10;console.log(event.code); // 1000&#10;console.log(event.wasClean); // true&#10;}, { once: true });&#10;</code></pre></p>
<p>If you do still call <code>close()</code> inside the handler, the call is silently ignored. This means existing code that manually replies to Close frames will not break when you update your compatibility date.</p>
<p>The automatic close behavior can interfere with WebSocket proxying. When a Worker proxies between a client and a backend, the old behavior allowed the Worker to observe a backend Close frame without the runtime tearing down the connection, giving the Worker time to coordinate a clean close on the client side. To support this pattern, the <code>accept()</code> method now accepts an option <code>allowHalfOpen</code>. Call <code>ws.accept({ allowHalfOpen: true })</code> to restore the old half-open behavior regardless of the compatibility flag.</p>
<pre tabindex="0"><code class="language-js">const [client, server] = Object.values(new WebSocketPair());&#10;<p>// Opt into half-open mode for proxying&#10;server.accept({ allowHalfOpen: true });</p>&#10;<p>server.addEventListener(&quot;close&quot;, (event) =&gt; {&#10;// With allowHalfOpen true, readyState is still CLOSING here,&#10;// giving you time to coordinate the close on the other side.&#10;console.log(server.readyState); // WebSocket.CLOSING</p>&#10;<p>// Manually close when ready.&#10;server.close(1000, &quot;done&quot;);&#10;}, { once: true });&#10;</code></pre></p>
<p>Note that there is no corresponding option to the <code>WebSocket</code> constructor. WebSockets constructed with <code>new WebSocket</code> will always auto-reply to closes after this flag takes effect. WebSockets constructed this way are automatically &quot;accepted&quot;, so there is no opportunity to pass the option to <code>accept()</code>. If you are creating a WebSocket with <code>new WebSocket</code>, but you need half-open behavior, you will need to switch to using <code>fetch()</code> instead.</p>
<pre tabindex="0"><code class="language-js">// This does not allow half-open:&#10;let ws = new WebSocket(&quot;wss://example.com&quot;);&#10;<p>// But you can do this instead:&#10;let resp = await fetch(&quot;<a href="https://example.com">https://example.com</a>&quot;, {&#10;headers: { &quot;Upgrade&quot;: &quot;websocket&quot; }&#10;});&#10;if (!resp.webSocket) {&#10;throw new Error(&quot;WebSocket handshake not accepted&quot;);&#10;}&#10;let ws = resp.webSocket;&#10;ws.accept({ allowHalfOpen: true });&#10;</code></pre></p>
<p>For more information, refer to the <a href="/workers/runtime-apis/websockets/">WebSocket API documentation</a>.</p>

<h3 id="duplicate-stubs-in-rpc-params-instead-of-transferring-ownership">Duplicate stubs in RPC params instead of transferring ownership</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2026-01-20</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>rpc_params_dup_stubs</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>rpc_params_transfer_stubs</code></td></tr></tbody></table><p>Changes the ownership semantics of RPC stubs embedded in the parameters of an RPC call, fixing compatibility issues with <a href="https://github.com/cloudflare/capnweb">Cap'n Web</a>.</p>
<p>When the <a href="/workers/runtime-apis/rpc/">Workers RPC system</a> was first introduced, RPC stubs that were embedded in the params or return value of some other call had their ownership transferred. That is, the original stub was implicitly disposed, with a duplicate stub being delivered to the destination.</p>
<p>This turns out to compose poorly with another rule: in the callee, any stubs received in the params of a call are automatically disposed when the call returns. These two rules combine to mean that if you proxy a call -- i.e. the implementation of an RPC just makes another RPC call passing along the same params -- then any stubs in the params get disposed twice. Worse, if the eventual recipient of the stub wants to keep a duplicate past the end of the call, this may not work because the copy of the stub in the proxy layer gets disposed anyway, breaking the connection.</p>
<p>For this reason, the pure-JS implementation of Cap'n Web switched to saying that stubs in params do NOT transfer ownership -- they are simply duplicated. This compat flag fixes the Workers Runtime built-in RPC to match Cap'n Web behavior.</p>
<p>One common use case that this fixes is clients that subscribe to callbacks from a Durable Object via Cap'n Web. In this use case, the client app passes a callback function over a Cap'n Web WebSocket to a stateless Worker, which in turn forwards the stub over Workers RPC to a Durable Object. The Durable Object stores a <a href="/workers/runtime-apis/rpc/lifecycle/#the-dup-method"><code>dup()</code></a> of the stub in order to call it back later to notify the client of events. Unfortunately, before this flag, this didn't work: as soon as the subscribe function itself returned, the Cap'n Web stub in the stateless worker would be disposed (because it was a parameter to a call that returned, and it was not <code>dup()</code>ed within the context of the stateless worker). Hence, when the Durable Object later tried to call the subscription callback, it would receive &quot;Error: RPC stub used after being disposed&quot;, despite the fact that it had carefully <code>dup()</code>ed the stub at its end.</p>

<h3 id="minimal-subrequests">Minimal subrequests</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2022-04-05</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>minimal_subrequests</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>no_minimal_subrequests</code></td></tr></tbody></table><p>With the <code>minimal_subrequests</code> flag set, <code>fetch()</code> subrequests sent to endpoints on the Worker's own zone (also called same-zone subrequests) have a reduced set of features applied to them. Specifically, Workers might observe the following behavior changes with the new flag:</p>
<ul>
<li>Response bodies will not be opportunistically gzipped before being transmitted to the Workers runtime. If a Worker reads the response body, it will read it in plaintext, as has always been the case, so disabling this prevents unnecessary decompression. <li>Automatic Platform Optimization may previously have been applied on both the Worker's initiating request and its subrequests in some circumstances. It will now only apply to the initiating request.</li>
<li>Link prefetching will now only apply to the Worker's response, not responses to the Worker's subrequests.</li>
</ul>

<h3 id="durable-object-stub-fetch-requires-a-full-url">Durable Object `stub.fetch()` requires a full URL</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2021-11-10</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>durable_object_fetch_requires_full_url</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>durable_object_fetch_allows_relative_url</code></td></tr></tbody></table><p>Originally, when making a request to a Durable Object by calling <code>stub.fetch(url)</code>, a relative URL was accepted as an input. <h3 id="fetch-improperly-interprets-unknown-protocols-as-http">`fetch()` improperly interprets unknown protocols as HTTP</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2021-11-10</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>fetch_refuses_unknown_protocols</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>fetch_treats_unknown_protocols_as_http</code></td></tr></tbody></table><p>Originally, if the <code>fetch()</code> function was passed a URL specifying any protocol other than <code>http:</code> or <code>https:</code>, it would silently treat it as if it were <code>http:</code>. For example, <code>fetch()</code> would appear to accept <code>ftp:</code> URLs, but it was actually making HTTP requests instead.</p>
<p>Note that Cloudflare Workers supports a non-standard extension to <code>fetch()</code> to make it support WebSockets. However, when making an HTTP request that is intended to initiate a WebSocket handshake, you should still use <code>http:</code> or <code>https:</code> as the protocol, not <code>ws:</code> nor <code>wss:</code>.</p>
<p>The <code>ws:</code> and <code>wss:</code> URL schemes are intended to be used together with the <code>new WebSocket()</code> constructor, which exclusively supports WebSocket. The extension to <code>fetch()</code> is designed to support HTTP and WebSocket in the same request (the response may or may not choose to initiate a WebSocket), and so all requests are considered to be HTTP.</p>
<h3 id="streams-byob-reader-detaches-buffer">Streams BYOB reader detaches buffer</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2021-11-10</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>streams_byob_reader_detaches_buffer</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>streams_byob_reader_does_not_detach_buffer</code></td></tr></tbody></table><p>Originally, the Workers runtime did not detach the <code>ArrayBuffer</code>s from user-provided TypedArrays when using the <a href="/workers/runtime-apis/streams/readablestreambyobreader/#methods">BYOB reader's <code>read()</code> method</a>, as required by the Streams spec, meaning it was possible to inadvertently reuse the same buffer for multiple <code>read()</code> calls. This change makes Workers conform to the spec.</p>
<p>User code should never try to reuse an <code>ArrayBuffer</code> that has been passed into a <a href="/workers/runtime-apis/streams/readablestreambyobreader/#methods">BYOB reader's <code>read()</code> method</a>. Instead, user code can reuse the <code>ArrayBuffer</code> backing the result of the <code>read()</code> promise, as in the example below.</p>
<pre tabindex="0"><code class="language-js">// Consume and discard `readable` using a single 4KiB buffer.&#10;let reader = readable.getReader({ mode: &quot;byob&quot; });&#10;let arrayBufferView = new Uint8Array(4096);&#10;while (true) {&#10;  let result = await reader.read(arrayBufferView);&#10;  if (result.done) break;&#10;  // Optionally something with `result` here.&#10;  // Re-use the same memory for the next `read()` by creating&#10;  // a new Uint8Array backed by the result&#x27;s ArrayBuffer.&#10;  arrayBufferView = new Uint8Array(result.value.buffer);&#10;}&#10;</code></pre>
<p>The more recently added extension method <code>readAtLeast()</code> will always detach the <code>ArrayBuffer</code> and is unaffected by this feature flag setting.</p>
<h3 id="formdata-parsing-supports-file">`FormData` parsing supports `File`</h3><table><tbody><tr><td><strong>Default as of</strong></td><td><code>2021-11-03</code></td></tr><tr><td><strong>Flag to enable</strong></td><td><code>formdata_parser_supports_files</code></td></tr><tr><td><strong>Flag to disable</strong></td><td><code>formdata_parser_converts_files_to_strings</code></td></tr></tbody></table><p><a href="https://developer.mozilla.org/en-US/docs/Web/API/FormData">The <code>FormData</code> API</a> is used to parse data (especially HTTP request bodies) in <code>multipart/form-data</code> format.</p>
<p>Originally, the Workers runtime's implementation of the <code>FormData</code> API incorrectly converted uploaded files to strings. Therefore, <code>formData.get(&quot;filename&quot;)</code> would return a string containing the file contents instead of a <code>File</code> object. This change fixes the problem, causing files to be represented using <code>File</code> as specified in the standard.</p>
<h3 id="htmlrewriter-handling-of-esi-include">`HTMLRewriter` handling of `&lt;esi:include&gt;`</h3><table><tbody><tr><td><strong>Flag to enable</strong></td><td><code>html_rewriter_treats_esi_include_as_void_tag</code></td></tr></tbody></table><p>The HTML5 standard defines a fixed set of elements as void elements, meaning they do not use an end tag: <code>&lt;area&gt;</code>, <code>&lt;base&gt;</code>, <code>&lt;br&gt;</code>, <code>&lt;col&gt;</code>, <code>&lt;command&gt;</code>, <code>&lt;embed&gt;</code>, <code>&lt;hr&gt;</code>, <code>&lt;img&gt;</code>, <code>&lt;input&gt;</code>, <code>&lt;keygen&gt;</code>, <code>&lt;link&gt;</code>, <code>&lt;meta&gt;</code>, <code>&lt;param&gt;</code>, <code>&lt;source&gt;</code>, <code>&lt;track&gt;</code>, and <code>&lt;wbr&gt;</code>.</p>
<p>HTML5 does not recognize XML self-closing tag syntax. For example, <code>&lt;script src=&quot;foo.js&quot; /&gt;</code> does not specify a script element with no body. A <code>&lt;/script&gt;</code> ending tag is still required. The <code>/&gt;</code> syntax simply is not recognized by HTML5 at all and it is treated the same as <code>&gt;</code>. However, many developers still like to use this syntax, as a holdover from XHTML, a standard which failed to gain traction in the early 2000's.</p>
<p><code>&lt;esi:include&gt;</code> and <code>&lt;esi:comment&gt;</code> are two tags that are not part of the HTML5 standard, but are instead used as part of <a href="https://en.wikipedia.org/wiki/Edge_Side_Includes">Edge Side Includes</a>, a technology for server-side HTML modification. These tags are not expected to contain any body and are commonly written with XML self-closing syntax.</p>
<p><code>HTMLRewriter</code> was designed to parse standard HTML5, not ESI. However, it would be useful to be able to implement some parts of ESI using <code>HTMLRewriter</code>. To that end, this compatibility flag causes <code>HTMLRewriter</code> to treat <code>&lt;esi:include&gt;</code> and <code>&lt;esi:comment&gt;</code> as void tags, so that they can be parsed and handled properly.</p>
<h2 id="experimental-flags">Experimental flags</h2>
<p>These flags can be enabled via <code>compatibility_flags</code>, but are not yet scheduled to become default on any particular date.</p>
<h3 id="queue-consumers-don-t-wait-for-ctx-waituntil-to-resolve-1">Queue consumers don&#x27;t wait for `ctx.waitUntil()` to resolve</h3><table><tbody><tr><td><strong>Flag to enable</strong></td><td><code>queue_consumer_no_wait_for_wait_until</code></td></tr></tbody></table><p>By default, <a href="/queues/">Queues</a> Consumer Workers acknowledge messages only after promises passed to <a href="/workers/runtime-apis/context"><code>ctx.waitUntil()</code></a> have resolved. This behavior can cause queue consumers which utilize <code>ctx.waitUntil()</code> to process messages slowly. The default behavior is documented in the <a href="/queues/configuration/javascript-apis#consumer">Queues Consumer Configuration Guide</a>.</p>
<p>This Consumer Worker is an example of a Worker which utilizes <code>ctx.waitUntil()</code>. Under the default behavior, this consumer Worker will only acknowledge a batch of messages after the sleep function has resolved.</p>
<pre tabindex="0"><code class="language-js">export default {&#10;  async fetch(request, env, ctx) {&#10;    // omitted&#10;  },&#10;<p>async queue(batch, env, ctx) {&#10;console.log(<code>received batch of ${batch.messages.length} messages to queue ${batch.queue}</code>);&#10;for (let i = 0; i &lt; batch.messages.length; ++i) {&#10;console.log(<code>message #${i}: ${JSON.stringify(batch.messages[i])}</code>);&#10;}&#10;ctx.waitUntil(sleep(30 * 1000));&#10;}&#10;};</p>&#10;<p>function sleep(ms) {&#10;return new Promise(resolve =&gt; setTimeout(resolve, ms));&#10;}&#10;</code></pre></p>
<p>If the <code>queue_consumer_no_wait_for_wait_until</code> flag is enabled, Queues consumers will no longer wait for promises passed to <code>ctx.waitUntil()</code> to resolve before acknowledging messages. This can improve the performance of queue consumers which utilize <code>ctx.waitUntil()</code>. With the flag enabled, in the above example, the consumer Worker will acknowledge the batch without waiting for the sleep function to resolve.</p>
<p>Using this flag will not affect the behavior of <code>ctx.waitUntil()</code>. <code>ctx.waitUntil()</code> will continue to extend the lifetime of your consumer Worker to continue to work even after the batch of messages has been acknowledged.</p>
