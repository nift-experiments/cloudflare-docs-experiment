<h3 id="loop-limit">Loop limit</h3>
<p>A Worker cannot call itself or another Worker more than 16 times. In order to prevent infinite loops between Workers, the <a href="/fundamentals/reference/http-headers/#cf-ew-via"><code>CF-EW-Via</code></a> header's value is an integer that indicates how many invocations are left. Every time a Worker is invoked, the integer will decrement by 1. If the count reaches zero, a <a href="#error-pages-generated-by-workers"><code>1019</code></a> error is returned.</p>
<h3 id="the-script-will-never-generate-a-response-errors">&quot;The script will never generate a response&quot; errors</h3>
<p>Some requests may return a 1101 error with <code>The script will never generate a response</code> in the error message. This occurs when the Workers runtime detects that all the code associated with the request has executed and no events are left in the event loop, but a Response has not been returned.</p>
<h4 id="cause-1-unresolved-promises">Cause 1: Unresolved Promises</h4>
<p>This is most commonly caused by relying on a Promise that is never resolved or rejected, which is required to return a Response. To debug, look for Promises within your code or dependencies' code that block a Response, and ensure they are resolved or rejected.</p>
<p>In browsers and other JavaScript runtimes, equivalent code will hang indefinitely, leading to both bugs and memory leaks. The Workers runtime throws an explicit error to help you debug.</p>
<p>In the example below, the Response relies on a Promise resolution that never happens. Uncommenting the <code>resolve</code> callback solves the issue.</p>
<pre tabindex="0"><code class="language-js">export default {&#10;	fetch(req) {&#10;		let response = new Response(&quot;Example response&quot;);&#10;		let { promise, resolve } = Promise.withResolvers();&#10;&#10;		// If the promise is not resolved, the Workers runtime will&#10;		// recognize this and throw an error.&#10;&#10;		// setTimeout(resolve, 0)&#10;&#10;		return promise.then(() =&gt; response);&#10;	},&#10;};&#10;</code></pre>
<p>You can prevent this by enforcing the <a href="https://typescript-eslint.io/rules/no-floating-promises/"><code>no-floating-promises</code> eslint rule</a>, which reports when a Promise is created and not properly handled.</p>
<h4 id="cause-2-websocket-connections-that-are-never-closed">Cause 2: WebSocket connections that are never closed</h4>
<p>If a WebSocket is missing the proper code to close its server-side connection, the Workers runtime will throw a <code>script will never generate a response</code> error. In the example below, the <code>'close'</code> event from the client is not properly handled by calling <code>server.close()</code>, and the error is thrown. In order to avoid this, ensure that the WebSocket's server-side connection is properly closed via an event listener or other server-side logic.</p>

<h3 id="illegal-invocation-errors">&quot;Illegal invocation&quot; errors</h3>
<p>The error message <code>TypeError: Illegal invocation: function called with incorrect this reference</code> can be a source of confusion.</p>
<p>This is typically caused by calling a function that calls <code>this</code>, but the value of <code>this</code> has been lost.</p>
<p>For example, given an <code>obj</code> object with the <code>obj.foo()</code> method which logic relies on <code>this</code>, executing the method via <code>obj.foo();</code> will make sure that <code>this</code> properly references the <code>obj</code> object. However, assigning the method to a variable, e.g.<code>const func = obj.foo;</code> and calling such variable, e.g. <code>func();</code> would result in <code>this</code> being <code>undefined</code>. This is because <code>this</code> is lost when the method is called as a standalone function. This is standard behavior in JavaScript.</p>
<p>In practice, this is often seen when destructuring runtime provided Javascript objects that have functions that rely on the presence of <code>this</code>, such as <code>ctx</code>.</p>
<p>The following code will error:</p>
<pre tabindex="0"><code class="language-js">export default {&#10;	async fetch(request, env, ctx) {&#10;		// destructuring ctx makes waitUntil lose its &#x27;this&#x27; reference&#10;		const { waitUntil } = ctx;&#10;		// waitUntil errors, as it has no &#x27;this&#x27;&#10;		waitUntil(somePromise);&#10;&#10;		return fetch(request);&#10;	},&#10;};&#10;</code></pre>
<p>Avoid destructuring or re-bind the function to the original context to avoid the error.</p>
<p>The following code will run properly:</p>
<pre tabindex="0"><code class="language-js">export default {&#10;	async fetch(request, env, ctx) {&#10;		// directly calling the method on ctx avoids the error&#10;		ctx.waitUntil(somePromise);&#10;&#10;		// alternatively re-binding to ctx via apply, call, or bind avoids the error&#10;		const { waitUntil } = ctx;&#10;		waitUntil.apply(ctx, [somePromise]);&#10;		waitUntil.call(ctx, somePromise);&#10;		const reboundWaitUntil = waitUntil.bind(ctx);&#10;		reboundWaitUntil(somePromise);&#10;&#10;		return fetch(request);&#10;	},&#10;};&#10;</code></pre>
<h3 id="cannot-perform-i-o-on-behalf-of-a-different-request">Cannot perform I/O on behalf of a different request</h3>
<pre tabindex="0"><code>Uncaught (in promise) Error: Cannot perform I/O on behalf of a different request. I/O objects (such as streams, request/response bodies, and others) created in the context of one request handler cannot be accessed from a different request&#x27;s handler.&#10;</code></pre>
<p>This error occurs when you attempt to share input/output (I/O) objects (such as streams, requests, or responses) created by one invocation of your Worker in the context of a different invocation.</p>
<p>In Cloudflare Workers, each invocation is handled independently and has its own execution context. This design ensures optimal performance and security by isolating requests from one another. When you try to share I/O objects between different invocations, you break this isolation. Since these objects are tied to the specific request they were created in, accessing them from another request's handler is not allowed and leads to the error.</p>
<p>This error is most commonly caused by attempting to cache an I/O object, like a <a href="/workers/runtime-apis/request/">Request</a> in global scope, and then access it in a subsequent request. For example, if you create a Worker and run the following code in local development, and make two requests to your Worker in quick succession, you can reproduce this error:</p>
<pre tabindex="0"><code class="language-js">let cachedResponse = null;&#10;&#10;export default {&#10;	async fetch(request, env, ctx) {&#10;		if (cachedResponse) {&#10;			return cachedResponse;&#10;		}&#10;		cachedResponse = new Response(&quot;Hello, world!&quot;);&#10;		await new Promise((resolve) =&gt; setTimeout(resolve, 5000)); // Sleep for 5s to demonstrate this particular error case&#10;		return cachedResponse;&#10;	},&#10;};&#10;</code></pre>
<p>You can fix this by instead storing only the data in global scope, rather than the I/O object itself:</p>
<pre tabindex="0"><code class="language-js">let cachedData = null;&#10;&#10;export default {&#10;	async fetch(request, env, ctx) {&#10;		if (cachedData) {&#10;			return new Response(cachedData);&#10;		}&#10;		const response = new Response(&quot;Hello, world!&quot;);&#10;		cachedData = await response.text();&#10;		return new Response(cachedData, response);&#10;	},&#10;};&#10;</code></pre>
<p>If you need to share state across requests, consider using <a href="/durable-objects/">Durable Objects</a>. If you need to cache data across requests, consider using <a href="/kv/">Workers KV</a>.</p>

<h3 id="validation-errors-10021">Validation Errors (10021)</h3>
<p>The 10021 error code includes all errors that occur when you attempt to deploy a Worker, and Cloudflare then attempts to load and run the top-level scope (everything that happens before your Worker's <a href="/workers/runtime-apis/handlers/">handler</a> is invoked). For example, if you attempt to deploy a broken Worker with invalid JavaScript that would throw a <code>SyntaxError</code> — Cloudflare will not deploy your Worker.</p>
<p>Specific error cases include but are not limited to:</p>
<h4 id="script-startup-exceeded-cpu-time-limit">Script startup exceeded CPU time limit</h4>
<p>This means that you are doing work in the top-level scope of your Worker that takes more than the <a href="/workers/platform/limits/#worker-startup-time">startup time limit (1s)</a> of CPU time.</p>
<h4 id="script-startup-exceeded-memory-limit">Script startup exceeded memory limit</h4>
<p>This means that you are doing work in the top-level scope of your Worker that allocates more than the <a href="/workers/platform/limits/#memory">memory limit (128 MB)</a> of memory.</p>

<h2 id="debug-exceptions-with-workers-logs">Debug exceptions with Workers Logs</h2>
<p><a href="/workers/observability/logs/workers-logs">Workers Logs</a> is a powerful tool for debugging your Workers. It shows all the historic logs generated by your Worker, including any uncaught exceptions that occur during execution.</p>
<p>To find all your errors in Workers Logs, you can use the following filter: <code>$metadata.error EXISTS</code>. This will show all the logs that have an error associated with them. You can also filter by <code>$workers.outcome</code> to find the requests that resulted in an error. For example, you can filter by <code>$workers.outcome = &quot;exception&quot;</code> to find all the requests that resulted in an uncaught exception.</p>
<p>All the possible outcome values can be found in the <a href="/logs/logpush/logpush-job/datasets/account/workers_trace_events/#outcome">Workers Trace Event</a> reference.</p>
<h2 id="debug-exceptions-from-wrangler">Debug exceptions from <code>Wrangler</code></h2>
<p>To debug your worker via wrangler use <code>wrangler tail</code> to inspect and fix the exceptions.</p>
<p>Exceptions will show up under the <code>exceptions</code> field in the JSON returned by <code>wrangler tail</code>. After you have identified the exception that is causing errors, redeploy your code with a fix, and continue tailing the logs to confirm that it is fixed.</p>
<h2 id="set-up-a-3rd-party-logging-service">Set up a 3rd party logging service</h2>
<p>A Worker can make HTTP requests to any HTTP service on the public Internet. You can use a service like <a href="https://sentry.io">Sentry</a> to collect error logs from your Worker, by making an HTTP request to the service to report the error. Refer to your service’s API documentation for details on what kind of request to make.</p>

<h2 id="go-to-origin-on-error">Go to origin on error</h2>
<p>By using <a href="/workers/runtime-apis/context/#passthroughonexception"><code>passThroughOnException()</code></a>, a Workers application can forward requests to your origin if an exception is thrown during the Worker's execution. This allows you to add logging, tracking, or other features with Workers, without degrading your application's functionality.</p>
<p><code>ctx.passThroughOnException()</code> forwards requests for unhandled exceptions in your Worker code, not for errors from the origin <code>fetch()</code>. When proxying requests to an origin, wrap <code>fetch(request)</code> in <code>try...catch</code> and return a <code>5xx</code> response on failure. If the origin <code>fetch()</code> throws after consuming the request body, <code>passThroughOnException()</code> cannot replay the body.</p>
