<h2 id="lifetimes-memory-and-resource-management">Lifetimes, Memory and Resource Management</h2>
<p>When you call another Worker over RPC using a Service binding, you are using memory in the Worker you are calling. Consider the following example:</p>
<pre tabindex="0"><code class="language-js">let user = await env.USER_SERVICE.findUser(id);&#10;</code></pre>
<p>Assume that <code>findUser()</code> on the server side returns an object extending <code>RpcTarget</code>, thus <code>user</code> on the client side ends up being a stub pointing to that remote object.</p>
<p>As long as the stub still exists on the client, the corresponding object on the server cannot be garbage collected. But, each isolate has its own garbage collector which cannot see into other isolates. So, in order for the server's isolate to know that the object can be collected, the calling isolate must send it an explicit signal saying so, called &quot;disposing&quot; the stub.</p>
<p>In many cases (described below), the system will automatically realize when a stub is no longer needed, and will dispose it automatically. However, for best performance, your code should dispose stubs explicitly when it is done with them.</p>
<h2 id="explicit-resource-management">Explicit Resource Management</h2>
<p>To ensure resources are properly disposed of, you should use <a href="https://github.com/tc39/proposal-explicit-resource-management">Explicit Resource Management</a>, a new JavaScript language feature that allows you to explicitly signal when resources can be disposed of. Explicit Resource Management is a Stage 3 TC39 proposal — it is <a href="https://bugs.chromium.org/p/v8/issues/detail?id=13559">coming to V8 soon</a>.</p>
<p>Explicit Resource Management adds the following language features:</p>
<ul>
<li>The <a href="https://github.com/tc39/proposal-explicit-resource-management?tab=readme-ov-file#using-declarations"><code>using</code> declaration</a></li>
<li><a href="https://github.com/tc39/proposal-explicit-resource-management?tab=readme-ov-file#additions-to-symbol"><code>Symbol.dispose</code> and <code>Symbol.asyncDispose</code></a></li>
</ul>
<p>If a variable is declared with <code>using</code>, when the variable is no longer in scope, the variable's disposer will be invoked. For example:</p>
<pre tabindex="0"><code class="language-js">function sendEmail(id, message) {&#10;  using user = await env.USER_SERVICE.findUser(id);&#10;  await user.sendEmail(message);&#10;&#10;  // user[Symbol.dispose]() is implicitly called at the end of the scope.&#10;}&#10;</code></pre>
<p><code>using</code> declarations are useful to make sure you can't forget to dispose stubs — even if your code is interrupted by an exception.</p>
<h3 id="how-to-use-the-using-declaration-in-your-worker">How to use the <code>using</code> declaration in your Worker</h3>
<p><a href="/workers/wrangler/">Wrangler</a> v4+ supports the <code>using</code> keyword natively. If you are using an earlier version of Wrangler, you will need to manually dispose of resources instead.</p>
<p>The following code:</p>
<pre tabindex="0"><code class="language-js">{&#10;	using counter = await env.COUNTER_SERVICE.newCounter();&#10;	await counter.increment(2);&#10;	await counter.increment(4);&#10;}&#10;</code></pre>
<p>...is equivalent to:</p>
<pre tabindex="0"><code class="language-js">{&#10;	const counter = await env.COUNTER_SERVICE.newCounter();&#10;	try {&#10;		await counter.increment(2);&#10;		await counter.increment(4);&#10;	} finally {&#10;		counter[Symbol.dispose]();&#10;	}&#10;}&#10;</code></pre>
<h2 id="automatic-disposal-and-execution-contexts">Automatic disposal and execution contexts</h2>
<p>The RPC system automatically disposes of stubs in the following cases:</p>
<h3 id="end-of-event-handler-execution-context">End of event handler / execution context</h3>
<p>When an event handler is &quot;done&quot;, any stubs created as part of the event are automatically disposed.</p>
<p>For example, consider a <a href="/workers/runtime-apis/handlers/fetch"><code>fetch()</code> handler</a> which handles incoming HTTP events. The handler may make outgoing RPCs as part of handling the event, and those may return stubs. When the final HTTP response is sent, the handler is &quot;done&quot;, and all stubs are immediately disposed.</p>
<p>More precisely, the event has an &quot;execution context&quot;, which begins when the handler is first invoked, and ends when the HTTP response is sent. The execution context may also end early if the client disconnects before receiving a response, or it can be extended past its normal end point by calling <a href="/workers/runtime-apis/context"><code>ctx.waitUntil()</code></a>.</p>
<p>For example, the Worker below does not make use of the <code>using</code> declaration, but stubs will be disposed of once the <code>fetch()</code> handler returns a response:</p>
<pre tabindex="0"><code class="language-js">export default {&#10;	async fetch(request, env, ctx) {&#10;		let authResult = await env.AUTH_SERVICE.checkCookie(&#10;			req.headers.get(&quot;Cookie&quot;),&#10;		);&#10;		if (!authResult.authorized) {&#10;			return new Response(&quot;Not authorized&quot;, { status: 403 });&#10;		}&#10;		let profile = await authResult.user.getProfile();&#10;&#10;		return new Response(`Hello, ${profile.name}!`);&#10;	},&#10;};&#10;</code></pre>
<p>A Worker invoked via RPC also has an execution context. The context begins when an RPC method on a <code>WorkerEntrypoint</code> is invoked. If no stubs are passed in the parameters or results of this RPC, the context ends (the event is &quot;done&quot;) when the RPC returns. However, if any stubs are passed, then the execution context is implicitly extended until all such stubs are disposed (and all calls made through them have returned). As with HTTP, if the client disconnects, the server's execution context is canceled immediately, regardless of whether stubs still exist. A client that is itself another Worker is considered to have disconnected when its own execution context ends. Again, the context can be extended with <a href="/workers/runtime-apis/context"><code>ctx.waitUntil()</code></a>.</p>
<h3 id="stubs-received-as-parameters-in-an-rpc-call">Stubs received as parameters in an RPC call</h3>
<p>When stubs are received in the parameters of an RPC, those stubs are automatically disposed when the call returns. If you wish to keep the stubs longer than that, you must call the <code>dup()</code> method on them.</p>
<h3 id="disposing-rpc-objects-disposes-stubs-that-are-part-of-that-object">Disposing RPC objects disposes stubs that are part of that object</h3>
<p>When an RPC returns any kind of object, that object will have a disposer added by the system. Disposing it will dispose all stubs returned by the call. For instance, if an RPC returns an array of four stubs, the array itself will have a disposer that disposes all four stubs. The only time the value returned by an RPC does not have a disposer is when it is a primitive value, such as a number or string. These types cannot have disposers added to them, but because these types cannot themselves contain stubs, there is no need for a disposer in this case.</p>
<p>This means you should almost always store the result of an RPC into a <code>using</code> declaration:</p>
<pre tabindex="0"><code class="language-js">using result = stub.foo();&#10;</code></pre>
<p>This way, if the result contains any stubs, they will be disposed of. Even if you don't expect the RPC to return stubs, if it returns any kind of an object, it is a good idea to store it into a <code>using</code> declaration. This way, if the RPC is extended in the future to return stubs, your code is ready.</p>
<p>If you decide you want to keep a returned stub beyond the scope of the <code>using</code> declaration, you can call <code>dup()</code> on the stub before the end of the scope. (Remember to explicitly dispose the duplicate later.)</p>
<h2 id="disposers-and-rpctarget-classes">Disposers and <code>RpcTarget</code> classes</h2>
<p>A class that extends <a href="/workers/runtime-apis/rpc/"><code>RpcTarget</code></a> can optionally implement a disposer:</p>
<pre tabindex="0"><code class="language-js">class Foo extends RpcTarget {&#10;	[Symbol.dispose]() {&#10;		// ...&#10;	}&#10;}&#10;</code></pre>
<p>The RpcTarget's disposer runs after the last stub is disposed. Note that the client-side call to the stub's disposer does not wait for the server-side disposer to be called; the server's disposer is called later on. Because of this, any exceptions thrown by the disposer do not propagate to the client; instead, they are reported as uncaught exceptions. Note that an <code>RpcTarget</code>'s disposer must be declared as <code>Symbol.dispose</code>. <code>Symbol.asyncDispose</code> is not supported.</p>
<h2 id="the-dup-method">The <code>dup()</code> method</h2>
<p>Sometimes, you need to pass a stub to a function which will dispose the stub when it is done, but you also want to keep the stub for later use. To solve this problem, you can &quot;dup&quot; the stub:</p>
<pre tabindex="0"><code class="language-js">let stub = await env.SOME_SERVICE.getThing();&#10;&#10;// Create a duplicate.&#10;let stub2 = stub.dup();&#10;&#10;// Call some function that will dispose the stub.&#10;await func(stub);&#10;&#10;// stub2 is still valid&#10;</code></pre>
<p>You can think of <code>dup()</code> like the <a href="https://man7.org/linux/man-pages/man2/dup.2.html">Unix system call of the same name</a>: it creates a new handle pointing at the same target, which must be independently closed (disposed).</p>
<p>If the instance of the <a href="/workers/runtime-apis/rpc/"><code>RpcTarget</code> class</a> that the stubs point to has a disposer, the disposer will only be invoked when all duplicates have been disposed. However, this only applies to duplicates that originate from the same stub. If the same instance of <code>RpcTarget</code> is passed over RPC multiple times, a new stub is created each time, and these are not considered duplicates of each other. Thus, the disposer will be invoked once for each time the <code>RpcTarget</code> was sent.</p>
<p>In order to avoid this situation, you can manually create a stub locally, and then pass the stub across RPC multiple times. When passing a stub over RPC, ownership of the stub transfers to the recipient, so you must make a <code>dup()</code> for each time you send it:</p>
<pre tabindex="0"><code class="language-js">import { RpcTarget, RpcStub } from &quot;cloudflare:workers&quot;;&#10;&#10;class Foo extends RpcTarget {&#10;	// ...&#10;}&#10;&#10;let obj = new Foo();&#10;let stub = new RpcStub(obj);&#10;await rpc1(stub.dup()); // sends a dup of `stub`&#10;await rpc2(stub.dup()); // sends another dup of `stub`&#10;stub[Symbol.dispose](); // disposes the original stub&#10;&#10;// obj&#x27;s disposer will be called when the other two stubs&#10;// are disposed remotely.&#10;</code></pre>
