<p>Static Site Generation (SSG) applications are web applications which are predominantly built or &quot;prerendered&quot; ahead-of-time. They are often built with a framework such as <a href="/workers/framework-guides/web-apps/more-web-frameworks/gatsby/">Gatsby</a> or <a href="/workers/framework-guides/web-apps/more-web-frameworks/docusaurus/">Docusaurus</a>. The build process of these frameworks will produce many HTML files and accompanying client-side resources (e.g. JavaScript bundles, CSS stylesheets, images, fonts, etc.). Data is either static, fetched and compiled into the HTML at build-time, or fetched by the client from an API with client-side requests.</p>
<p>Often, an SSG framework will allow you to create a custom 404 page.</p>
<h2 id="configuration">Configuration</h2>
<p>In order to deploy a Static Site Generation application to Workers, you must configure the <code>assets.directory</code>, and optionally, the <code>assets.not_found_handling</code> and <code>assets.html_handling</code> options in your <a href="/workers/wrangler/configuration/#assets">Wrangler configuration file</a>:</p>
<div class="nb-wrangler-config">
@markup("md", "content/.markup/bodies/17277.md")
</div>
<p><code>assets.html_handling</code> defaults to <code>auto-trailing-slash</code> and this will usually give you the desired behavior automatically: individual files (e.g. <code>foo.html</code>) will be served <em>without</em> a trailing slash and folder index files (e.g. <code>foo/index.html</code>) will be served <em>with</em> a trailing slash. Alternatively, you can force trailing slashes (<code>force-trailing-slash</code>) or drop trailing slashes (<code>drop-trailing-slash</code>) on requests for HTML pages.</p>
<h3 id="custom-404-pages">Custom 404 pages</h3>
<p>Configuring <code>assets.not_found_handling</code> to <code>404-page</code> overrides the default serving behavior of Workers for static assets. When an incoming request does not match a file in the <code>assets.directory</code>, Workers will serve the contents of the nearest <code>404.html</code> file with a <code>404 Not Found</code> status.</p>
<h3 id="navigation-requests">Navigation requests</h3>
<p>If you have a Worker script (<code>main</code>), have configured <code>assets.not_found_handling</code>, and use the <a href="/workers/configuration/compatibility-flags/#navigation-requests-prefer-asset-serving"><code>assets_navigation_prefers_asset_serving</code> compatibility flag</a> (or set a compatibility date of <code>2025-04-01</code> or greater), <em>navigation requests</em> will not invoke the Worker script. A <em>navigation request</em> is a request made with the <code>Sec-Fetch-Mode: navigate</code> header, which browsers automatically attach when navigating to a page. This reduces billable invocations of your Worker script, and is particularly useful for client-heavy applications which would otherwise invoke your Worker script very frequently and unnecessarily.</p>

<h4 id="client-side-callbacks">Client-side callbacks</h4>
<p>In some cases, you might need to pass a value from a navigation request to your Worker script. For example, if you are acting as an OAuth callback, you might expect to see requests made to some route such as <code>/oauth/callback?code=...</code>. With the <code>assets_navigation_prefers_asset_serving</code> flag, your HTML assets will be server, rather than your Worker script. In this case, we recommend, either as part of your client application for this appropriate route, or with a slimmed-down endpoint-specific HTML file, passing the value to the server with client-side JavaScript.</p>
