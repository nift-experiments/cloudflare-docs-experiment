<p>This guide will show you how to set up <a href="/workers/testing/miniflare">Miniflare</a> to test your Workers. Miniflare is a low-level API that allows you to fully control how your Workers are run and tested.</p>
<p>To use Miniflare, make sure you've installed the latest version of Miniflare v3:</p>

<p>The rest of this guide demonstrates concepts with the <a href="https://nodejs.org/api/test.html"><code>node:test</code></a> testing framework, but any testing framework can be used.</p>
<p>Miniflare is a low-level API that exposes a large variety of configuration options for running your Worker. In most cases, your tests will only need a subset of the available options, but you can refer to the <a href="/workers/testing/miniflare/get-started/#reference">full API reference</a> to explore what is possible with Miniflare.</p>
<p>Before writing a test, you will need to create a Worker. Since Miniflare is a low-level API that emulates the Cloudflare platform primitives, your Worker will need to be written in JavaScript or you'll need to <a href="#custom-builds">integrate your own build pipeline</a> into your testing setup. Here's an example JavaScript-only Worker:</p>
<pre><code class="language-js">export default {&#10;	async fetch(request) {&#10;		return new Response(`Hello World`);&#10;	},&#10;};&#10;</code></pre>
<p>Next, you will need to create an initial test file:</p>
<pre><code class="language-js">import assert from &quot;node:assert&quot;;&#10;import test, { after, before, describe } from &quot;node:test&quot;;&#10;import { Miniflare } from &quot;miniflare&quot;;&#10;&#10;describe(&quot;worker&quot;, () =&gt; {&#10;	/**&#10;	 &#42; @type {Miniflare}&#10;	 &#42;/&#10;	let worker;&#10;&#10;	before(async () =&gt; {&#10;		worker = new Miniflare({&#10;			modules: [&#10;				{&#10;					type: &quot;ESModule&quot;,&#10;					path: &quot;src/index.js&quot;,&#10;				},&#10;			],&#10;		});&#10;		await worker.ready;&#10;	});&#10;&#10;	test(&quot;hello world&quot;, async () =&gt; {&#10;		assert.strictEqual(&#10;			await (await worker.dispatchFetch(&quot;http://example.com&quot;)).text(),&#10;			&quot;Hello World&quot;,&#10;		);&#10;	});&#10;&#10;	after(async () =&gt; {&#10;		await worker.dispose();&#10;	});&#10;});&#10;</code></pre>
<p>You should be able to run the above test via <code>node --test</code></p>
<p>The highlighted lines of the test file above demonstrate how to set up Miniflare to run a JavaScript Worker. Once Miniflare has been set up, your individual tests can send requests to the running Worker and assert against the responses. This is the main limitation of using Miniflare for testing your Worker as compared to the <a href="/workers/testing/vitest-integration/">Vitest integration</a> — all access to your Worker must be through the <code>dispatchFetch()</code> Miniflare API, and you cannot unit test individual functions from your Worker.</p>

<h2 id="interacting-with-bindings">Interacting with Bindings</h2>
<aside class="nb-aside caution">
@markup("md", "content/.markup/bodies/17358.md")
</aside>
<p>The <code>dispatchFetch()</code> API from Miniflare allows you to send requests to your Worker and assert that the correct response is returned, but sometimes you need to interact directly with bindings in tests. For use cases like that, Miniflare provides the <a href="/workers/testing/miniflare/get-started/#reference"><code>getBindings()</code></a> API. For instance, to access an environment variable in your tests, adapt the test file <code>src/index.test.js</code> as follows:</p>
<pre><code class="language-diff">...&#10;describe(&quot;worker&quot;, () =&gt; {&#10;	...&#10;	before(async () =&gt; {&#10;		worker = new Miniflare({&#10;			...&#10;&#43;			bindings: {&#10;&#43;				FOO: &quot;Hello Bindings&quot;,&#10;&#43;			},&#10;		});&#10;		...&#10;	});&#10;&#10;	test(&quot;text binding&quot;, async () =&gt; {&#10;		const bindings = await worker.getBindings();&#10;		assert.strictEqual(bindings.FOO, &quot;Hello Bindings&quot;);&#10;	});&#10;	...&#10;});&#10;</code></pre>
<p>You can also interact with local resources such as KV and R2 using the same API as you would from a Worker. For example, here's how you would interact with a KV namespace:</p>
<pre><code class="language-diff">...&#10;describe(&quot;worker&quot;, () =&gt; {&#10;	...&#10;	before(async () =&gt; {&#10;		worker = new Miniflare({&#10;			...&#10;&#43;			kvNamespaces: [&quot;KV&quot;],&#10;		});&#10;		...&#10;	});&#10;&#10;	test(&quot;kv binding&quot;, async () =&gt; {&#10;		const bindings = await worker.getBindings();&#10;		await bindings.KV.put(&quot;key&quot;, &quot;value&quot;);&#10;		assert.strictEqual(await bindings.KV.get(&quot;key&quot;), &quot;value&quot;);&#10;	});&#10;	...&#10;});&#10;</code></pre>
<h2 id="more-complex-workers">More complex Workers</h2>
<p>The example given above shows how to test a simple Worker consisting of a single JavaScript file. However, most real-world Workers are more complex than that. Miniflare supports providing all constituent files of your Worker directly using the API:</p>
<pre><code class="language-js">new Miniflare({&#10;	modules: [&#10;		{&#10;			type: &quot;ESModule&quot;,&#10;			path: &quot;src/index.js&quot;,&#10;		},&#10;		{&#10;			type: &quot;ESModule&quot;,&#10;			path: &quot;src/imported.js&quot;,&#10;		},&#10;	],&#10;});&#10;</code></pre>
<p>This can be a bit cumbersome as your Worker grows. To help with this, Miniflare can also crawl your module graph to automatically figure out which modules to include:</p>
<pre><code class="language-js">new Miniflare({&#10;	scriptPath: &quot;src/index-with-imports.js&quot;,&#10;	modules: true,&#10;	modulesRules: [{ type: &quot;ESModule&quot;, include: [&quot;**/*.js&quot;] }],&#10;});&#10;</code></pre>
<h2 id="custom-builds">Custom builds</h2>
<p>In many real-world cases, Workers are not written in plain JavaScript but instead consist of multiple TypeScript files that import from npm packages and other dependencies, which are then bundled by a build tool. When testing your Worker via Miniflare directly you need to run this build tool before your tests. Exactly how this build is run will depend on the specific test framework you use, but for <code>node:test</code> it would likely be in a <code>setup()</code> hook. For example, if you use <a href="/workers/wrangler/">Wrangler</a> to build and deploy your Worker, you could spawn a <code>wrangler build</code> command like this:</p>
<pre><code class="language-js">before(() =&gt; {&#10;	spawnSync(&quot;npx wrangler build -c wrangler-build.json&quot;, {&#10;		shell: true,&#10;		stdio: &quot;pipe&quot;,&#10;	});&#10;});&#10;</code></pre>
