<p>The Workers Vitest plugin has the following known issues:</p>
<h3 id="coverage">Coverage</h3>
<p>Native code coverage via <a href="https://v8.dev/blog/javascript-code-coverage">V8</a> is not supported. You must use instrumented code coverage via <a href="https://istanbul.js.org/">Istanbul</a> instead. Refer to the <a href="https://vitest.dev/guide/coverage">Vitest Coverage documentation</a> for setup instructions.</p>
<h3 id="fake-timers">Fake timers</h3>
<p>Vitest's <a href="https://vitest.dev/guide/mocking.html#timers">fake timers</a> do not apply to KV, R2 and cache simulators. For example, you cannot expire a KV key by advancing fake time.</p>
<h3 id="dynamic-import-statements-with-exports-and-durable-objects">Dynamic <code>import()</code> statements with <code>exports</code> and Durable Objects</h3>
<p>Dynamic <code>import()</code> statements do not work inside <code>export default { ... }</code> handlers when writing integration tests with <code>exports.default.fetch()</code>, or inside Durable Object event handlers. You must import and call your handlers directly, or use static <code>import</code> statements in the global scope.</p>
<h3 id="websockets">WebSockets</h3>
<p>Using WebSockets with Durable Objects is not supported with per-file storage isolation. To work around this, run your tests with shared storage using <code>--max-workers=1 --no-isolate</code>.</p>
<h3 id="storage-isolation">Storage isolation</h3>
<p>Storage isolation is per test file. The test runner will undo any writes to storage at the end of each test file as detailed in the <a href="/workers/testing/vitest-integration/isolation-and-concurrency/">isolation and concurrency documentation</a>. Cloudflare recommends the following actions to avoid common issues:</p>
<h4 id="await-all-storage-operations">Await all storage operations</h4>
<p>Always <code>await</code> all <code>Promise</code>s that read or write to storage services.</p>
<pre><code class="language-ts">// Example: Seed data&#10;beforeAll(async () =&gt; {&#10;	await env.KV.put(&quot;message&quot;, &quot;test message&quot;);&#10;	await env.R2.put(&quot;file&quot;, &quot;hello-world&quot;);&#10;});&#10;</code></pre>
<h4 id="explicitly-signal-resource-disposal">Explicitly signal resource disposal</h4>
<p>When calling RPC methods of a Service Worker or Durable Object that return non-primitive values (such as objects or classes extending <code>RpcTarget</code>), use the <code>using</code> keyword to explicitly signal when resources can be disposed of. See <a href="https://github.com/cloudflare/workers-sdk/tree/main/fixtures/vitest-plugin-examples/rpc/test/unit.test.ts#L155">this example test</a> and refer to <a href="/workers/runtime-apis/rpc/lifecycle#explicit-resource-management">explicit-resource-management</a> for more details.</p>
<pre><code class="language-ts">using result = await stub.getCounter();&#10;</code></pre>
<h4 id="consume-response-bodies">Consume response bodies</h4>
<p>When making requests via <code>fetch</code> or <code>R2.get()</code>, consume the entire response body, even if you are not asserting its content. For example:</p>
<pre><code class="language-ts">test(&quot;check if file exists&quot;, async () =&gt; {&#10;	await env.R2.put(&quot;file&quot;, &quot;hello-world&quot;);&#10;	const response = await env.R2.get(&quot;file&quot;);&#10;&#10;	expect(response).not.toBe(null);&#10;	// Consume the response body even if you are not asserting it&#10;	await response.text();&#10;});&#10;</code></pre>
<h3 id="missing-properties-on-ctx-exports">Missing properties on <code>ctx.exports</code></h3>
<p>The <code>ctx.exports</code> property provides access to the exports of the main Worker. The Workers Vitest integration attempts to automatically infer these exports by statically analyzing the Worker source code using esbuild. However, complex build setups, such as those using virtual modules or wildcard re-exports that esbuild cannot follow, may result in missing properties on the <code>ctx.exports</code> object.</p>
<p>For example, consider a Worker that re-exports an entrypoint from a virtual module using a wildcard export:</p>
<pre><code class="language-ts">// index.ts&#10;export * from &quot;@virtual-module&quot;;&#10;</code></pre>
<p>In this case, any exports from <code>@virtual-module</code> (such as <code>MyEntrypoint</code>) cannot be automatically inferred and will be missing from <code>ctx.exports</code>.</p>
<p>To work around this, add the <code>additionalExports</code> option to your Vitest configuration:</p>
<pre><code class="language-ts">import { cloudflareTest } from &quot;@cloudflare/vitest-plugin&quot;;&#10;import { defineConfig } from &quot;vitest/config&quot;;&#10;&#10;export default defineConfig({&#10;	plugins: [&#10;		cloudflareTest({&#10;			wrangler: { configPath: &quot;./wrangler.jsonc&quot; },&#10;			additionalExports: {&#10;				MyEntrypoint: &quot;WorkerEntrypoint&quot;,&#10;			},&#10;		}),&#10;	],&#10;});&#10;</code></pre>
<p>The <code>additionalExports</code> option is a map where keys are the export names and values are the type of export (<code>&quot;WorkerEntrypoint&quot;</code>, <code>&quot;DurableObject&quot;</code>, or <code>&quot;WorkflowEntrypoint&quot;</code>).</p>
<h3 id="module-resolution">Module resolution</h3>
<p>If you encounter module resolution issues such as: <code>Error: Cannot use require() to import an ES Module</code> or <code>Error: No such module</code>, you can bundle these dependencies using the <a href="https://vitest.dev/config/#deps-optimizer">deps.optimizer</a> option:</p>
<pre><code class="language-ts">import { cloudflareTest } from &quot;@cloudflare/vitest-plugin&quot;;&#10;import { defineConfig } from &quot;vitest/config&quot;;&#10;&#10;export default defineConfig({&#10;	plugins: [&#10;		cloudflareTest({&#10;			// ...&#10;		}),&#10;	],&#10;	test: {&#10;		deps: {&#10;			optimizer: {&#10;				ssr: {&#10;					enabled: true,&#10;					include: [&quot;your-package-name&quot;],&#10;				},&#10;			},&#10;		},&#10;	},&#10;});&#10;</code></pre>
<p>You can find an example in the <a href="/workers/testing/vitest-integration/recipes">Recipes</a> page.</p>
<h3 id="importing-modules-from-global-setup-file">Importing modules from global setup file</h3>
<p>Although Vitest is set up to resolve packages for the <a href="https://github.com/cloudflare/workerd"><code>workerd</code></a> runtime, it runs your global setup file in the Node.js environment. This can cause issues when importing packages like <a href="https://github.com/cloudflare/workers-sdk/issues/6465">Postgres.js</a>, which exports a non-Node version for <code>workerd</code>.
To work around this, you can create a wrapper that uses Vite's SSR module loader to import the global setup file under the correct conditions. Then, adjust your Vitest configuration to point to this wrapper. For example:</p>
<pre><code class="language-ts">// File: global-setup-wrapper.ts&#10;import { createServer } from &quot;vite&quot;;&#10;&#10;// Import the actual global setup file with the correct setup&#10;const mod = await viteImport(&quot;./global-setup.ts&quot;);&#10;&#10;export default mod.default;&#10;&#10;// Helper to import the file with default node setup&#10;async function viteImport(file: string) {&#10;	const server = await createServer({&#10;		root: import.meta.dirname,&#10;		configFile: false,&#10;		server: { middlewareMode: true, hmr: false, watch: null, ws: false },&#10;		optimizeDeps: { noDiscovery: true },&#10;		clearScreen: false,&#10;	});&#10;	const mod = await server.ssrLoadModule(file);&#10;	await server.close();&#10;	return mod;&#10;}&#10;</code></pre>
<pre><code class="language-ts">// File: vitest.config.ts&#10;import { cloudflareTest } from &quot;@cloudflare/vitest-plugin&quot;;&#10;import { defineConfig } from &quot;vitest/config&quot;;&#10;&#10;export default defineConfig({&#10;	plugins: [&#10;		cloudflareTest({&#10;			// ...&#10;		}),&#10;	],&#10;	test: {&#10;		// Replace the globalSetup with the wrapper file&#10;		globalSetup: [&quot;./global-setup-wrapper.ts&quot;],&#10;	},&#10;});&#10;</code></pre>
