<p>A Worker config file may contain configuration for multiple <a href="/workers/wrangler/environments/">Cloudflare environments</a>.
With the Cloudflare Vite plugin, you select a Cloudflare environment at dev or build time by providing the <code>CLOUDFLARE_ENV</code> environment variable.
Consider the following example Worker config file:</p>
<div class="nb-wrangler-config">
@markup("md", "content/.markup/bodies/17400.md")
</div>
<p>If you run <code>CLOUDFLARE_ENV=production vite build</code> then the output <code>wrangler.json</code> file generated by the build will be a flattened configuration for the 'production' Cloudflare environment, as shown in the following example:</p>
<pre tabindex="0"><code class="language-json">{&#10;	&quot;name&quot;: &quot;my-worker&quot;,&#10;	&quot;compatibility_date&quot;: &quot;2025-04-03&quot;,&#10;	&quot;main&quot;: &quot;index.js&quot;,&#10;	&quot;vars&quot;: { &quot;MY_VAR&quot;: &quot;Production var&quot; }&#10;}&#10;</code></pre>
<p>Notice that the value of <code>MY_VAR</code> is <code>Production var</code>.
This flattened configuration combines <a href="/workers/wrangler/configuration/#top-level-only-keys">top-level only</a>, <a href="/workers/wrangler/configuration/#inheritable-keys">inheritable</a>, and <a href="/workers/wrangler/configuration/#non-inheritable-keys">non-inheritable</a> keys.</p>
<aside class="nb-aside note">
@markup("md", "content/.markup/bodies/17399.md")
</aside>
<p>Cloudflare environments can also be used in development.
For example, you could run <code>CLOUDFLARE_ENV=development vite dev</code>.
It is common to use the default top-level environment as the development environment and then add additional environments as necessary.</p>

<h2 id="secrets-in-local-development">Secrets in local development</h2>
<aside class="nb-aside caution">
@markup("md", "content/.markup/bodies/17397.md")
</aside>
<p>Put secrets for use in local development in either a <code>.dev.vars</code> file or a <code>.env</code> file, in the same directory as the Wrangler configuration file.</p>
<aside class="nb-aside note">
@markup("md", "content/.markup/bodies/17396.md")
</aside>
<aside class="nb-aside info">
@markup("md", "content/.markup/bodies/17395.md")
</aside>
<p>These files should be formatted using the <a href="https://hexdocs.pm/dotenvy/dotenv-file-format.html">dotenv</a> syntax. For example:</p>
<pre tabindex="0"><code class="language-bash">SECRET_KEY=&quot;value&quot;&#10;API_TOKEN=&quot;eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9&quot;&#10;</code></pre>
<aside class="nb-aside caution">
<h3 class="nb-aside-title" id="do-not-commit-secrets-to-git">Do not commit secrets to git</h3>
@markup("md", "content/.markup/bodies/17394.md")
</aside>
<p>To set different secrets for each Cloudflare environment, create files named <code>.dev.vars.&lt;environment-name&gt;</code> or <code>.env.&lt;environment-name&gt;</code>.</p>
<p>When you select a Cloudflare environment in your local development, the corresponding environment-specific file will be loaded ahead of the generic <code>.dev.vars</code> (or <code>.env</code>) file.</p>
<ul>
<li>When using <code>.dev.vars.&lt;environment-name&gt;</code> files, all secrets must be defined per environment. If <code>.dev.vars.&lt;environment-name&gt;</code> exists then only this will be loaded; the <code>.dev.vars</code> file will not be loaded.</li>
<li>In contrast, all matching <code>.env</code> files are loaded and the values are merged. For each variable, the value from the most specific file is used, with the following precedence:
<ul>
<li><code>.env.&lt;environment-name&gt;.local</code> (most specific)</li>
<li><code>.env.local</code></li>
<li><code>.env.&lt;environment-name&gt;</code></li>
<li><code>.env</code> (least specific)</li>
</ul>
</li>
</ul>

<h2 id="combining-cloudflare-environments-and-vite-modes">Combining Cloudflare environments and Vite modes</h2>
<p>You may wish to combine the concepts of <a href="/workers/wrangler/environments/">Cloudflare environments</a> and <a href="https://vite.dev/guide/env-and-mode.html#modes">Vite modes</a>.
With this approach, the Vite mode can be used to select the Cloudflare environment and a single method can be used to determine environment specific configuration and code.
Consider again the previous example:</p>
<div class="nb-wrangler-config">
@markup("md", "content/.markup/bodies/17401.md")
</div>
<p>Next, provide <code>.env.staging</code> and <code>.env.production</code> files:</p>
<pre tabindex="0"><code class="language-sh">CLOUDFLARE_ENV=staging&#10;</code></pre>
<pre tabindex="0"><code class="language-sh">CLOUDFLARE_ENV=production&#10;</code></pre>
<p>By default, <code>vite build</code> uses the 'production' Vite mode.
Vite will therefore load the <code>.env.production</code> file to get the environment variables that are used in the build.
Since the <code>.env.production</code> file contains <code>CLOUDFLARE_ENV=production</code>, the Cloudflare Vite plugin will select the 'production' Cloudflare environment.
The value of <code>MY_VAR</code> will therefore be <code>'Production var'</code>.
If you run <code>vite build --mode staging</code> then the 'staging' Vite mode will be used and the 'staging' Cloudflare environment will be selected.
The value of <code>MY_VAR</code> will therefore be <code>'Staging var'</code>.</p>
<p>For more information about using <code>.env</code> files with Vite, see the <a href="https://vite.dev/guide/env-and-mode#env-files">relevant documentation</a>.</p>
